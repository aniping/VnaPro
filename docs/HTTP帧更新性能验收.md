# HTTP 帧更新性能验收

验收日期：2026-10-12。环境为 Windows、MinGW/GCC 10.3 Debug、TDC1VN10 模拟设备，noise 模式与种子 42。

## 故障与复现

连续扫描使用 4000 个原始频点、四条迹线。HTTP 仍传输每条 2001 个绘图点，共 8004 个迹线采样值，响应约 0.8 MB。

基线提交 `63deec0` 下，真实帧响应约 2.7 秒，其中首字节等待约 2.6 秒。浏览器显示帧约每三秒变化一次；即使使用 HOLD 已完成帧，慢响应仍能复现。201 点四迹线的响应约 320 毫秒。

直接调用当前 C++ API 和编码器进行拆分测量：

| 4000 点、四迹线 | 耗时或次数 |
| --- | --- |
| HttpApi 构造帧响应 | 12.37 ms |
| JsonEncoder 无休眠推进 | 36.76 ms |
| Advance(256) 调用次数 | 477 |
| 分片之间固定等待 5 ms | 至少约 2380 ms |

主因是 HTTP 未参与共享网络就绪等待，增量编码每轮之后都可能等待 SCPI 的 5 ms 超时。前端实际解码、轮询和绘图路径回放未发现秒级 CPU 耗时。

## 修改与结果

HTTP 套接字参与共同的 SocketPollSet；有可立即推进的编码或文件工作时采用零超时检测，其他轮次继续等待真实事件。每轮的 256 步编码与 32 KiB 发送预算保留，以保证不同连接及服务任务公平推进。

编码完成后的未发送字节只注册可写事件。慢接收端造成背压时，执行器继续等待就绪；空闲状态也保留短周期等待。

同一 8191 验收服务、相同点数及显示集合的真实 HTTP 中位耗时：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 帧完整响应 | 2736 ms | 59.51 ms |
| 等待首字节 | 2609 ms | 58.84 ms |
| 状态查询 | 38 ms | 0.99 ms |

修复后五次帧请求最大耗时为 94.30 ms。浏览器以 250 ms 间隔观察八秒，连续显示了 17 个帧序号，变化间隔约 0.51 秒，与该模拟设备的产帧节拍一致；HTTP 响应速度和新测量产生速度分别测量。

## 回归范围

`WebFrameSchedulingTest.py` 启动独立端口的真实 TDC1VN10 服务，并发请求四条 S 参数迹线、带控制令牌的状态以及只读 SCPI。验证完整原始频轴、当时共同抽点下标、当前帧身份、响应时间及控制查询的中位与最大延迟。

三次快速读取允许返回同一完整帧，帧序号只要求单调。采集推进另用带截止时间的窗口验证，避免将读取变快误判为停采。另保留不消费 HTTP 响应的客户端，检查其余查询仍能完成。

`socket_poll_set` 使用真实 TCP 套接字验证监听和读写唤醒；实际填满非阻塞发送缓冲，直到 WouldBlock 且无可写事件，再消费对端字节并验证发送恢复。无严格毫秒断言。

```powershell
ctest --test-dir cmake-build-debug --output-on-failure -R "^(web_frame_scheduling|socket_poll_set)$"
```

本次正式 Debug 构建全量 42 项 CTest 通过，包括采集并发、共享显示状态、HTTP、SCPI、驱动、离线依赖与有序关闭。前端源代码及采集配置未因提速而调整。

## 2026-10-14 完整扫频显示修正

以上记录保留 2026-10-12 的真实验收结果。2026-10-14 发现固定 2001 点上限使 4000 和 8000 点扫描都只向网页提供 2001 点；同一 HOLD 帧的 SCPI 分别返回完整 4000 和 8000 点，采集配置已经生效，损失发生在 HTTP 传输选点。

首轮修正（下方进一步修订）改为单条最多 10001 点、总采样预算 40004，一至四迹线保留全部原始扫频点。更多迹线仅在总预算不足时抽点，并通过 `originalPointCount`、`displayPointCount`、`decimated` 明示；这是项目资源限制，不是 ZNB 原机规则。前端只是解码和逐点绘制后端数据，格式和采样策略仍在 C++ 中确定。

首轮 JSON 编码上限调整为 16 MiB，以覆盖完整 Smith、逆 Smith、Polar 和实虚投影；静态文件上限保持 4 MiB。每轮 256 步编码、32 KiB 发送和有界连接数保持，单连接仍只保留当前响应，不积压连续帧。

`WebFrameResolutionTest.py` 对 201、4000、8000、10001 点分别验证一至四条迹线，与同一冻结帧的 SCPI 完整频轴及 IQ 逐值一致。`WebFrameSchedulingTest.py` 改为实际传输四条 4000 点完整迹线，并继续验证控制查询公平性和慢客户端隔离。多迹线总预算及完整最大点数 Smith 编码由 `web_frame_selection` 验收。

```powershell
ctest --test-dir cmake-build-debug --output-on-failure -R "^(web_frame_resolution|web_frame_scheduling|web_frame_selection|web_display_control|web_api|web_http_integration)$"
```

| --- | --- | --- | --- |
| 4000 | 2001 / 61.45 ms | 4000 / 107.94 ms | 1,587,325 |
| 8000 | 2001 / 65.39 ms | 8000 / 215.37 ms | 3,155,544 |

每组十次请求，时间包含后端投影、编码和本机完整响应收取，不包含浏览器绘制。10001 点四迹线另外五次实测：Smith 5,351,225 字节 / 342.79 ms，逆 Smith 5,351,238 字节 / 332.09 ms，Polar 6,884,770 字节 / 438.81 ms，实虚格式 4,551,170 字节 / 294.82 ms，均在 16 MiB 有界响应内。更高传输成本来自完整采样保留，不应恢复固定 2001 点截断来掩盖；后续若继续提高多迹线吞吐，应采用保真显示投影或标准二进制传输。

## 2026-10-14 所有显示迹线保留完整采样

进一步取消按迹线数量均匀抽点的策略：最多 128 条显示迹线，每条均保留全部扫频点（单条上限 10001），不再分摊 40004 总点数预算。`sampleIndexes` 连续包含所有原始下标，`originalPointCount=displayPointCount`、`decimated=false`。普通 JSON 和 `encoding=packed` 始终读取同一不可变帧，区别仅在数组表示。

WebUI 默认请求紧凑数组：数值/null 为 f64le，布尔为 u8，状态字符串为 enum8 字典，字节使用 Base64；不采用 float32，也不重算测量。轴及每条迹线的数值树生成后立即转成紧凑表示，避免先构造全部普通数组造成较高临时内存占用。兼容的普通 JSON 单响应上限为 256 MiB；每轮 256 步编码、32 KiB 发送和单连接一个当前响应继续保持。

独立 VN10 noise/seed 42、Debug、HOLD 四迹线实测（十次请求中位数，仅 HTTP 完整响应）：

| 点数 / 格式 | 普通 JSON 中位耗时 | 紧凑响应中位耗时 | 紧凑响应字节 |
| --- | --- | --- | --- |
| 4000 / dB Mag | 107.94 ms | 52.71 ms | 853,579 |
| 8000 / dB Mag | 215.37 ms | 88.38 ms | 1,685,587 |
| 10001 / dB Mag | 261.32 ms | 119.85 ms | 2,101,827 |
| 10001 / Smith | 342.79 ms | 158.22 ms | 3,009,179 |
| 10001 / Polar | 438.81 ms | 160.24 ms | 3,062,772 |

大集合真实网络验收使用紧凑表示：16 条 × 10001 点为 7,766,162 字节，响应及独立 Python 解码总耗时 478.45 ms；128 条 × 10001 点为 60,633,327 字节，总耗时 3816.37 ms。该数值包含所有迹线完整传输与独立解码，不是浏览器帧率。四迹线 4000 点并发回归的帧中位耗时为 120.12 ms，状态查询为 1.97 ms、SCPI 为 0.30 ms，最大控制查询延迟分别为 18.45 ms 和 19.17 ms。

窄峰回归在 4000 点原始下标 2 注入单点峰，并显示十六条迹线；原均匀抽点遗漏该位置，修改前同一测试失败，修改后复数及 dB 投影均保留。容量回归覆盖 16 / 128 条最大点数 Smith；网络回归逐字段比较普通与紧凑表示，覆盖完整频轴、IQ、有效位、十三种格式所需数组的代表格式及帧身份。实际后端紧凑响应回放到当前 WebUI 解码和 Canvas 路径，4000 / 8000 / 10001 点分别绘制完整 4000 / 8000 / 10001 个点，没有前端抽点。
