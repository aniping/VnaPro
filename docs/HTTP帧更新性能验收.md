# HTTP 帧更新性能验收

验收日期：2026-10-12。环境为 Windows、MinGW/GCC 10.3 Debug、TDC1VN10 模拟设备，noise 模式与种子 42。

## 故障与复现

连续扫描使用 4000 个原始频点、四条迹线。HTTP 仍传输每条 2001 个绘图点，共 8004 个迹线采样值，响应约 0.8 MB。

基线提交 `63deec0` 下，真实帧响应约 2.7 秒，其中首字节等待约 2.6 秒。浏览器显示帧约每三秒变化一次；即使使用 HOLD 已完成帧，慢响应仍能复现。201 点四迹线的响应约 320 毫秒。

直接调用当前 C++ API 和编码器进行拆分测量：

| 4000 点、四迹线 | 耗时或次数 |
| --- | --- |
| HttpApi 构造帧响应 | 12.37 ms |
| JsonEncoder 无休眠推进 | 36.76 ms |
| Advance(256) 调用次数 | 477 |
| 分片之间固定等待 5 ms | 至少约 2380 ms |

主因是 HTTP 未参与共享网络就绪等待，增量编码每轮之后都可能等待 SCPI 的 5 ms 超时。前端实际解码、轮询和绘图路径回放未发现秒级 CPU 耗时。

## 修改与结果

HTTP 套接字参与共同的 SocketPollSet；有可立即推进的编码或文件工作时采用零超时检测，其他轮次继续等待真实事件。每轮的 256 步编码与 32 KiB 发送预算保留，以保证不同连接及服务任务公平推进。

编码完成后的未发送字节只注册可写事件。慢接收端造成背压时，执行器继续等待就绪；空闲状态也保留短周期等待。

同一 8191 验收服务、相同点数及显示集合的真实 HTTP 中位耗时：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 帧完整响应 | 2736 ms | 59.51 ms |
| 等待首字节 | 2609 ms | 58.84 ms |
| 状态查询 | 38 ms | 0.99 ms |

修复后五次帧请求最大耗时为 94.30 ms。浏览器以 250 ms 间隔观察八秒，连续显示了 17 个帧序号，变化间隔约 0.51 秒，与该模拟设备的产帧节拍一致；HTTP 响应速度和新测量产生速度分别测量。

## 回归范围

`WebFrameSchedulingTest.py` 启动独立端口的真实 TDC1VN10 服务，并发请求四条 S 参数迹线、带控制令牌的状态以及只读 SCPI。验证完整原始频轴、共同抽点下标、当前帧身份、响应时间及控制查询的中位与最大延迟。

三次快速读取允许返回同一完整帧，帧序号只要求单调。采集推进另用带截止时间的窗口验证，避免将读取变快误判为停采。另保留不消费 HTTP 响应的客户端，检查其余查询仍能完成。

`socket_poll_set` 使用真实 TCP 套接字验证监听和读写唤醒；实际填满非阻塞发送缓冲，直到 WouldBlock 且无可写事件，再消费对端字节并验证发送恢复。无严格毫秒断言。

```powershell
ctest --test-dir cmake-build-debug --output-on-failure -R "^(web_frame_scheduling|socket_poll_set)$"
```
