# 硬件适配层设计与实现评审

| 项目 | 内容 |
| --- | --- |

| 对照依据 | `docs/硬件适配层软件设计.md`、`docs/硬件适配层原型说明.md`、当前源码与测试 |

| 当前范围 | 仅 Simulator 驱动 |

## 1. 结论

原评审指出的 CommandId 完成事件缺失、Simulator 能力虚高、`perPoint*` 验证
缺口和帧完整性过度依赖计数，都是合理且需要修复的问题。但原文也有三类
结论不够严谨：无可量化依据的完成百分比、把本版明确不实现的真机驱动当成缺陷，
以及在未先定义策略时把 Simulator 重复 `open()` 直接判定为错误。

当前版本已收口为“`VnaHardware` + `VnaDriverSimulator` 可验证闭环”。公司 VNA 和
商用 VNA 不实现、不创建占位目标、不纳入本版验收。按该范围，本轮没有阻塞实现的产品决策；
资源隔离、命令准入、连续复用和构建门禁均可直接以工程约束关闭。真机资源阈值与吞吐目标属于
后续数值确认，不应阻塞当前正确性实现。

## 2. 原评审的合理部分

| 原问题 | 复核结论 | 处理 |
| --- | --- | --- |
| abort / disconnect 成功无 CommandId 完成事件 | 合理，破坏异步命令一致性 | 新增 `AbortCompletedEvent` 和 `DisconnectCompletedEvent` |
| Simulator 声明外部触发但不等待触发 | 合理，属于能力虚报 | 只声明并接受内部触发 |
| Simulator 声明逐点 dwell 但执行不依赖该值 | 合理，计划语义会被静默改变 | 取消逐点 dwell 能力声明 |
| 宿主未落实 `perPoint*` 能力位 | 合理，能力快照未形成 ABI 前门禁 | 在 `validatePlan` 检查 IFBW、功率和 dwell 的跨点一致性 |
| 只用收帧总数判断完整 | 合理，“重复 + 缺失”可以得到相同总数 | 改为预编译布局/点覆盖跟踪 |
| 背压耗尽语义不一致 | 合理，数据已无法完整交付 | 缓冲池或队列耗尽统一终结为 `DataLoss` |
| Prepare 状态与诊断文案不一致 | 合理，会干扰日志排障 | 文案与 Idle / Prepared 实际状态对齐 |

## 3. 原评审需要改进的部分

### 3.1 不应使用主观完成百分比

“约 75%”和“约 40%”没有分母、权重和测量方法，不能支持排期或发布决策。
改用可追溯的契约项、测试证据和门禁结果表达完成状态。

### 3.2 未实现真机驱动不是本版缺陷

当前产品决策已明确只实现 Simulator。Company / Commercial、Windows DLL 和真机归一化
可作为后续版本输入，但不能继续列为当前实现缺陷或降低当前完成度。

### 3.3 Simulator 重复打开是策略问题

虚拟设备不会争用同一物理传输。当前策略是：同一 `DeviceId` 可多次 `open()`，每次
创建独立状态、配置、扫描和缓冲池的虚拟会话。后续真机驱动应另行定义独占或
共享策略，不应倒推 Simulator 必须单开。

### 3.4 `estimatedBytesPerPoint` 原问题定性不准确

实现的真实含义是“单频点峰值复数波值载荷”，本就不包含 `qualityFlags` 和块头。
问题在于原文没有把该口径写清，而不是计算式必然错误。现已明确该字段不能
单独作为完整带宽或内存预算。

### 3.5 shutdown 需要以前置条件评审

`shutdown()` 不是普通命令，而是关闭事件域的同步边界。契约要求调用方将它与新的
发现、打开和会话 API 外部同步。进入关闭后，已分配 ID 的事件观察义务失效；
`shutdown()` 返回后不再有 Sink 回调。在禁止的并发调用下“收到 ID 但等不到事件”
不应当作正常使用缺陷；该前置条件必须写入公开文档和生命周期测试。

## 4. 原评审遗漏的高优先级问题

### 4.1 Abort 可能覆盖真实故障

“驱动已接受中止”只是中间状态。如果 Worker 最终返回 `ConnectionLost`、`Timeout`、
`DataLoss` 或 `HardwareFault`，这些具体故障必须优先于 abort accepted，否则日志和
上层恢复策略都会失真。

修复后的固定契约为：

1. 扫描实际终态为 `Aborted` 时，先发布 `SweepCompletion(Aborted)`。
2. 随后发布带原 `commandId` 和 `sweepId` 的 `AbortCompletedEvent`。
3. 如果实际终态是具体故障，发布带该原因的 `SweepCompletion`，中止命令发布
   `CommandFailedEvent`，不发布 `AbortCompletedEvent`。
4. `InvalidState` 可以表示 Start/Execute 交接尚未完成，也可以表示扫描已越过收尾
   线性化点；宿主等待 Worker 实际终态裁决，不得把自然完成事后改写为
   `Aborted`。

### 4.2 收帧总数相等不代表完整覆盖

两次提交同一范围并缺失另一范围时，收帧总数仍可以等于预期数。因此 Hardware 的
`FrameTracker` 必须按 `prepare()` 编译的合法 `(layoutId, pointIndex)` 组合跟踪，它是覆盖和
扫描完整性的权威校验者，并在热路径同时验证：

- `layoutId` 已由本次配置定义；
- 块范围连续、不越界且范围内每个点都适用该布局；
- 与既有提交无重复、无部分重叠；
- 事件入队失败时回滚预留；
- 扫描成功返回时所有合法组合已完整覆盖，否则终结为 `DataLoss`。

`VnaAcquisition` 不复制上述 bitmap 或再建块队列。它在公开 `IVnaHardware` 边界仅保留
`O(L)` 防御状态：一个全局下一 `sequence` 和每个 layout 的下一预期点偏移。这道轻量防线
在复制前拒绝断序、重放、重叠和乱序，但不与 `FrameTracker` 争夺完整性权威。`L` 是
当前 prepared layout 数。

### 4.3 ABI 次版本兼容声明与实现不符

当前函数表和宿主都按当前大小与版本工作，没有完整的双向小版兼容协商。因此
本版必须精确匹配 ABI `1.0`，而不是仅匹配主版本。`structSize` 只用于顶层函数表、
创建信息和顶层 View；不带 `structSize` 的嵌套叶子结构在 V1 冻结。

### 4.4 ABI 信任边界不能只验证指针

ABI 字段是不可信整数，C++ 枚举也可以通过强制转换得到非法值。因此本版还需
校验全部保留字段为零，拒绝未知触发/波类型、能力/执行位和质量标志位。
尾部短批必须使用本次 Acquire 返回的 `pointCapacity` 作为多波跨距，否则会静默
读错第二个及后续波值。

### 4.5 固定槽位不等于内存有界（已关闭）

异常或错误驱动仍可能返回单项合法、组合后不合理的波数与块容量；独立维度上限不能替代
`slotCount × Wmax × waveBlockPointCapacity × 样本字节数` 的 checked 总字节门禁。
当前实现从受信配置读取 slot 数，生产样例为 2，并在分配前按实际布局执行 64 MiB 总载荷门禁。

### 4.6 Prepared plan 聚合内存和重复拷贝（已关闭工程门禁）

驱动能力的 points、每点激励和端口上限都是单维限制，未约束 fully-expanded plan 的聚合大小。
当前 Hardware 对 requested/prepared/pending/event-retained 四个生命周期执行 checked 聚合预算，
并按容器 `capacity()` 计量宿主持有的分配。Prepare 事件和 Acquisition 共享不可变 snapshot；
同一配置重复 Start 复用 FrameTracker 与波池。逻辑预算不等于进程 RSS，allocator、驱动缓冲和
调用方延寿仍须用最终部署基准验证。

## 5. 本次修复后的契约地图

| 能力块 | 当前契约 | 验收重点 |
| --- | --- | --- |
| 驱动范围 | 仅 `VnaDriverSimulator` | 无 Company / Commercial 占位目标 |
| ABI | 精确 `1.0`，顶层校验大小，保留/未知位失败关闭 | C99/C++17 布局、版本、枚举和短批跨距契约 |
| 触发 / 驻留 | 仅内部触发，不声明逐点 dwell | 外部触发在宿主和驱动两层都被拒绝 |
| 逐点设定 | Simulator 支持逐点 IFBW 和功率 | 能力为假时变化计划在 ABI 前被拒绝 |
| 流式帧 | Hardware `FrameTracker` 权威覆盖；Acquisition 仅保留 `O(L)` 边界防御 | 非法提交不交付，缺口不得误报 Completed |
| 背压 | 缓冲池或队列有界等待后耗尽 | 统一为 `DataLoss`，不静默丢数 |
| 容量门禁 | slotCount、波池、requested/prepared/pending/event-retained 均有部署预算 | 精确边界、溢出、慢回调滞留及峰值 RSS |
| Abort | `SweepCompletion(Aborted)` 先于 `AbortCompleted` | 具体故障优先，不被 abort accepted 覆盖 |
| Disconnect | 进入 `Disconnected` 后发布 `DisconnectCompleted` | 成功和失败都可用原 CommandId 关联 |
| 关闭 | 调用方外部同步，开始关闭即终止事件观察义务 | 返回后无 Sink 回调且不再使用会话 |
| 重复 `open()` | Simulator 创建多个独立虚拟会话 | 会话状态、配置、扫描和缓冲池不共享 |

## 6. 验证结果与环境限制

| 门禁 | 结果 |
| --- | --- |
| 现代编译器 Debug 测试 | 104/104 个 CTest 用例通过，包含 C99 ABI 契约程序和 Acquisition 大形状测试 |
| 并发稳定性 | 9 个生命周期、shutdown、回调门禁和 Abort 乱序用例各重复 50 次，共 450 次通过 |
| UBSan | 独立门禁的 104/104 个 CTest 用例通过 |
| LLVM 22.1.8 ASan + LSan + UBSan | 104/104 个 CTest 用例通过，三类 sanitizer 均无报告 |
| 现代编译器 Release 生产目标 | Hardware、Acquisition 和 Simulator 编译通过 |
| Docker GCC 7.3.0 生产目标 | Linux/amd64、单 CPU 串行全量编译通过 |
| 本机 Release 目标吞吐基准 | `09c7de8`；M1 / 16 GB，10/30 kHz P95 墙钟/逻辑时间 `< 1.00013` |
| 格式与基础检查 | clang-format 22.1.8 检查 84 个变更 C++ 文件，`git diff --check` 通过 |
| 代码规范结构门禁 | Tree-sitter 0.23.2 / C++ 0.23.4 检查 84 个文件，0 finding、0 violation；66 个复杂度 advisory 均未超过 required 上限 10 |

`check-coding-standards` 的 C++ style、structure、API/lifetime、correctness、concurrency 和 security
规则均已执行；两路语义复核没有 required 或高风险遗留项。CMake、INI 和 Markdown 不属于当前
技能的 C++/Python 规则包，已通过构建、严格配置解析、`git diff --check` 和人工一致性复核覆盖，
不把“不支持”误写成规则通过。

GCC 7.3 在 arm64 主机仿真 amd64 时曾于多个无关翻译单元随机触发 `cc1plus` 段错误，重试后同一
源码范围全量链接成功。这证明当前源码兼容 GCC 7.3，但若发布门禁要求一次 clean build 零重试，
仍应在原生 x86_64 runner 补跑；不能把仿真器稳定性等同于源码确定性。

[本机目标吞吐基准](../benchmarks/LocalThroughputBenchmark.cpp) 使用 10,000 点、每点 4 个顺序激励、
每激励 4 波的 3,200,000 B 有效帧载荷。10 MHz 软件压力管线的 P95 有效载荷吞吐至少
42.358 MiB/s；大块完整帧组装微基准的“分配 + 校验/复制 + 冻结”P95 至少 13,054 MiB/s。
这些是 Simulator 本机回归基线；`1/IFBW` 只是其逻辑时间模型，不是普适物理下限，也不能
关闭真机生产吞吐、CPU、RSS 或长稳门禁。

量化成功路径不需要当前决策：ABI 1.0 无法返回量化后的 `effectivePlan`，因此当前版
继续对任何 `quantized` 结果失败关闭。Simulator 的默认开路噪声精确为
`measured = nominal * (1 + relativeNoise) + additiveNoise`：每个 `a/b` 通道都有独立的复白噪声，
只有非零 `nominal` 会产生乘性残余 trace noise 贡献，两者复 RMS 均按 `sqrt(IFBW)` 缩放。
噪声跨 Sweep/点/通道变化；可配置噪声档位、过载、失锁、断线注入、Windows 加载和真机波量归一化
仍是后续版本项，不影响 Simulator-only 当前版范围收口。

## 7. 最终评审结论

修订后的设计不再用未实现真机驱动衡量当前版，也不再用无根据百分比代替验收证据。
当前版的正确性结论应只由以下事实支持：Simulator 能力与行为一致；每个异步命令
在存活事件域且订阅有效时可关联终结；扫描帧按合法集合完整覆盖；故障原因不被中止覆盖；
背压耗尽不静默丢数；关闭后不再回调。功能、资源隔离、Continuous 复用、编译和代码规范门禁
已经通过，当前 Simulator-only 版本可作为正确性与容量受控原型；本机基准也已建立回归基线。
仍不能据此宣称真机生产吞吐通过：
目标 Sweep/s、首批延迟、完成间隙 P99、CPU、RSS 和真机长稳值尚未由产品场景给出并实测。
