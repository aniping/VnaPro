# VnaPro 架构依据与取舍矩阵

> 本文件是证据体系入口。详细事实、逆向记录、开源机制和决策验收分别由四个子文件唯一维护。

## 1. 如何判断证据等级

查证一条设计结论时，按下面四步判断：

1. 先确认来源是否绑定了型号、版本、提交或内容哈希；
2. 再区分来源直接证明的是产品行为、二进制边界、开源机制，还是本项目推断；
3. 看到证据缺口（`GAP-*`）或待补证（`Pending`）时，必须把相关能力视为未证实或待解禁；
4. 最后通过架构决策（`DEC-*`）反向找到验收方式，不能用“资料没有反对”代替证据。

“以 ZNB、SNA 为准”只能解释为：以商用品可观察的对象语义、状态机、数据访问点、兼容性和错误行为作为产品需求基线。用户手册、SCPI、COM/TLB 和 DLL 导出都不能证明厂商内部源码如何分层。

不存在适用于所有问题的一条总排序。每条结论必须分别评价：来源真实性、与结论的直接性、可重复性、跨环境可移植性和适用范围。例如商用手册是产品外部行为的一手来源，却不能替代数值算法的独立 oracle；固定提交源码能直接证明其实现机制，却不能决定商用产品模型；本机二进制哈希能证明对象字节身份，却不能自动证明官方来源。选择证据时先按结论类型匹配，再比较上述五个维度。

### 1.1 证据标签

| 标签 | 能证明什么 | 使用限制 |
| --- | --- | --- |
| 观察事实 | 手册、协议、二进制导入/导出或源码可直接复核的内容 | 不得外推未公开内部结构 |
| 跨厂商不变量 | 至少两个独立商用品呈现的相同核心语义 | 必须逐项核对适用型号和版本 |
| 产品特例 | 某型号或版本特有的能力与限制 | 进入产品兼容配置（`Profile`），不固化进核心 |
| 架构推断 | VnaPro 为满足事实选择的内部设计 | 必须关联证据缺口和验收 |
| 拒绝照搬 | 来源中存在但不满足本项目目标的耦合 | 只作反例，不继承其边界 |

### 1.2 稳定引用 ID

- `SRC-*`：固定来源或分析对象；绑定版本、提交或内容哈希。
- `EV-COM-*`：商用品手册或协议的可观察证据。
- `EV-REV-*`：本机取得、按哈希绑定的 SNA 对象集之静态逆向观察；来源真实性未闭环时必须保留 Local 标签。
- `EV-OSS-*`：固定提交的开源代码证据。
- `DEC-*`：VnaPro 架构决策；详细定义和验收只在决策文件维护。
- `GAP-*`：证据缺口，即当前资料明确不能证明的事项；关闭前保持未证实或待解禁。

ID 一经被其他文档引用不得改名或重编号。事实范围实质变化时新增 ID；来源替换时也新增 Source ID，不复用旧 ID。后缀为 -PENDING 的来源只预留采集容器，不能作为已存在证据。

证据缺口（`GAP-*`）还必须区分两种用途：

- **内部闭包缺口**：描述 VnaPro 尚须用契约测试、故障注入或可重复计算关闭的内部义务，可以进入 `ARCH-*` 的“阻断性内部缺口”列；
- **来源证明边界**：例如“商用品资料不证明内部 single-live 基数”。它只防止把项目策略冒充来源事实，不能由 VnaPro 内部测试关闭，也不得阻断原生能力（Native）的 `ARCH-*` 验收门。需要声明厂商兼容时，应另走精确产品兼容配置的 `GATE-COMPAT-*` 验收门与交互记录缺口。

## 2. 四个查证分区

| 要查什么 | 唯一详细入口 |
| --- | --- |
| ZNB、SNA 手册和协议直接呈现的产品行为，以及待采集 transcript | [01：商用品行为证据](./架构依据/01-商用品行为证据.md) |
| SNA 二进制导入/导出、静态依赖和本地迁移资产边界 | [02：SNA 逆向证据](./架构依据/02-SNA逆向证据.md) |
| LibreVNA、NanoVNA 固定提交中可借鉴的机制与反例 | [03：开源机制参考](./架构依据/03-开源机制参考.md) |
| VnaPro 决策内容、证据/缺口反向映射和最低验收 | [04：决策与验收映射](./架构依据/04-决策与验收映射.md) |

四区不能相互冒充：商用品行为不能证明厂商内部实现；逆向观察不能决定领域所有权；开源机制不能升级为商用品语义；本项目推断不能回写成来源事实。

### 2.1 唯一维护规则

- 来源身份、版本、URL 和哈希只在所属证据文件详细登记；
- 商用品观察及其不能证明的边界只在商用品文件详细登记；
- 二进制观察和迁移资产边界只在 SNA 逆向文件详细登记；
- 固定提交的代码机制和反例只在开源文件详细登记；
- 决策内容和最低验收只在决策文件详细登记。

其他文件可以引用 ID，但不得复制一份可独立漂移的详细定义。

### 2.2 跨文件引用规则

证据条目只写它约束的架构决策 ID；架构决策条目反向列出证据/缺口 ID，并给出最低验收。这样既能从事实找到设计，也能从设计回查依据，而不重复维护结论正文。

产品差异若只有网页线索、匿名经验或未采集的交互记录（transcript），标为 `NonNormativeProfileLead`，不分配证据/缺口 ID，也不参与验收门判定。只有进入当前规范的缺口才保留 `GAP-*`，并必须反链至少一个架构决策；单产品观察要成为正式证据，同样必须有唯一正文和架构决策反链。

### 2.3 架构验收门与厂商兼容验收门分开

- `ARCH-*` 只评价 VnaPro 内部决策、内部缺口和测试，不把 ZNB/SNA 的交互记录缺口合取为全局前置条件；
- 每个 `ARCH-*` 验收范围（`scope`）只能消费不晚于该范围激活阶段的决策/缺口；后期模型可以细化早期公共边界，但不能反向改变旧回执含义。例如 R2 通用结果责任不能以 S1 产品溯源/实时当前结果代替，R2 Prepare/Rebind 并发也不能以 S1 Channel single-live 代替；
- 一个验收范围的义务扩展时，继续扩展该范围已有的决策/缺口闭包，不为同一事实另建平行映射。例如 S3 的五类 `CalibrationAttempt` 与 `Binding` 唯一责任仍由 `NUM-CAL@S3` 单行映射，S7 的 `ChannelDelete`/`CatalogDelete` 恢复仍由 `PERSIST-SESSION@S7` 单行映射；
- 先到者胜出（first-wins）、责任原子移交、启动恢复与安全退役等恢复协议是 VnaPro 内部可验证义务，不得因为 ZNB/SNA 未公开内部实现就降级，也不得反写成商用品内部事实；
- 厂商兼容声明按 `(ProductProfileKey, GATE-COMPAT-domain)` 单独判定，型号、固件、选件或域变化都要重验；
- `Passed` 必须绑定验收门、阶段化断言范围及版本、代码/构建修订、精确产品兼容配置/能力修订和证据/测试包哈希。任一输入变化后，旧回执只能审计，不能继续放行。

阶段化断言何时激活只查[架构约束 §6](./架构设计/06-架构约束与验收索引.md#6-阶段切片与十六个阻断性验收门)，评估键和回执协议只查[详细设计 05](./详细设计/05C-依赖验收与竞态.md#1231-验收门评估键与回执)。

## 3. 推荐查证路径

### 3.1 从设计正文查证

1. 在架构或详细设计中找到架构决策 ID（`DEC-*`）；
2. 进入[决策与验收映射](./架构依据/04-决策与验收映射.md)，查看决策内容、证据/缺口和最低验收；
3. 再按证据 ID 前缀进入商用品、逆向或开源文件核对原始来源与边界；
4. 若存在证据缺口、待补证或待解禁验收门，不得把兼容性写成已完成。

### 3.2 从来源反查设计

1. 先在对应证据文件找到唯一详细条目；
2. 确认型号、固件、提交或哈希与当前分析对象一致；
3. 沿条目中的关联决策进入决策文件；
4. 只有最低验收通过，才能宣称 VnaPro 已实现该决策。

### 3.3 新增证据

新增来源、观察、决策或缺口时，必须在职责对应的子文件中登记。入口文件只新增导航类别，不复制详细事实。具体模板见[新证据与决策登记模板](./架构依据/04-决策与验收映射.md#新证据与决策登记模板)。

## 4. 查证前检查

- 来源是否有稳定版本、固定提交或内容哈希；
- 结论是否只覆盖来源真正可观察的范围；
- 推断是否同时列出不能证明的边界；
- 产品差异是否进入显式产品兼容配置（`Profile`），而不是匿名写成“通常如此”；
- 待采集交互记录（transcript）是否仍保持待补证（`Pending`）；
- 兼容门禁是否在证据完成前保持待解禁；
- 架构决策是否有可自动执行或可重复复核的最低验收。
