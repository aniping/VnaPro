# 模拟设备采集验收

日期：2026-10-10。本次以 NativeSimulator 动态库作为被测设备，通过实际设备适配、Core、仪器服务及 TCP/HTTP 验收采集链路；门控设备只用于制造可重复的阻塞和故障时序。

下面保留各阶段真实完成的验证记录。采集功能验收、此前文件拆分验证与本次规范整改是不同源码快照，历史通过不能直接代替最新版本的全量复验。

## 结果与证据

Windows MinGW/GCC 10.3 的 **12/12 CTest 通过**，最终复验耗时 13.18 秒。WSL Ubuntu/GCC 13.3 对全部 C++ 生产库、动态库和测试目标启用 ThreadSanitizer 后，**12/12 CTest 通过**，最终复验耗时 10.34 秒，未报告数据竞争。两轮最终复验均故意从 `noise` 模式和最大 uint64 种子的终端启动，确认固定值测试不受外部噪声环境污染；噪声脚本仍自行指定种子。

另外在 ThreadSanitizer 下连续运行核心并发验收 20 轮，全部通过，耗时 9.05 秒。这是有界重复压力验证，不称为长时间稳定性测试。

Core 并发测试共 11 组，原生单元 18 组、动态合同 22 组、服务/SCPI 13 组、Web API 8 组。上述数字是场景数，12 项 CTest 是测试程序/脚本数。

golden 来自 [golden_iq_vectors.h](../VnaNativeSimulator/tests/golden_iq_vectors.h) 的固定数值，运行时不调用生产模型计算期望。独立黄金向量使用 tests/golden_test.yml 的历史 1 Hz–1 GHz 能力，服务端 golden 验收采用 Start=Stop=1 GHz、两点扫描；生产默认支持与扫描范围为 10 MHz–8 GHz，由 instrument_configuration_integration 直接启动默认 YAML 验证；不同频点及高字完整数值由 Core/DLL 验收覆盖。

检查了测试的失败敏感性：旧固定 DLL 运行噪声贯通测试时明确因“采集间数据未变化”失败，噪声实现后通过。另在测试进程内临时扰动最后一个源的 B4.imag 基准，SCPI 和 HTTP 各自准确在对应分量失败，仓库 golden 文件未改变。复核发现并修复服务/SCPI 测试继承噪声环境、将合法噪声当作固定数值错误的问题，实际先复现失败，再隔离环境并复验通过。

## 复验

在根目录按 [README](../README.md) 构建前端和服务后执行：

```powershell
cmake --build build --parallel
cmake -E chdir build ctest --output-on-failure
```

仅运行采集、四参数与配置的重点验收：

```powershell
cmake -E chdir build ctest -R "^(core_|golden_iq_|noise_iq_|service_scpi|web_api|measurement_processing|service_measurement|sparameter_integration|instrument_|server_config|logging_integration)" --output-on-failure
```

噪声用例主动指定模式与种子；固定数值用例主动指定 golden 模式。无需为了跑测试改变服务环境。网络测试启动独立进程并选择空闲端口，不接管正在使用的仪器面板。Python 进程终止只用于清理，关闭屏障与 join 的正确性由受控生命周期测试断言。

Linux/WSL 下全目标 ThreadSanitizer 复验使用独立目录。只设置 `VNA_SIM_ENABLE_TSAN` 会覆盖模拟器目标；以下全局编译/链接参数同时覆盖 Core、Service、Server：

```bash
cmake -S . -B build-tsan -G Ninja -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS="-fsanitize=thread -fno-omit-frame-pointer -g" \
  -DCMAKE_EXE_LINKER_FLAGS=-fsanitize=thread \
  -DCMAKE_SHARED_LINKER_FLAGS=-fsanitize=thread
cmake --build build-tsan --parallel 4
ctest --test-dir build-tsan --output-on-failure
```

本机 WSL 首次运行出现 `ThreadSanitizer: unexpected memory mapping`，测试尚未开始。使用 `setarch x86_64 -R ctest --test-dir build-tsan --output-on-failure` 仅关闭这些测试进程的 ASLR 后通过，不更改系统全局设置。这里的通过结论限定本次受控场景与并发压力，不能推导任意线程交错都已穷尽。

## 按职责组织与异常安全整改验证

本阶段移除 Core、Service、SCPI 和 Web 的 PImpl/转发层。独立行为类保留各自文件，简单结构体和枚举按职责收拢：公共核心控制值位于 core_types.h，内部命令与 Kind 位于 core_command.h，配置/ConfigPatch/触发与扫描枚举位于 instrument_settings.h，服务任务与 Kind/Stage 位于 service_task.h。SCPI 消息、HTTP 会话/操作及连接记录归所属类，共享 HTTP 值位于 http_types.h；不再要求每个数据类型独立一文件。

完成此职责收拢时，Core/Service 及 test_support 使用 Windows MinGW/GCC 10.3 重编译通过，`core_concurrency` 和 `core_native_integration` 两项局部 CTest 通过（0.61 秒）；实际 clang-format 18.1.8 检查通过。随后行为修复后的正式代码已通过 Windows 全量 **12/12 CTest（13.87 秒）**、WSL 全目标 ThreadSanitizer **12/12 CTest（9.98 秒）**。70 个正式头分别按 C++14 单独编译通过，头文件循环依赖为 0；127 个正式 C++ 头/源具有指定版权头，正式头均有宏保护。上述结果对应命名空间统一前的快照，统一后的 Windows/ThreadSanitizer 终检另行补记。

命名空间统一后的最终快照再次完整构建，Windows/GCC 10.3 **12/12 CTest（14.26 秒）**、WSL/GCC 13.3 全目标 ThreadSanitizer **12/12 CTest（10.22 秒）** 通过，未报告数据竞争。同步了单元测试的内部符号可见性，两个工具链构建没有编译告警；70 个头独立编译和包含循环检查再次通过，实际 clang-format 18.1.8 检查与 `git diff --check` 通过。该验收针对本项目模拟驱动，不替代真实硬件、macOS 或既定 GCC 7.3 的发布验证。

HttpApi 异常安全使用仓外实际 C++ probe 验证，链接正式 HttpApi 与现有 ControlledDevice/Fixture，不增加生产测试钩子。临时程序静态链接 MinGW 标准库，替换 C++ new/new[]，仅在主线程调用期间开启 thread_local 的第 N 次分配故障；每轮只抛一次 bad_alloc 后恢复，工作线程不受注入影响。先记录基线分配数，再为每个分配位置创建全新 Fixture 逐点注入。

| 实际路径 | 注入位置 | 公开行为断言 |
| --- | --- | --- |
| Claim | 15 个分配点 | 失败后没有未知 token 占权，正常重试可取得控制权；成功 token 完整为 `web-` 加 32 个字符，返回身份与持权身份一致 |
| Single Write | 37 个分配点，其中 3 个在服务已接受之后 | 同 requestId 重试返回同一操作身份，FIFO 仍只有一项，最终只增加一次 run 和一帧 |
| 已失败操作的结果 Poll | 5 个分配点，含非 SSO 错误字符串复制 | 故障后仍能恢复完整失败结果；完成后 59 秒可查询，61 秒已过期，不提前提交完成时间 |

首次注入额外检出 token 的 ostringstream 吞掉分配失败并返回截断字符串。启用 badbit/failbit exceptions 后复跑，完整 token 检查通过。为确认断言有检测能力，只在临时目录恢复三种旧的危险提交顺序，同一 probe 分别检出“失败 Claim 遗留未知控制权”“已接受写请求重试被拒”和“失败 Poll 丢失记录或提前过期”；正式实现通过，三份负对照按预期失败。

该验证覆盖上述路径的单次主线程 C++ 分配失败，不覆盖 malloc、操作系统/随机源失败、设备线程分配、持续或多点 OOM，也未逐分配点遍历全部配置/测量路由。首个失败响应没有返回操作 ID 时，验证恢复后的两次重试 ID 一致及仅一轮实际动作；原 ID 曾成功返回时直接比较原 ID。

本机临时报告为 `C:/Users/Administrator/.codex/tmp/vnapro-http-fault-probe-20261010/RESULTS.md`，同目录保留 probe 源、已验证 HttpApi 快照、三份负对照与构建产物。该临时程序按验证时的命名空间编译，后续重新编译需要同步源码 alias；已有可执行程序保留此次证据。

## 2026-10-11：Autoscale 后刻度固定

用户报告并提供截图：Continuous 中点击 Autoscale 后，每格刻度从 0.01 dB 变成 0.02 dB，Ref 和纵轴标签也变化。实际生产页面复现相同行为；原因是将刻度保存为 `null`，绘图在每个新帧上重新拟合，而 Scale 输入仍保留首次结果。

现改为一次性显示操作：工具栏与 Scale 面板共用动作，按点击时当前迹线的显示数据计算并保存具体范围。后续帧不重算，每条迹线独立；再次点击才重新适配。无有限显示值或无法表示的缩放范围不会覆盖原刻度；微小范围继续显示相对 Ref 的 `Δ` 刻度。

新增工作区动作与实际绘图读取联测。原行为在连续帧固定范围断言上失败，整改后通过；另覆盖再次适配、迹线隔离、手动刻度、格式切换、无有效数据、实虚部共同范围及极大值的无效拟合。WebUI **33 项测试**、类型检查和生产构建通过。

Chromium 从 `http://127.0.0.1:8191/` 加载生产构建，使用原有 seed 42 噪声服务。工具栏 Autoscale 后，帧序号 **39863→44718**，11 条纵轴标签、**0.01 dB/div、Ref −13.94 dB** 均固定，Per Div 的未应用草稿 0.025 也未被轮询覆盖；Scale 面板再次点击才将 Ref 调整到 −13.93 dB，并在帧 **44737→48495** 期间保持图内刻度一致。随后对 RAW 迹线适配不影响 S11 已保存的刻度，浏览器无 warning/error。仪器 run=5、revision=5 保持不变。

TSAN 的记录是一次全量运行与一次失败项修正后的定向复验，不记为单次 22/22 全量通过。修正只匹配 YAML 已返回的诊断类别，没有放宽非法 Unicode 输入的拒绝规则；没有竞争报告也不表示已穷尽所有线程交错。

Smith 的 Γ 来自未校准反射参数，`z` 为无量纲归一化阻抗；当前没有物理参考阻抗 Z0，不输出 Ω。本轮结果证明软件比值、完整帧一致性、显示与配置合同，校准和真实板卡射频准确度仍属于后续工作。处理结构、活动图和命令合同见[未校准 S 参数测量设计](未校准S参数测量设计.md)。
