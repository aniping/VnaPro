# WebSocket 实时帧推送设计

日期：2026-10-14。状态：待实现。本次用户选择先完成全点保真与定位日志，保留当前 HTTP 轮询，不新增 WebSocket 运行入口。

## 数据与分层边界

WebSocket 负责传输，不能替代后端仪器状态，也不会自动解决采样丢失、序列化耗时或绘图耗时。当前 HTTP 完整帧和无损数组编码作为第一阶段基础；后续传输共用同一快照与字段定义。

```text
采集核心的不可变完整帧
       ↓
仪器服务快照 + C++ 显示域的格式、刻度、标记与图窗状态
       ↓
统一显示帧编码
       ├─ HTTP 完整帧读取（当前）
       └─ WebSocket 订阅与会话（后续）
                     ↓
              WebUI 解码、校验和绘制
```

- 驱动、采集核心、测量和显示域不感知 WebSocket 会话，不由浏览器保存正式仪器状态。
- 订阅初期只推送状态和显示帧；控制命令继续使用已有 HTTP 事务、控制租约、版本比较和操作结果读取。SCPI 与 HTTP 共享同一 C++ 状态。
- 相同编码结果可供同一快照的多个观察窗口复用，编码和发送不持有驱动或显示状态锁。
- 交互预览与图窗像素几何仍属于瞬时绘制，不作为仪器配置保存。

## 完整性与一致性

每个逻辑消息包含完整选中集合的全部原始频点，不均匀抽点、不降为 float32、不在浏览器重新计算仪器格式。

| 字段 | 用途 |
| --- | --- |
| 协议版本、消息类型、会话编号、消息编号 | 协议协商与单连接顺序检查 |
| `channelId`、`runId`、`frameSeq` | 标识具体完整采集帧 |
| 采集、测量、显示及校准版本 | 避免旧数据套用新格式、标题、刻度或校准状态 |
| 原始点数、迹线数量、完整频轴及采样索引 | 明确原始分辨率和对应关系 |
| 各迹线 IQ、后端投影、有效性与特殊数值状态 | 保留实际值与无效点语义 |

64 位身份继续按十进制字符串或明确的 uint64 二进制字段传输，不能经过 JavaScript number 转换。

同一逻辑消息从一次服务快照和一个不可变 FramePtr 构造；不能把多次 HTTP 请求或多次采集拼成一帧。消息若分片，先验证身份、分片次序、总长度及总点数，完整接收后再替换页面正式帧。

显示版本变化也需要触发推送：HOLD 下修改 Scale、Format 或 Marker，即使 `frameSeq` 不变，仍产生新投影。订阅去重依据上述版本组合，不能只比较 `frameSeq`。

## 背压与资源边界

显示会话最多保留一条正在发送的完整消息和一个待发送的最新快照。慢客户端可以跳过尚未开始发送的旧完整帧，必须记录跳帧数量；不能删掉一帧中的频点，也不能拼接新旧迹线。

采集不等待某个浏览器。连续显示跳过旧帧不等于丢弃采集数据，历史记录和完整导出使用独立的保真读取或存储路径。

发送采用有界分片和每轮工作预算；长时间无进展时断开该会话，其余 HTTP、SCPI 和观察者继续工作。连接数、消息长度、采样数量、未完成分片和重连频率均须在解码或分配前检查。

浏览器传统 WebSocket API 没有自动接收背压。应用需限制待解码消息数量并报告过载，必要时显式请求降低完整帧推送频率；降低刷新频率不能改变每帧采样分辨率。[MDN WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket)

## 连接生命周期

订阅端点和子协议在实施时定稿。采用标准 Upgrade、文本/二进制消息、Ping/Pong、关闭握手和合法分片；不把当前 HTTP 自定义数组编码当作 WebSocket 协议本身。[RFC 6455](https://datatracker.ietf.org/doc/html/rfc6455)

- 建立连接后先发送权威状态与一个完整帧，完成版本校验后再进入更新流。
- 断线后显示最后完整帧及失联状态，按有上限的退避重连；重连重新读取状态和完整帧，不自动重放控制写入。
- 会话退出释放快照和发送资源，不停止仪器扫描、不更改活动迹线、不释放其他控制客户端的租约。
- 不支持 WebSocket 或连接失败时保留 HTTP 完整帧读取；切换路径不重置测量、显示状态或运行轮次。

## 当前已实现的定位方式

配置 `log.level: DEBUG` 开启后端帧阶段日志；需要立即查看文件时可设置 `log.flush.level: DEBUG`，继续受既有滚动文件上限约束。默认 INFO 不输出逐帧诊断。

| 记录 | 字段与解释 |
| --- | --- |
| `frame_build` | 连接编号、`frameSeq/runId/displayRevision`、点数、迹线数、快照构造与投影/打包耗时 `buildUs` |
| `frame_encode` | 相同连接/帧号、响应字节、实际编码 CPU 耗时 `encodeCpuUs` 与含调度间隔的 `encodeWallUs` |
| `frame_send` | 相同连接/帧版本、字节数、发送耗时 `sendUs`、WouldBlock 次数 `writeBlocked` |
| `frame_send_timeout` / `frame_send_failed` | 已发送/总字节、帧号、超时或套接字错误；不把未完成发送记为成功 |
| `http_encode_failed` | 连接/帧号与编码失败原因 |

连接编号仅在本进程内关联请求；`sendUs` 表示字节交给操作系统的时间，不代表浏览器已经显示。无实际帧、请求解析失败和错误 HTTP 响应使用原有 HTTP 状态日志，不伪造帧构造耗时。

访问 `/?debug=frames` 开启浏览器诊断：记录帧版本、字节数、接收、JSON 解析和解码校验耗时。默认关闭，超时、主动取消、协议错误分别分类，不重发已受理写入。

日志不输出整帧 IQ、Base64 数据、控制令牌或请求正文。需要复查数值时使用完整数据读取，避免日志体积与磁盘写入干扰采集。

## 后续 WebSocket 定位与验收

增加连接建立/重连/关闭原因、消息编号、完整帧跳过数量、发送队列占用、Ping/Pong 延迟，以及客户端解码、绘图提交和版本丢弃原因。日志按会话及消息编号关联；常规统计应限频，完整逐消息记录仅在 DEBUG 下启用。

实施必须覆盖：

1. 4000、10001 点的全部迹线保真，窄峰、坏点和特殊数值不消失；与同一冻结帧的 HTTP/SCPI 对照。
2. 连续扫描与 HOLD 显示设置更新，多观察窗口和重新打开页面的一致性。
3. 慢读者、断网、重连、消息分片或丢弃、不完整消息、版本竞争，不能阻塞采集或拼接半帧。
4. 原始点数、传输点数、绘制点数分别可观测；发送成功与绘图完成不能混为同一指标。
5. Debug 开关、滚动文件、消息关联、发送背压和取消分类均有自动化验收，日志不泄漏控制令牌或采样数组。
