# VNB 四端口软件联调

本流程用于独立 `vna_server.exe` 和 VN10 模拟采集驱动，不代表真实硬件带宽、校准溯源或测量精度。四端口 TOSM 的标准采集与联合求解见[校准接入与使用](校准接入与使用.md)。

## 启动与诊断夹具

先构建 `cmake --build cmake-build-debug --target vna_server -j 6`，把 `release` 复制到独立部署目录，将 [vnb-software-40ghz.yml](../config/vnb-software-40ghz.yml) 复制为该目录的 `vnapro.yml`，再无参数启动其中的 `vna_server.exe`。程序只读取自身目录配置。该配置明确使用 simulator：P1～P4、10 MHz～40 GHz、800 点、1 kHz、0 dBm，启动 HOLD；默认发布配置仍为 8 GHz。CableTest 的 TDR 分析重采样到 10 MHz 网格，因此这里从 10 MHz 起扫，供其补 DC 后连续成网格；原始采样间隔不等于分析网格间隔，TDR 前置校验由 CableTest 执行。

隔离部署位于 `reference/analysis/vnb-software-e2e-20261016/deployment`，SCPI 为 `127.0.0.1:55025`，HTTP 为 `http://127.0.0.1:58080`。这些端口与原默认 5025/8080 分开。

服务就绪且无其他控制者时，在仓库根目录执行：

```powershell
python scripts/vnb_simulation_calibration.py --http-url http://127.0.0.1:58080 --name SIMULATION_ONLY_FOUR_PORT_DIAGNOSTIC --output reference/analysis/vnb-software-e2e-20261016/deployment/simulation-calibration.json
```

脚本只允许真实回读为 `NativeSimulator` 的四口后台及当前 0 dBm 刺激，按实际能力校验频轴，不改能力。它通过正式 HTTP 完成 HOLD、一次真实采集、非单位诊断系数导入、选择、启用、同帧 16 项数值核对和服务导出，再清理临时测量定义并释放控制权。每格 tracking/offset 不同、match=0，独立期望为 `(M-offset)/tracking`。该文件是显式软件诊断夹具，不能冒充 OSM/THRU 物理标准求得的 TOSM 或自动用于硬件。

成功后用 `SENS1:CORR:CSET:ACT 'SIMULATION_ONLY_FOUR_PORT_DIAGNOSTIC',0;*OPC?` 激活，检查 `SYST:ERR?` 和 `SENS1:CORR?`。完整 16 参数使用 `CALC:DATA:MSD? '1,2,...,16'`，配合 `FORM REAL,64;:FORM:BORD SWAP`。序号按测量定义顺序，调用者需先建立对应的 S11～S44。

校准集冻结频轴、点数、IFBW、逐点功率和身份。改变刺激时应重新生成明确的软件夹具或导入匹配的实际校准文件，不能改变轴后继续套用旧集。`*RST` 保留池；默认 `server.calibrationStore: calibration` 使 Ch1 池和选择跨重启恢复，校正仍需显式激活。关闭持久化时需 Export/Import 或重新生成软件夹具。每通道最多 256 集、512 MiB，仪器合计 1 GiB；其他逻辑通道当前不自动持久化。不同路径可有不同实际系数和名称，不允许用多份名字冒充物理校准精度。

## HTTP 短连接超时定位与修复

原入口有时通过，额外记录每个请求也会改变复现时序。采用成功时只保留内存连接环、仅失败时采样的独立副本，在约 8.6 s 内捕获了真实 `socket.connect` 超时：失败 GET 的客户端源端口 7651，曾被此前四口大 POST 使用；间隔 16 条成功连接后，隐式分配又选回了同一 `127.0.0.1:7651 → 127.0.0.1:13733` 四元组。失败原 socket 尚未关闭时，客户端为 SYN_SENT、服务监听正常，同时反向四元组仍为 TIME_WAIT。不能再仅用 TIME_WAIT 总量或解释器版本推断原因。

最小实验不运行 VNB：TCP 服务完整读取 1 MiB 后回复并主动关闭，客户端读到 EOF，再将新 socket 普通绑定到同一源端口。3/3 在真实 connect 阶段超时约 5 s，应用层只接到第一条连接；仅换新源端口或仅把数据改为 1 KiB，控制组均成功。结合真实调用记录，确认失败机制为旧四元组尚受服务端 TIME_WAIT 保护时被客户端重新选用；无需校准解析、保存或服务执行器阻塞即可重现。未抓取 TCP 序号/时间戳，不能把具体内核 SYN 判定宣称为已测事实。[TCP TIME_WAIT 规范](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6)

已否决两种端口绑定方案：显式 `bind(0)` 的候选仍在原完整 CTest 第 131 次导入后的 GET connect 超时，`SO_EXCLUSIVEADDRUSE` 最小实验也仍超时。绑定只保证 socket 存活期间的资源，不能保证被动关闭后的旧四元组不再被选中，不能把窄化测试通过当成修复成立。[Winsock bind 文档](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-bind)

最终修复让服务端支持显式 `Connection: keep-alive` 的串行请求，完整发送响应后保留同一个 TCP socket，并重建全部请求状态；正文、头、控制令牌、编码器及计时不继承。无显式保留请求及 `Connection: close` 仍关闭；`close` 优先。framing、超限及编码错误关闭连接；HEAD 保持关闭边界，不扩展其既有响应支持。仍最多 8 个连接，下一请求或空闲等待沿用 10 s 接收期限，写进展期限不变。暂不支持 pipelining，同批多消息拒绝，响应期间可见的提前字节也会导致关闭。[HTTP 持久连接规范](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3)

共享测试 `HttpClient` 每实例持有一条连接，完整读取响应后复用；异常时关闭并直接抛出，不自动重发。并发读取使用独立实例，结束后调用 `close()`。HTTP 请求超时仍为 5 s，持久化轮询仍为 50 ms，未新增传输重试、sleep 或系统 TCP 调整；原有 429 操作历史背压等待保持原预算。

新增跨平台 `http_client_connection` CTest 用真实 HTTP/1.1 peer 验证 1 MiB POST、大响应、API 错误后 GET 只发生一次 accept，并验证丢失写响应不会重发。旧 helper 明确失败（四次请求建立四条连接），新 helper 通过。真实旧 VNB 也因不保留连接被新增回归检出；新服务覆盖同 socket 的 API/静态文件/JSON 切换、令牌隔离、坏 framing 与超限关闭及显式关闭优先。
