# 硬件适配层原型说明

## 当前范围

本原型实现《硬件适配层软件设计》的第一阶段可验证闭环：

- `VnaDriverSdk`：可由 C99 与 C++17 包含的 V1 C ABI；
- `VnaHardware`：插件加载、设备发现、计划验证、异步状态机、缓冲池和事件分发；
- `VnaDriverSimulator`：以真实 MODULE 形式加载的四端口开路模拟驱动；
- `VnaLogger`：从 `vnapro.conf` 读取级别与轮转策略的线程安全循环文件日志；
- ABI 布局、计划验证以及发现、连接、准备、流式扫描、重复启动、中止和断开测试。

当前版本明确只交付 Simulator。公司 VNA 和商用 VNA 驱动不属于本版开发与验收范围；
两者未来立项时仍需设备协议、厂商 SDK、波量归一化定义和目标部署工具链，不能用
占位实现冒充可联调驱动。

## 构建与测试

现代编译器测试链：

```bash
cmake -S . -B build/test -DCMAKE_BUILD_TYPE=Debug -DVNA_BUILD_TESTS=ON
cmake --build build/test --parallel
ctest --test-dir build/test --output-on-failure
```

模拟驱动输出到 `build/test/drivers`，集成测试从该绝对目录加载插件。配置阶段会从仓库内
校验和固定的归档恢复 GoogleTest，不需要在线下载。

macOS 内存与未定义行为门禁使用独立的 Homebrew LLVM 22.1.8，避免旧 Apple Clang 17 ASan
运行库在 macOS 26 初始化阶段的自身死锁：

```bash
brew install llvm
cmake -S . -B build/llvm-asan -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_C_COMPILER=/opt/homebrew/opt/llvm/bin/clang \
  -DCMAKE_CXX_COMPILER=/opt/homebrew/opt/llvm/bin/clang++ \
  -DCMAKE_CXX_FLAGS='-fsanitize=address,undefined -fno-omit-frame-pointer' \
  -DCMAKE_EXE_LINKER_FLAGS='-fsanitize=address,undefined' \
  -DCMAKE_MODULE_LINKER_FLAGS='-fsanitize=address,undefined' \
  -DVNA_BUILD_TESTS=ON
cmake --build build/llvm-asan --parallel
ASAN_OPTIONS=detect_leaks=1:halt_on_error=1:abort_on_error=1 \
UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1 \
  ctest --test-dir build/llvm-asan --output-on-failure
```

当前全量证据为：现代编译器 Debug 104/104、独立 UBSan 104/104，以及 LLVM 22.1.8
ASan + LSan（LeakSanitizer）+ UBSan 104/104，后者三类 sanitizer 均无报告。旧运行库故障不再构成覆盖缺口，
也不改变生产 GCC 7.3.0 工具链约束。

生产工具链门禁：

```bash
cmake -S . -B build/production \
  -DVNA_BUILD_TESTS=OFF \
  -DVNA_ENFORCE_PRODUCTION_TOOLCHAIN=ON
cmake --build build/production --parallel
```

门禁只接受 GCC 7.3.0。本机可使用已有镜像执行 Linux/amd64 生产编译，源目录以只读方式
挂载，构建产物只写入容器临时目录：

```bash
docker run --rm --platform linux/amd64 --cpus 1 \
  -v "$PWD":/src:ro -w /src \
  vna-gcc73-toolchain:7.3.0 sh -lc \
  'cmake -S /src -B /tmp/vnapro-production -G "Unix Makefiles" \
    -DCMAKE_BUILD_TYPE=Release \
    -DVNA_BUILD_TESTS=OFF \
    -DVNA_ENFORCE_PRODUCTION_TOOLCHAIN=ON && \
   cmake --build /tmp/vnapro-production --parallel 1'
```

该命令已在 GCC 7.3.0 下完成全量生产目标编译。它证明当前代码可被约定编译器接受，
但不能替代最终部署系统的 target triple、libstdc++、系统运行库和真机运行验证。本机通过
QEMU 运行 amd64 镜像时采用单 CPU、串行 Make 构建，降低仿真环境自身并发崩溃对门禁的干扰。

## 可维护性约束

- 代码格式门禁固定使用 clang-format 22.1.8，版本由仓库根目录的 `.clang-format-version` 声明。
- 复杂协议流程按输入校验、资源获取、状态转换和结果发布拆分；单个函数只负责一个失败边界。
- 中文注释解释 ABI 视图寿命、缓冲区所有权、线程同步和失败关闭原因，不逐行复述代码。
- 文件行数按项目约定不计注释；同时仍运行规范工具的物理行检查，避免空行或注释掩盖过大的文件。
- 命令和事件分派保留显式穷举 `switch`。这两个函数的分支数来自协议种类，改成间接表或多态层
  只会隐藏完整性检查，不会减少实际状态空间。

## 循环日志配置

管理器默认读取驱动目录下的 `vnapro.conf`；配置文件位于其他目录时，使用
`VnaHardwareManager::create(driverDirectory, configurationFile)` 显式传入。仓库提供
[`config/vnapro.conf`](../config/vnapro.conf) 作为生产配置样例：

```ini
[logging]
file=logs/vnapro-{pid}.log
level=info
flush_level=warning
max_file_bytes=10485760
max_files=5
```

- 相对日志路径以配置文件所在目录为基准，`{pid}` 会替换为进程号，避免多个进程争用同一文件。
- 活动日志使用 `file` 指定的名称，达到 `max_file_bytes` 后在扩展名前插入序号，例如
  `vnapro-1234.log` 依次轮转为 `vnapro-1234.1.log`、`vnapro-1234.2.log`，最多保留
  `max_files` 个历史文件。
- `level` 和 `flush_level` 接受 `trace`、`debug`、`info`、`warning`、`error`、`critical`
  和 `off`。达到刷盘级别的记录会立即落盘，其他记录在后端刷新或关闭时落盘。
- 配置文件必须是当前用户或 root 拥有、不可被组或其他用户写入的普通文件，且不得超过 64 KiB；
  缺少字段、未知字段或非法数值都会使管理器创建失败，避免静默退化为无日志运行。
- 宿主记录插件装载、发现、设备打开、状态迁移、配置代次、扫描终态、回调异常和背压故障；驱动
  通过 `HostServices::Log` 写入同一后端。按照实时性约束，不记录逐点和逐波数据。
- 每次创建管理器只读取一次受信配置快照，并从该快照同时解析日志和硬件资源段，避免配置文件
  原子替换时组合两个代次。资源限制属于各管理器；日志后端在进程内共享，因此并存管理器的
  `[logging]` 必须等价。修改配置只影响之后创建的管理器。

## 硬件资源配置

同一受信配置文件必须提供完整的 `[hardware_resources]` 段。生产样例采用以下保守基线：

```ini
[hardware_resources]
wave_pool_slot_count=2
maximum_wave_pool_payload_bytes=67108864
maximum_requested_plan_payload_bytes=16777216
maximum_prepared_sweep_payload_bytes=33554432
maximum_pending_commands_per_device=8
maximum_pending_prepare_payload_bytes_per_device=33554432
```

- 波池按有效布局最大波数、`waveBlockPointCapacity`、槽位数和复数/质量载荷执行 checked 计算；
  超过 64 MiB 时 Prepare 在建池前失败关闭。
- requested plan 的 16 MiB 上限同时用于调用准入；prepared snapshot 的 32 MiB 上限覆盖有效计划、
  layouts、warnings 及相关字符串。宿主持有的 `vector`/`string` `capacity()` 会计入预算，避免只看
  `size()` 而低估常驻分配。
- 每设备最多保留 8 条已接纳且尚未处理完成的外部命令；普通命令只使用前 7 个名额，最后 1 个
  专供 Abort/Disconnect。所有 pending Prepare 的请求载荷合计不超过 32 MiB。
- 已排队和正在回调的 Prepare 快照共用 32 MiB 滞留预算。当前活动配置最多再持有一代；插件返回
  到宿主转换的瞬时对象、allocator 开销及调用方延长的旧快照不属于该逻辑预算，仍需用峰值 RSS
  基准验证。
- 资源字段缺失、未知、非十进制、溢出或关系非法都会使 Manager 创建失败。当前值不是永久产品
  常量，应依据真机吞吐、RSS 和 P99 等待时间调整。

## 原型契约

- 驱动目录必须能规范化为绝对目录；加载器只枚举该目录第一层中名为
  `VnaDriver*.so` 或 `VnaDriver*.dylib` 的普通文件。目录和文件必须由当前用户或 root
  拥有且不能被组或其他用户写入；加载器通过目录描述符以 `O_NOFOLLOW` 打开候选，再从
  同一文件描述符加载，不跟随候选符号链接，也不在校验后重新按原路径打开。
- 扫描计划中的同一 `ExcitationId` 必须始终使用同一波布局。
- ABI 当前只接受精确 `1.0`；顶层函数表和 View 校验 `structSize`，不带该字段的
  叶子结构在 V1 冻结，不宣称尚未实现的次版本兼容。
- ABI 1.0 的所有 `reserved`/`reservedFlags` 必须为零；未知枚举、能力位、
  执行位和质量标志位失败关闭，不做默认映射或透传。
- 当前 ABI 准备结果尚未携带量化后的实际点表，因此原型对驱动报告的 `quantized` 结果
  一律失败关闭；补齐实际 `effectivePlan` 往返契约后才能启用允许量化策略。
- 驱动若声明支持中止，则 `RequestAbort` 回调必须存在，否则连接阶段按协议错误拒绝。
- 每台设备只允许一个事件订阅者。原因是 `VnaWaveBlock` 使用唯一所有权移动交付；在没有
  决定共享只读所有权或复制策略前，多订阅者广播会破坏该契约。
- 五个异步控制 API 返回 `Result<CommandId>`。成功只表示命令已通过固定环和 payload 预算准入；
  同步失败不分配 CommandId，也不产生终态事件。已准入命令才满足恰好一个成功或失败终态。
- `abortAsync()` 只有在目标扫描先发布 `SweepCompletion(Aborted)` 后才发布
  `AbortCompletedEvent`；具体故障优先并使中止命令失败。成功断开在进入
  `Disconnected` 后发布 `DisconnectCompletedEvent`。
- `RequestAbort` 与 `Execute` 收尾必须线性化；Start/Execute 交接前或收尾已发生时
  均可返回 `InvalidState`，宿主等待 Worker 终态区分。请求返回 OK 后，无更具体
  故障时 `Execute` 返回 `Cancelled`。宿主只以实际
  Worker/数据通路结果判定终因，不以“曾接受请求”直接推导 `Aborted`。
- 单生产者在中止被接受前已准入的普通 Commit 最多允许再完成一个块；下一批在等待/Acquire 前
  观察取消。全扫描最终 Commit 则先在 `sweepMutex_` 内关闭中止准入，再于锁外调用 Host API；
  因此 Abort 与最终 Commit 二者只有一个成功，不会把完整覆盖事后改判为 `Aborted`。
- 事件只交付给入队时有效的订阅代次；没有订阅者时事件会被丢弃，因此调用方必须先订阅
  再发命令。控制事件在固定环上等待容量，保证不因队列短暂饱和而丢失；波块按 250 ms
  背压上限失败关闭为 `DataLoss`，缓冲池槽位耗尽采用相同终态。关闭会先关闭事件队列，
  再等待设备线程，解除等待而不死锁。
- Hardware 的 `FrameTracker` 在准备阶段按布局预编译合法覆盖集，是块覆盖和扫描完整性的
  权威校验者。未知布局、越界、跨布局空洞、重复、重叠或乱序块会按协议错误拒绝；
  只有无缺口覆盖全部合法帧才能报告 `Completed`。
- `VnaAcquisition` 越过公开 `IVnaHardware` 边界时仅保留 `O(L)` 防御状态：一个全局下一
  `sequence` 和每个 layout 的下一预期点偏移。它在复制前拒绝断序、重放、重叠和乱序，
  但不复制 `FrameTracker` 的覆盖 bitmap，也不增加波块队列。`L` 是当前 prepared layout 数。
- 驱动提交后失去写权限，调用者销毁波块时槽位自动归还。
- 同一配置重复 Start 时只重置准备阶段的覆盖表并复用固定波池；不可变 `PreparedSweep` 通过
  `shared_ptr<const ...>` 在会话、事件和采集层之间共享，不按 Sweep 深拷贝或重建资源。
- 宿主 `ExecutionReport::waveBlockPointCapacity` 承接 ABI 1.0 准备结果的
  `preferredBatchPoints`；为保持 ABI 兼容，C ABI 与 `VnaCapabilities` 字段仍保留原名。
- 每个波的跨距使用本次 Acquire 返回的 `pointCapacity`，尾部短批不得使用池的
  最大容量解析。Commit 前检查质量位，ABI 1.0 未知位以 `ProtocolError` 拒绝。
- `VnaWaveBlock::copyWaveTo()` 以指针和元素数接收两个借用目标，先校验空指针、波索引
  和点数，再按 Acquire 容量跨距逐项转为 `std::complex<double>` 并复制质量位。
- 模拟器批次大小固定为 2 个点。每批在 Acquire 前按批内实际记录累计
  `ceil(1e9 / IFBW_Hz)` ns；不同激励顺序计时，同一激励的多源和 required waves 同时采集，
  不重复计时，点级 dwell 只在该点最先执行的布局计一次。
- 计时采用 `steady_clock` 累计绝对截止时间；数据处理落后时不再追加睡眠，因此不会把调度和
  传输开销逐批叠加。驱动本地 Abort 通过条件变量立即唤醒，宿主取消在最长 10 ms 内轮询一次。
- `1/IFBW` 是模拟器的最低阶逻辑时间带宽模型，不是普适物理下限，也不宣称复现具体仪器的
  滤波器阶数、源/LO 切换和校准开销。10–30 kHz 对应每个“点 × 激励”100–33.334 us，
  不再附加固定批次节流。
- Prepare 会按同一公式预检整次逻辑时间并设置 1 小时硬上限，避免极大 dwell/窄 IFBW 长期占住
  设备 Worker；恰好 1 小时合法，多 1 ns 即失败关闭。
- 模拟器只声明并接受内部触发，声明逐点 IFBW 和逐点功率，不声明逐点驻留时序能力。
- 模拟器波值是无量纲测试模型，不代表工厂归一化：源入射幅度为 `10^(powerDbm/20)`；内建 DUT
  是四个彼此独立、带短参考面延迟、微损耗和频率纹波的开路端口，同端口反射接近 1，跨端口
  有约 -100 dB 的有限隔离泄漏。
- 每个原始 `a/b` 接收通道按
  `measured = nominal * (1 + relativeNoise) + additiveNoise` 生成结果。每个通道都有独立的
  复高斯白噪声 `additiveNoise`；只有 `nominal` 非零时，乘性 `relativeNoise` 才会形成高电平
  残余 trace noise 贡献。两者的复 RMS 均按 `sqrt(IFBW)` 缩放。
- 噪声种子由 SweepId、PointId、ExcitationId 和波通道派生，因此同一样本可复现，但跨 Sweep、
  频点和通道持续变化。归一化复白噪声幅度密度为 `3.1623e-8 / sqrt(Hz)`，即 10 kHz 下
  复 RMS 约 `3.1623e-6`（相对单位波幅约 -110 dB）。10 kHz 下开路 `b/a` 幅度 trace noise
  目标为 0.001 dB RMS。该量级只用于物理合理的仿真，不是仪器校准指标。

## 本机目标吞吐基准

[本机目标吞吐基准](../benchmarks/LocalThroughputBenchmark.cpp) 在 `09c7de8` 中落地。Apple M1 / 16 GB、
Release 下以 10,000 点、每点 4 个顺序激励、每激励 4 波的 3,200,000 B 有效帧载荷测量：

- 10 kHz 和 30 kHz IFBW 的 P95 墙钟/逻辑时间均小于 `1.00013`，说明当前 `B=2` 本机
  Simulator 管线没有叠加固定批次节流。
- 10 MHz 只作为软件压力场景；管线 P95 有效载荷吞吐至少 42.358 MiB/s。
- 大块完整帧组装微基准的“分配 + 校验/复制 + 冻结”P95 有效载荷吞吐至少 13,054 MiB/s。

这些数字是特定本机、Simulator 和基准边界的回归基线，不是真机 IFBW 的普适物理极限，
也不能关闭最终部署镜像与真机的生产吞吐、CPU、RSS 和长稳门禁。

## 线程安全与生命周期

- 同一 `IVnaHardware` 的查询、订阅和异步命令可以由多个线程调用；命令在设备 Actor
  串行执行，同一设备的回调只在其事件线程串行发生，回调期间不持有设备内部状态锁。
- Host API 缓冲回调只允许在当前设备的 `Execute` 调用链内由单一生产者串行调用；
  `Execute` 返回前必须完成全部 Acquire/Commit/Discard，返回后不得继续提交数据。
- Acquire 成功后的句柄由一次 Commit 或 Discard 终结；Commit 正常返回即完成所有权交接，
  非 OK 状态只表示数据没有成功发布，驱动不得对同一句柄再次 Discard。
- `IVnaHardwareEventSink` 必须比其 `Subscription` 活得更久。销毁订阅会等待正在执行的
  回调结束；若在回调自身销毁订阅，则当前回调自然返回后不再产生后续调用。
- `IVnaDiscoverySink` 必须存活到对应的完成或失败回调。发现回调由管理器发现线程执行。
- `VnaHardwareManager::shutdown()` 必须与新的发现、打开以及所有会话 API 调用外部同步；
  shutdown 返回后不再使用管理器或既有会话。普通发现和打开调用由管理器内部加锁保护。

## 后续版本事项

1. 固定生产目标 OS、CPU、GCC target triple、libstdc++ 与系统运行库，并在最终部署镜像或
   真机上补充链接、加载和运行验证；Linux/amd64 容器内的 GCC 7.3.0 编译门禁已通过。
2. 定义公司硬件的 `a/b` 单位、参考平面、参考阻抗、接收机修正和工厂归一化格式，并把
   参考阻抗、归一化标识及必要的实际值旁路数据补进 ABI 与公开波块契约。
3. 给出最大端口数、最大点数、目标点速率、首批延迟、CPU 和内存预算。
4. 根据目标平台补齐并验证 Windows DLL 加载封装；当前加载器已在 POSIX `dlopen` 路径实现。
5. 若上层需要多个事件消费者，先确定波块广播的所有权模型，再扩展订阅接口。
6. 获得公司硬件协议以及选定商用仪器的厂商 SDK/协议后，实现并联调两类真实驱动。
