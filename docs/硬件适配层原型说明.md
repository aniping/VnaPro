# 硬件适配层原型说明

## 当前范围

本原型实现《硬件适配层软件设计》的第一阶段可验证闭环：

- `VnaDriverSdk`：可由 C99 与 C++17 包含的 V1 C ABI；
- `VnaHardware`：插件加载、设备发现、计划验证、异步状态机、缓冲池和事件分发；
- `VnaDriverSimulator`：以真实 MODULE 形式加载的确定性四端口模拟驱动；
- `VnaLogger`：从 `vnapro.conf` 读取级别与轮转策略的线程安全循环文件日志；
- ABI 布局、计划验证以及发现、连接、准备、流式扫描、重复启动、中止和断开测试。

公司 VNA 和商用 VNA 驱动尚未实现。两者需要设备协议、厂商 SDK、波量归一化定义和
目标部署工具链，不能用占位实现冒充可联调驱动。

## 构建与测试

现代编译器测试链：

```bash
cmake -S . -B build/test -DVNA_BUILD_TESTS=ON
cmake --build build/test --parallel
ctest --test-dir build/test --output-on-failure
```

模拟驱动输出到 `build/test/drivers`，集成测试从该绝对目录加载插件。配置阶段会从仓库内
校验和固定的归档恢复 GoogleTest，不需要在线下载。

生产工具链门禁：

```bash
cmake -S . -B build/production \
  -DVNA_BUILD_TESTS=OFF \
  -DVNA_ENFORCE_PRODUCTION_TOOLCHAIN=ON
cmake --build build/production --parallel
```

门禁只接受 GCC 7.3.0。本机可使用已有镜像执行 Linux/amd64 生产编译，源目录以只读方式
挂载，构建产物只写入容器临时目录：

```bash
docker run --rm --platform linux/amd64 \
  -v "$PWD":/src:ro -w /src \
  vna-gcc73-toolchain:7.3.0 sh -lc \
  'cmake -S /src -B /tmp/vnapro-production -G Ninja \
    -DCMAKE_BUILD_TYPE=Release \
    -DVNA_BUILD_TESTS=OFF \
    -DVNA_ENFORCE_PRODUCTION_TOOLCHAIN=ON && \
   cmake --build /tmp/vnapro-production --parallel 1'
```

该命令已在 GCC 7.3.0 下完成全量生产目标编译。它证明当前代码可被约定编译器接受，
但不能替代最终部署系统的 target triple、libstdc++、系统运行库和真机运行验证。本机通过
QEMU 运行 amd64 镜像时采用串行构建，避免老版本 `cc1plus` 在并行仿真压力下偶发崩溃。

## 可维护性约束

- 代码格式门禁固定使用 clang-format 22.1.8，版本由仓库根目录的 `.clang-format-version` 声明。
- 复杂协议流程按输入校验、资源获取、状态转换和结果发布拆分；单个函数只负责一个失败边界。
- 中文注释解释 ABI 视图寿命、缓冲区所有权、线程同步和失败关闭原因，不逐行复述代码。
- 文件行数按项目约定不计注释；同时仍运行规范工具的物理行检查，避免空行或注释掩盖过大的文件。
- 命令和事件分派保留显式穷举 `switch`。这两个函数的分支数来自协议种类，改成间接表或多态层
  只会隐藏完整性检查，不会减少实际状态空间。

## 循环日志配置

管理器默认读取驱动目录下的 `vnapro.conf`；配置文件位于其他目录时，使用
`VnaHardwareManager::create(driverDirectory, configurationFile)` 显式传入。仓库提供
[`config/vnapro.conf`](../config/vnapro.conf) 作为生产配置样例：

```ini
[logging]
file=logs/vnapro-{pid}.log
level=info
flush_level=warning
max_file_bytes=10485760
max_files=5
```

- 相对日志路径以配置文件所在目录为基准，`{pid}` 会替换为进程号，避免多个进程争用同一文件。
- 活动日志使用 `file` 指定的名称，达到 `max_file_bytes` 后在扩展名前插入序号，例如
  `vnapro-1234.log` 依次轮转为 `vnapro-1234.1.log`、`vnapro-1234.2.log`，最多保留
  `max_files` 个历史文件。
- `level` 和 `flush_level` 接受 `trace`、`debug`、`info`、`warning`、`error`、`critical`
  和 `off`。达到刷盘级别的记录会立即落盘，其他记录在后端刷新或关闭时落盘。
- 配置文件必须是当前用户或 root 拥有、不可被组或其他用户写入的普通文件，且不得超过 64 KiB；
  缺少字段、未知字段或非法数值都会使管理器创建失败，避免静默退化为无日志运行。
- 宿主记录插件装载、发现、设备打开、状态迁移、配置代次、扫描终态、回调异常和背压故障；驱动
  通过 `HostServices::Log` 写入同一后端。按照实时性约束，不记录逐点和逐波数据。
- 配置只在创建首个管理器时读取。进程内并存的管理器必须使用等价配置；修改文件后需销毁全部
  管理器并重新创建才会生效。

## 原型契约

- 驱动目录必须能规范化为绝对目录；加载器只枚举该目录第一层中名为
  `VnaDriver*.so` 或 `VnaDriver*.dylib` 的普通文件。目录和文件必须由当前用户或 root
  拥有且不能被组或其他用户写入；加载器通过目录描述符以 `O_NOFOLLOW` 打开候选，再从
  同一文件描述符加载，不跟随候选符号链接，也不在校验后重新按原路径打开。
- 扫描计划中的同一 `ExcitationId` 必须始终使用同一波布局。
- 当前 ABI 准备结果尚未携带量化后的实际点表，因此原型对驱动报告的 `quantized` 结果
  一律失败关闭；补齐实际 `effectivePlan` 往返契约后才能启用允许量化策略。
- 驱动若声明支持中止，则 `RequestAbort` 回调必须存在，否则连接阶段按协议错误拒绝。
- 每台设备只允许一个事件订阅者。原因是 `VnaWaveBlock` 使用唯一所有权移动交付；在没有
  决定共享只读所有权或复制策略前，多订阅者广播会破坏该契约。
- 事件只交付给入队时有效的订阅代次；没有订阅者时事件会被丢弃，因此调用方必须先订阅
  再发命令。控制事件在固定环上等待容量，保证不因队列短暂饱和而丢失；波块按 250 ms
  背压上限失败关闭为 `DataLoss`。关闭会先关闭事件队列，再等待设备线程，解除等待而不死锁。
- 波缓冲在准备阶段按布局预分配。驱动提交后失去写权限，调用者销毁波块时槽位自动归还。
- 模拟器批次大小固定为 2 个点，批次间加入 20 ms 延迟，以便确定性验证流式返回和中止。
- 模拟器波值是无量纲测试模型，不代表工厂归一化：源入射幅度为
  `10^(powerDbm/20)`；同端口反射系数为 0.1，跨端口耦合幅度为
  `0.5 / 端口距离`，每个端口距离加入 0.1 ns 延迟。

## 线程安全与生命周期

- 同一 `IVnaHardware` 的查询、订阅和异步命令可以由多个线程调用；命令在设备 Actor
  串行执行，同一设备的回调只在其事件线程串行发生，回调期间不持有设备内部状态锁。
- `IVnaHardwareEventSink` 必须比其 `Subscription` 活得更久。销毁订阅会等待正在执行的
  回调结束；若在回调自身销毁订阅，则当前回调自然返回后不再产生后续调用。
- `IVnaDiscoverySink` 必须存活到对应的完成或失败回调。发现回调由管理器发现线程执行。
- `VnaHardwareManager::shutdown()` 必须与新的发现、打开以及所有会话 API 调用外部同步；
  shutdown 返回后不再使用管理器或既有会话。普通发现和打开调用由管理器内部加锁保护。

## 未关闭事项

1. 固定生产目标 OS、CPU、GCC target triple、libstdc++ 与系统运行库，并在最终部署镜像或
   真机上补充链接、加载和运行验证；Linux/amd64 容器内的 GCC 7.3.0 编译门禁已通过。
2. 定义公司硬件的 `a/b` 单位、参考平面、参考阻抗、接收机修正和工厂归一化格式，并把
   参考阻抗、归一化标识及必要的实际值旁路数据补进 ABI 与公开波块契约。
3. 给出最大端口数、最大点数、目标点速率、首批延迟、CPU 和内存预算。
4. 根据目标平台补齐并验证 Windows DLL 加载封装；当前加载器已在 POSIX `dlopen` 路径实现。
5. 若上层需要多个事件消费者，先确定波块广播的所有权模型，再扩展订阅接口。
6. 获得公司硬件协议以及选定商用仪器的厂商 SDK/协议后，实现并联调两类真实驱动。
7. 为模拟器补齐噪声、过载、失锁、断线和数据丢失注入，并增加乱序、重复块、背压与
   性能预算测试；当前模拟器只覆盖确定性正常流和中止。
8. 多驱动接入后，把当前发现线程内的逐模块探测扩展为有界并行发现，并提供逐模块加载报告。
   当前超时只在模块调用之间检查，无法强制打断一个不返回的第三方 `Discover` 回调。
