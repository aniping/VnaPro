# 原始波采集层设计评审

| 项目 | 内容 |
| --- | --- |
| 评审对象 | `docs/原始波采集层软件设计.md` v0.12 |
| 代码基线 | `main` / `0155dc8` |
| 对照依据 | 当前 `VnaHardware` 源码、R&S ZNB v7.4、LibreVNA、NanoVNA、本地 SNA |
| 评审日期 | 2026-08-23 |
| 结论 | 原始波采集层职责通过；容量基线已定义，Hardware 内存与 Continuous 性能仍有 P0 |

## 1. 结论

用户指出“上一版太复杂”是准确的。v0.7 虽然纠正了平均和校准的数据阶段，但又走向另一端：
它试图在一份原始波采集层文档中预先解决完整产品级 Channel、Trace 需求、校准 workflow、校正
provenance、多 Channel 调度、订阅 QoS 和未来 Detector。结果是边界文字正确，领域模型仍然越界。

第一性原理判断标准很简单：

> 如果一项设计不影响“当前 Sweep 要采哪些波、块如何变成完整帧、运行何时终结”，它就不应
> 进入 V1 原始波采集层。

v0.12 已收敛为：

```text
VnaSweepPlan
  -> hardware Prepare
  -> 单个 ActiveSweep
  -> VnaWaveBlock 连续复制
  -> RawSweepFrame
  -> RunCompletion
```

该范围可以进入正确性原型。当前不应实现 Point Detector、多 Sweep 流水线或任何平均/校准算法。
由于职责已经不包含测量数学，建议模块使用 `VnaAcquisition`，中文称“原始波采集层”，避免
“测量核心层”继续暗示它负责 S 参数或校准，也避免“原始采集”被误解成 ADC/IF 采样。

## 2. 为什么 v0.7 过度设计

| v0.7 内容 | 问题 | v0.12 处理 |
| --- | --- | --- |
| ChannelCoordinator 和 owner requirement | 产品配置聚合侵入采集执行 | 移出本层 |
| S/Ratio/Wave 三套测量量键 | 原始波采集层开始解释最终量 | 输入直接使用 `VnaSweepPlan.requiredWaves` |
| PointDetectorConfiguration | 下层没有采样或能力契约 | 删除 |
| Calibration request/reducer/solver | 属于校准工作流 | 只保留一句边界 |
| Correction stage/provenance | 属于后续数值处理 | 删除 |
| Sweep Average 类型 | 本层不应跨 Sweep 运算 | 删除 |
| 多 Channel program cache | 当前硬件只驻留一个配置 | 删除 |
| 多在途 Sweep context | 当前硬件只有一个 active Sweep | 删除 |
| 第二套 Ingress/coverage/fence | 硬件层已经完成同一检查 | 删除 |
| 多订阅 QoS 和 latest/history | 属于上层分发和结果存储 | 删除 |
| Revision/Epoch/Program/Schema 多重 ID | 用户难以区分且 V1 无需公开 | 收敛为 ConfigurationId、RunId、sweepIndex |

这些不是“以后永远不做”，而是不能提前放错层。把未来功能写成当前公开类型，会制造兼容承诺，
也会让实现者误以为必须在热路径维护并不存在的状态。

## 3. 与最新 VnaHardware 的职责核对

主分支更新后，硬件层已经实现：

- 单个事件订阅者和同设备串行回调。
- WaveBlock 与 SweepCompletion 共用 FIFO 事件队列。
- `ConfigurationId`、`SweepId` 和迟到块过滤。
- 布局、点范围、意外点、重复点和逐布局乱序检查。
- 按点×激励统计完整覆盖，缺失时以 `DataLoss` 终结。
- 单个 `activeSweep_` 和有界硬件波块池。

因此原始波采集层重复构建 `FrameTracker`、coverage bitmap、sequence fence 和第二套波块队列既增加
CPU/内存，也会形成两个“谁才是完整性权威”的问题。v0.12 选择信任下层契约，只保留本层
复制计数作为内部自检。

主分支实现还补充了四条不能靠抽象猜测的控制语义，v0.12 已按源码写死：

- 从 `Prepared` 重新 Prepare 失败时，硬件保留旧配置；首次失败才保持未准备。
- 硬件 Prepare 成功后，本层若无法编译复制索引，旧配置已经失效，本层只能清空准备结果。
- Abort 正常路径先发 `SweepCompleted`，驱动立即报错路径可能先发 `CommandFailed`；必须对两个
  终态做顺序无关的双锁存。
- ConnectionLost、Timeout、DataLoss、HardwareFault 都清除硬件配置并进入 Fault。

这四条若写错，会造成旧配置误失效、合法 Abort 事件被判为协议错，或故障后继续启动过期配置；
它们不是可延后的实现细节。

进一步复核还补齐了命令提交锁、StateChanged 非权威终态、回调前状态提交、Engine/Manager 生命周期、
Start 事务和 Sink 反压。它们不是新增业务功能，而是“唯一完成、允许回调重入”成立所必需的
并发前提。

## 4. Point Detector 评审

### 4.1 准确语义

本文将 ZNB v7.4 §4.3.5.3 的 Detector settings 称为 Point Detector。它主要通过 Wave/Ratio
设置暴露，并在单点内处理：

- Normal 不额外归约。
- AVG Real Imag 在一个点的 observation time 内分别平均实部和虚部。
- AVG Mag Phase 分别平均幅度和相位。
- Peak 选择最大幅度，且相位未被评估。

它与跨完整 Sweeps 的 Sweep Average 不是一回事。
AVG 另用于 Noise Figure gain，手动校准采集也有独立 Detector 控制；这些语义不应合并成
原始波采集层的一个通用四态枚举。

ZNB 的 detector mode 随 measured quantity 选择，而 Detector Meas Time 是 Channel 级设置；
未来建模不能默认把两者合并成 per-wave 配置。

### 4.2 所有权结论

当前 `VnaHardware` 每点只返回一个复数波，没有 observation window 内的子结果、Detector mode、
observation time 或 capability。原始波采集层无法从一个最终复数值重建 Point Detector。

结论：

- 商用产品将来可能需要 Point Detector。
- V1 原始波采集层不需要该类型，也不实现算法。
- 真正增加时先扩展硬件 capability/plan/Prepare，由设备、驱动或接收机处理产生点值。
- 原始波采集层只透传计划并复制结果。
- 不把当前硬件输出未经证明地命名为“ZNB Normal Detector 等价结果”。

## 5. 任意波与校准能力没有丢失

删除 `SParameterKey` 和校准请求，不等于不能采校准所需波。上层可直接生成：

```text
Src P1 -> requiredWaves [a1, a2, b1, b2]
Src P2 -> requiredWaves [a1, a2, b1, b2]
```

原始波采集层原样发布这些波。因此 `a2@Src1`、Thru、Isolation 或将来的其他校准方法都不依赖
从 S 参数反推。区别只在于：由校准层决定“需要什么”，由采集层保证“完整取得”。

`NetworkMeasurementRequest` 也已删除。直接复用 `VnaSweepPlan`，避免两套点表、源设置和波定义。

ZNB v7.4 §5.9.4 说明：校准 Sweep 使用 Average Factor，system correction data 基于 averaged
trace 计算。但手册没有把这里的 trace 定义成 `a/b` 原始波，也没有给出
`Calibration(mean(raw)) == mean(Calibration(raw))`。因此可以确认“平均不属于本原始波采集层”，
却不能据此臆造校准与平均可交换；具体顺序必须由后续校准层的数据域和算法定义。

## 6. 性能评审

### 6.1 已消除的成本

- 不做 S/Ratio、校准、平均、幅相转换或 Trace 运算。
- 不做逐点对象分配和字符串 Map 查询。
- 不重复跟踪每点覆盖。
- 不设置第二条块队列或多 Sweep context。
- 不维护多订阅者队列、latest/history 或多 Channel cache。
- 只允许一个活动 Sweep，状态分支显著减少。

热路径理论复杂度是 `O(M)`，其中 M 是本 Sweep 的复数波样本数；每个样本只应复制一次。

### 6.2 真正的性能缺口

当前 `VnaWaveBlock` 只有逐元素 `value()`/`quality()`。底层每个值都会经过函数调用和边界检查，
不能整块复制。这是当前最值得优先解决的性能问题。

更稳妥的优化方向是由 `VnaWaveBlock` 提供单波批量复制：输出继续使用已有
`std::complex<double>`，硬件层隐藏 ABI 存储并把范围检查移出逐元素循环。这样不必为了优化
再冻结一个新的公共复数类型。若暂不增加，必须用明确的最大点数/波数/点速率基准证明逐元素
接口足够，不能凭感觉宣称性能没有问题。

### 6.3 为什么不是零复制

硬件块是有限缓冲池租约。若整次 Sweep 一直保留所有块，超过池容量后驱动无法继续提交。
所以原始波采集层必须边收边复制并立即释放块。这里的一次复制是完整帧长期所有权的必要成本，
额外队列和额外中间帧才是不必要成本。

### 6.4 4 端口容量验证基线

用户给出的参数只作为表驱动测试行，不进入生产常量：10,000 点、每点 4 激励、每激励 4 波。
端口数只约束源和波键合法性，不能再额外乘一次 4。

| 项目 | 结果 |
| --- | ---: |
| 点×激励记录 | 40,000 |
| 复数样本 | 160,000 |
| values payload | 2,560,000 B |
| quality payload | 640,000 B |
| 单帧 payload | 3,200,000 B（3.052 MiB） |
| layout 共享点索引 | 160,000 B（0.153 MiB） |
| 两槽池 payload（`waveBlockPointCapacity=10,000`） | 1,600,000 B（1.526 MiB） |
| 帧 + 两槽池 + pointIndices 子项 | 4,960,000 B（4.730 MiB） |

这组 4 波基线采用 `b1/b2/b3/b4`，只验证容量、端口映射和维度转置，不证明完整四端口 S 参数
或校准波集合。生产代码必须从 effective plan 求和，并由 `AcquisitionLimits` 提供单帧和本层
私有映射的逻辑 payload 预算；后者不包含 PreparedSweep 或分配器开销。

若 `ExcitationId=1..4`、`LayoutId=1..4`、PointId 与索引相等，且波键和容器都按自然顺序，错误
实现也可能通过。因此测试必须使用非连续乱序 ExcitationId/LayoutId/PointId、让 PointId 不等于
pointIndex、让四个布局采用各自不同的波顺序，并在部分点改变激励容器顺序；哨兵值按 ID 和
WaveKey 生成，不能按数组下标生成。

该核算还暴露了三项此前漏掉的下层风险：

- 当前 Hardware 把 slot 数写死为 8，并把驱动的批点数直接当成池容量；目标应是 Hardware 配置
  `slotCount`（V1 默认 2），并按实际 `slotCount × Wmax × waveBlockPointCapacity × 样本字节数`
  检查总池字节。全局批点数上限只属于异常输入防御。
- `PreparedSweep/effectivePlan` 在 Hardware 常驻、Prepare 事件和 Acquisition 持有之间存在多份
  fully-expanded plan；当前缺少聚合 plan payload 预算和 Prepare 峰值内存门禁。
- `processStart()` 每 Sweep 深拷贝完整 effective plan 并重建 FrameTracker/池；本用例约有
  90,000 个非空嵌套 vector，Continuous 性能风险可能高于 acquisition 的帧复制。

因此该用例关闭“验证规模未定义”，但不能替代目标 Sweep/s、CPU、P99 间隙和 RSS 验收值。

## 7. 保留的最小对象

| 对象 | 必要性 |
| --- | --- |
| `VnaSweepPlan` | 唯一采集输入 |
| `PreparedAcquisition` | 持有 `PreparedSweep` 和热路径复制索引 |
| `AcquisitionRunRequest` | 区分 Finite/Continuous 和 Sweep 次数 |
| `ActiveSweep` | 当前 `SweepId`、sweepIndex 和一个组装缓冲 |
| `RawSweepFrame` | 完整、不可变的原始波结果 |
| `AcquisitionRunCompletion` | 将一次 Start 与唯一结果直接绑定 |

不再定义产品 Channel、Trace、校准、校正、平均和 QoS 对象。

为了避免“精简了名字、仍把复杂度泄漏给调用方”，v0.12 还收紧了四处接口：

- `PreparedAcquisition` 对外只读，复制范围和目标偏移留在实现内部。
- 帧直接使用现有 `std::complex<double>`；批量复制优化不改变帧 Schema。
- Engine 独占已连接的 Idle 硬件和唯一订阅；活动 Run 不允许直接析构，Fault 通过外层重连恢复。
- 所有 Sink 回调串行、可重入且由 Engine 截断异常，不能让一次上层异常停用硬件订阅。

性能承诺也被收窄为“`onWaveBlock()` 不分配”。每 Sweep 是否需要内部帧池应由基准决定，不能
为了一个尚未给出的点速率目标先引入缓冲归还通知和等待状态机。

## 8. 参考实现对照

| 实现 | 支持本设计的事实 | 不照搬的部分 |
| --- | --- | --- |
| 当前 `VnaHardware` `0155dc8` | 单活动 Sweep；块与完成事件串行 FIFO；下层已做顺序和覆盖检查 | 不在上层重复 coverage、块队列或多 Sweep 流水线 |
| 本地 SNA | 单 outstanding job；终态形成只读 Snapshot | 不用 `LatestSnapshots` 关联本次 Run；失败后它仍可能保留旧成功结果 |
| [LibreVNA `c4276df1`](https://github.com/jankae/LibreVNA/tree/c4276df1e79c559f878ebc17e9f0bd3bd0a70f57) | 固件完成一个点的全部 stage/source 后才发布，显式保留激励阶段 | 主机端逐点求比值和字符串 Map 不进入原始成帧热路径 |
| [NanoVNA `d02db797`](https://github.com/ttrftech/NanoVNA/tree/d02db797a7032822137882f8f8a6c4ec21f064cd) | 静态完整 Sweep 数组，Sweep 完成后再交给显示 | 固定 `2×101` 模型以及采集循环内的比值、校准和电延迟不适合作为桌面分层 |

更具体的源码落点包括当前工程的 `VnaEventDispatcher.cpp`、`VnaFrameTracker.cpp` 和
`VnaSweepCommands.cpp`；本地 SNA 的 `HardwareRuntimeOpen.cpp`、`HardwareRuntimeAdapter.cpp` 和
`HardwareRuntimeWait.cpp`；LibreVNA 的固件 `Application/VNA.cpp` 与主机
`Device/LibreVNA/librevnadriver.cpp`；NanoVNA 的 `main.c`。

共同证据只支持“单活动 Sweep、有限存储、完整后发布原始帧”。它们不支持提前设计多 Sweep
并发、块级多订阅、字符串化测量量或在采集层内做校准。

## 9. P0/P1 门禁

| 优先级 | 项目 | 关闭条件 |
| --- | --- | --- |
| P0 | 波块批量复制能力 | 增加批量复制 API，或基准证明逐元素接口满足明确目标 |
| P0 | Acquisition 自有容量 | v0.12 参数化用例通过，部署给出帧和私有映射 payload 预算，全部算术受检 |
| P0 | Hardware 池策略 | slotCount 可配置且默认 2；Prepare 按实际组合检查总字节；全局维度上限仅作异常输入防御 |
| P0 | Prepared plan 聚合内存 | Hardware 对 plan/result 执行 checked 聚合预算，并验证 Prepare 峰值 RSS/分配数 |
| P0 | Continuous 下层成本 | 基准证明每 Sweep 深拷贝/重建可接受，或复用 prepared plan/tracker/pool |
| P1 | 真机波数值契约 | 真机版本定义单位、参考阻抗/平面、相干和工厂归一化边界 |

Point Detector、Calibration、Sweep Average、Trace 和多 Channel 调度不是本层 P0；它们应在
对应模块启动时各自设计。

## 10. 实现顺序

1. 只读 `PreparedAcquisition` 和紧凑波序列布局。
2. 单次 Sweep 的块复制、硬件终态映射和不可变帧发布。
3. Finite/Continuous、Stop、Abort 和唯一 RunCompletion。
4. 正确性、故障注入和长时间运行测试。
5. 基准测试后决定批量复制 API 与内部帧池。

不应在第 5 步以前增加多 Sweep pipeline、多 Channel cache 或通用 QoS。

## 11. 最终判定

| 结论项 | 判定 |
| --- | --- |
| 原始波采集层职责 | 通过 |
| 任意直接波支持 | 通过，由 `requiredWaves` 表达 |
| Single/Finite/Continuous 语义 | 通过，每 Sweep 一帧，不含平均 |
| Point Detector V1 | 删除正确；不是本层算法 |
| 校准/平均/Trace 边界 | 通过，只保留边界，不设计其内部 |
| Prepare/Abort/生命周期闭环 | 通过，与 `0155dc8` 实际事件语义一致 |
| 4P/10k/4 激励/4 波验证 | 通过设计评审；等待实现测试 |
| Hardware 池策略 | 不通过；当前仍写死 8 slot，且未按实际组合执行总字节门禁 |
| Prepared plan 聚合内存 | 不通过；当前存在多份嵌套 plan 且没有聚合预算 |
| Continuous Start 成本 | 暂缓；需测试深拷贝和重建成本 |
| 高吞吐数据接口 | 暂缓验收，需批量复制 API 或基准证据 |
| 完整商用 VNA 数值链 | 不在本层范围 |

v0.12 可以作为 V1 正确性原型依据。通过的是“单设备逐 Sweep 原始波采集层”和一组容量验证
基线，不是完整测量软件栈；Hardware 池字节预算、Prepared plan 聚合内存、Continuous Start 成本
和产品吞吐目标关闭前，不能把它判为生产高吞吐设计通过。
