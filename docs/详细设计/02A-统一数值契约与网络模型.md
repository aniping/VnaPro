## 6. L4：确定性数值核心

### 6.1 统一处理阶段契约与显式状态（`Stage`）

六个 Core 的算法不同，但都使用同一条纯计算边界：输入是已经冻结的 Prepared operator、NumericSchema、只读数值视图和可选状态快照，输出是不可变数值、质量和可选状态增量。L4 不创建线程，不访问文件、网络或 Repository，也不拥有 WAL、重试或 startup recovery。

这条边界同时禁止产品和存储身份渗入数值 API。L4 不接收 `ChannelId/MeasurementId/TraceId/TraceRevision`，也不接收 `ResultRef/CalSetRef`、Repository port、artifact 路径或序列化字节。L5 可以把产品关系编译为计划内 `NumericNodeKey/OperandSlot`，L7 可以把持久引用解析为受保护的不可变数据；L4 最终只看计划内坐标、数值含义和借用视图。

#### 6.1.1 纯处理阶段接口形状（`Stage`）

```text
PreparedStage
  StageId + StageKind + ProcessingRevision
  input/output NumericSchema + ProcessingAccessPoint
  InputCompletenessRequirement   // Point / Segment / LogicalUnit / FullSweep
  OutputEmissionGranularity      // Point / Segment / Frame / Snapshot
  OrderingRequirement            // Independent / InOrder / SingleWriterStateful
  Statefulness                   // Stateless / ExplicitState
  ResourceEstimate + Quality/ErrorPolicy

StageStateSnapshot
  StageStateKey
  StateRevision
  immutable payload + payloadHash

StageStateDelta
  StageStateKey
  expectedBaseRevision + expectedBaseHash
  immutable delta + deltaHash
  CommitBoundary                 // CursorSlice / CountCommitBoundary / RunTerminal

StageEvaluationResult
  immutable output frame(s) + Quality
  optional StageStateDelta
  resource disposition
```

Core API 是同步确定性函数：`evaluate(preparedOperator, numericInputs, optional priorState) -> StageEvaluationResult`。Core 不保存可变字段，不读取“当前 Channel/Trace”，不解析处理图，也不提交 delta。相同 Prepared operator、数值视图和 StateSnapshot 必须得到相同输出与 delta。

#### 6.1.2 正常路径

1. L5 bind 冻结 Stage 顺序、输入/输出 Schema、完整度、状态键、`StageStateRetention` 和资源上界，并逐节点调用 L4 的无 I/O prepare 入口形成 Prepared operator。
2. [D3 §8.4](./03B-测量生命周期与完成.md#84-通道运行实例vnarunengine)通过冻结计划指定的 state port 取得 exact `StageStateSnapshot`，再按冻结顺序连同输入 Frame 交给 Core。
3. Core 完成一次求值，返回 immutable output/Quality；有状态 Stage 额外返回基于 exact revision/hash 的 delta。
4. [D3 §8.4](./03B-测量生命周期与完成.md#84-通道运行实例vnarunengine)只在声明的 `CommitBoundary` 闭合后，按 `StageStateKey` 的冻结提交序号处置 output 与 delta；Point/Segment 预览不得冒充完整逻辑单位。
5. 普通运行期状态走 [D3A 运行周期内状态存储](./03A-运行对象职责与端口.md#运行周期内状态存储普通扫频平均与迹线保持)实现的 `RuntimeEpochStatePort.commit`；只有产品明确要求跨重启恢复的工作流状态才走 [D4D §9.5.5](./04D-持久化结果与恢复.md#955-持久交付的唯一提交与恢复协议)对应的 `DurableStateContributionPort.begin`。两者都必须取得对应 state-head commit receipt，[D3 §8.4](./03B-测量生命周期与完成.md#84-通道运行实例vnarunengine)才推进逻辑计数。
6. 结果交付与状态保留是两个正交维度：实时当前结果走 `LiveResultPort`，历史或工作流证据走 `DurableResultPort`，未计划的维度不建立 obligation。只有冻结计划明确要求“持久结果 + 持久状态”原子可见时，持久适配器才以同一 decision 提交；基础设施不支持时必须在运行准入前拒绝。

这类状态遵守以下规则：

- 普通 Sweep Average 固定在 Prepared 声明的访问点，以 `CountCommitBoundary` 提交完整逻辑单位；Trace Hold 同样使用显式 snapshot/delta。
- 两者默认 `StageStateRetention=RuntimeEpochEphemeral`：状态只属于当前 RuntimeEpoch，进程重启、SessionGeneration 或 RuntimeEpoch 切换后重新起算，不写 WAL、不访问 Repository。
- 只有明确的可恢复工作流才使用 `WorkflowDurable`。
- 参考迹线数据（Trace Memory）进入 L4 时已经是带 NumericSchema、访问点、轴和内容摘要的 `ExternalNumericInputView`，不是 Core 内隐藏缓存，也不携带其 Repository 引用。
- Calibration solver candidate、transform plan 等天然不可变对象不需要伪造 StateSnapshot。

#### 6.1.3 线性化点与唯一责任方

普通运行期状态的线性化点是 `RuntimeEpochStatePort` 对 state head 的成功 CAS；L6 取得 receipt 后才推进逻辑计数，再按冻结交付计划发布实时当前结果。实时发布失败、被新 ordinal 取代或因 Recall/Close 失效，都不得回滚已经提交的平均/保持状态。实时 current 是会话视图，不承担“状态与结果跨存储原子提交”的含义。

只有 `WorkflowDurable` 与持久 Result 同时属于同一冻结业务决策时，才要求适配器以一个 durable decision 覆盖 result publish 和全部 state-head CAS；否则状态贡献与结果交付分别形成 disposition。Contributor 可以没有本 Run 的 Result，但必须取得与其保留策略匹配的 state receipt，不能只改 Core 内存后直接报成功。L4 只声明 `StageStateDelta + CommitBoundary`，不实现端口提交或跨 store 事务。

同一 `StageStateKey` 的状态提交采用冻结的单写序列。L5 为每个有状态 Stage 声明稳定 key、`StageStateRetention` 和顺序要求，L6 在 logical-unit admission 时按序分配不复用的 `contributionOrdinal`；同一 key 最多一个 state-head commit 在途，后一项只能读取前一项 receipt 指向的 next snapshot。两个 Run 同读 base revision 后各自提交的实现不满足本合同，发生冲突时也不得跳过前项或按 worker 完成时间重排。

| 责任 | 唯一 owner | 本篇边界 |
| --- | --- | --- |
| 计算 output/Quality/delta | L4 Core | 唯一纯计算事实源 |
| Trace DAG、拓扑排序、Schema 推导、整图资源估算与产品节点映射 | L5 Channel compiler | L4 只准备和求值单个算子 |
| Trace 产品身份、ResultRef、pin、Repository 读取和产品事务 | L7 Application | L4/L5 都不执行读取或修改保留责任 |
| ResultArtifact 格式校验、版本迁移和数值 payload 解码 | Infrastructure Repository adapter | 解码完成后只交付不可变数据说明与 Lease |
| 冻结 snapshot、分配 per-key `contributionOrdinal`、登记并收口 state/result obligation | [D3B §8.4 通道测量任务](./03B-测量生命周期与完成.md#84-通道运行实例vnarunengine) | L4 不见 Run journal、WAL、实时槽或 Repository |
| 当前 RuntimeEpoch 的内存 state head | [D3A `RuntimeStageStateStore`](./03A-运行对象职责与端口.md#运行周期内状态存储普通扫频平均与迹线保持) | 普通 Average/Hold 的唯一写者；切换运行周期或重启后清空，零 WAL/Repository 调用 |
| 可跨重启的 state/result commit、WAL、Repository decision、超时移交和 startup recovery | [D4D §9.5.5 持久交付](./04D-持久化结果与恢复.md#955-持久交付的唯一提交与恢复协议) | 仅 `WorkflowDurable` 或持久 Result；L4 不执行 I/O，不拥有 record/receipt/retirement |

因此 `StageStateSnapshot/Delta` 不携带 `ResultCommitIdentity`、WAL record、Repository `PreparedResultRecord` 或 `CommitDecision`；这些身份在 owner 端用强类型 envelope 关联，不能反向污染数值 API。

#### 6.1.4 失败与恢复

- 输入 Schema、状态 revision/hash、有限值或资源预算不满足时，Core 返回确定性的字段级失败；delta 视为未产生，输入 owner 仍负责释放。
- Retry、Stop、Abort 或 Failed 未到 CommitBoundary 时不得应用 delta。到达 boundary 后，delta 只能经其 `StageStateRetention` 指定的 state port 提交；是否重试、是否新建 operation 由 [D3 §8.4](./03B-测量生命周期与完成.md#84-通道运行实例vnarunengine)冻结策略决定。
- 进程恢复不反序列化 Core 内存。`RuntimeEpochEphemeral` head 按 [D3A 运行周期内状态存储](./03A-运行对象职责与端口.md#运行周期内状态存储普通扫频平均与迹线保持)直接清空并以新 RuntimeEpoch 起算；只有 `WorkflowDurable` 才能由 [D3 运行完成处理](./03B-测量生命周期与完成.md#84-通道运行实例vnarunengine)与 [D4D 持久交付协议](./04D-持久化结果与恢复.md#955-持久交付的唯一提交与恢复协议)从 exact Prepared、数值输入内容摘要、base snapshot 和持久 owner record 继续。需要重新读取 artifact 时只能由 L7/Infrastructure 按原精确引用恢复，L4 不参与。
- 任何“L4 写 WAL”“Core 直接调用 Repository”“把 TraceId/ResultRef 塞入 PreparedStage”或“从当前 state head 猜上次 delta”的实现都违反依赖方向。

#### 6.1.5 验证

验证分为四层：

- 纯单元测试覆盖 Stateless/ExplicitState、两种 `StageStateRetention`、三种 OrderingRequirement、所有 CommitBoundary、snapshot revision/hash 冲突、delta 确定性、失败时无 delta 和预算 exact/少 1 byte。
- L4 静态依赖测试还必须禁止产品 ID、ResultRef、Repository header 和 artifact codec；用两个不同 Repository 引用解析出的相同 Numeric view 调用 L4 时，Prepared hash 与数值输出必须相同。
- 模型测试还必须覆盖同 key 两个 Run 严格按 ordinal 串行；普通 Average/Hold 在重启后清空且 WAL/Repository 调用数为零；`WorkflowDurable` 在 accepted 后立即崩溃，恢复后贡献恰好一次且下一项读取其 next snapshot。
- 跨层故障注入、state/result 偏序和全进程恢复由 [D3C §8.7](./03C-触发多通道调度与验证.md#87-线程与运行时验证)与 [D4D §9.6](./04D-持久化结果与恢复.md#96-应用层验证门禁)验证；本篇不复制那套 WAL/Repository 字段墙。

### 6.2 原始观测数值核心（`VnaObservationCore`）

这是现 `VnaMeasurement` 的目标职责和名称。

- L5 先把产品 `MeasurementSet` 降低为不含 MeasurementId 的 `ObservationOperatorSpec`，并推导 Source/Receiver/Wave 需求；L4 不读取产品集合。
- `prepare(operatorSpec, EffectiveExecutionPlan, WaveSchema)` 依据实际轴、布局和逐 series/Axis span 语义建立不可变数值索引；产品级兼容报告仍由 L5 汇总。
- `evaluate(prepared, RawWaveFrameView)` 生成带 `ObservationSchema` 的 DirectWave、ReceiverRatio 等 `ObservationFrame`；只依赖 L0 只读契约，不包含 L3 头。
- 比值前按每个相交 Axis span 验证相干组、归一化、参考路径和 Partial 关系；不得只检查分母非零。
- 输出继续称 Observation；只有后续网络模型证明后才称 S 参数。

Observation 的质量不是一个 OR 后的模糊 bitset，必须分别保存来源和本次计算事实：

```text
ObservationSampleQuality
  numeratorWaveQuality
  optional denominatorWaveQuality
  CalculationQuality calculationQuality

CalculationQuality
  disposition                 // closed enum
    Valid
    MissingNumerator
    MissingDenominator
    DenominatorZeroOrBelowThreshold
    InputNonFinite
    ArithmeticOverflowOrNonFinite
```

Direct observation 原样保留 numerator value/quality，denominator 为空，CalculationQuality 默认 Valid；输入质量不净不等于本次计算失败。Ratio 分别复制 numerator/denominator quality，绝不 OR 成 CalculationQuality。计算主因按上表顺序选第一个适用项，因而互斥；`minimumDenominatorMagnitude` 来自 Prepared 数值策略，不散落魔数。

失败主因确定后输出规范 quiet NaN 占位，并停止对占位值做二次分类：不能因为该 NaN 再追加 InputNonFinite，也不能因为缺失时填了 0 再追加 DenominatorZero。只有两个输入原值均存在且有限、分母达标，而复数除法结果仍非有限时，才是 ArithmeticOverflowOrNonFinite。后续 Calibration/NetworkModel 可以按自己的 policy 阻断输入质量，但不能改写 Observation 的原始三段质量事实。

它是同步纯函数集合，不创建线程、不运行 Sweep、不持有 Channel。

### 6.3 厂商修正状态调理核心（`VnaProviderConditioningCore`）

Factory normalization/correction 是独立 typed stage，不属于用户 CalSet，也不能被 `NetworkModelCore` 隐式吞掉。`EffectiveExecutionPlan` 必须逐 span 声明 `ProviderConditioningState {Unconditioned, FactoryNormalized(revision), FactoryCorrected(revision)}`、适用访问点和模型 fingerprint：

```text
ConditioningOperation
  ConditioningOperationId
  Placement                    // ProviderApplied / WaveSide / NetworkSide
  Mode                         // Apply / VerifyAlreadyApplied / NotRequired
  input/output CorrectionStateId
  model revision/hash + AxisSpans
```

- 若 provider 已在硬件/Driver Host 中完成 conditioning，Wave/Network Schema 直接声明已应用状态和 revision，Core 只验证，不重复计算。
- 若受信 provider 交付本项目支持的不可变 factory model，`VnaProviderConditioningCore` 可在明确的 wave-side 或 network-side access point 纯函数应用，并输出新 `CorrectionStateId`。
- 未知第三方算法既不能伪装为未处理 raw wave，也不能作为任意计算 DLL 注入 L4；它只能从 provider 真实声明的后续访问点接入。
- Stage placement、输入/输出 Schema、质量传播和 provenance 在 `PreparedStagePipeline` 中冻结。NetworkModel 只做量/拓扑映射，必须原样传播输入 correction state。

同一 ConditioningOperationId 在每个 Axis span 必须恰好 `Apply` 一次、`VerifyAlreadyApplied` 一次，或由 capability/Schema 证明 `NotRequired`；bind 对遗漏、重复 placement、revision/hash 不一致或状态转移不闭合一律失败。wave/network 两侧都有处理时必须是两个不同 OperationId。`NotRequired` 是“该 factory operation 对此 span 经证明无需执行”的算法事实，仍写 provenance，不是用户关闭校准。

### 6.4 网络参数模型核心（`VnaNetworkModelCore`）

这是 Observation 与网络参数之间不可省略的类型转换边界：

- L5 把产品 `NetworkMeasurementDefinition + PortTopology` 降低为不含 MeasurementId/ChannelId 的 `NetworkModelOperatorSpec`，明确激励端口/模式、响应端口/模式、波定义、数学参考阻抗和期望矩阵元素。
- L4 `prepare(operatorSpec, ObservationSchema)` 对每个 Axis span 证明必需的 incident/reference/outgoing Observation 齐全，相干关系和模拟路径关系成立，激励矩阵可解且端口拓扑一致。
- `evaluate(prepared, ObservationFrame)` 输出带 `NetworkMatrixSchema` 的网络矩阵，并原样传播已声明 factory conditioning state；不得仅凭名称 `b/a` 或二维索引把值改称 `Sij`。
- `AP_OBSERVATION` 是类型化内部访问点；产品是否对 SCPI/Data API 暴露它由 Adapter capability 决定。网络侧 factory stage 完成或 Schema 明确声明 provider 已应用后，结果才进入 `AP_BEFORE_USER_CORRECTION`。

对于一列一激励的直接比值，证明可能退化为索引映射；对于多源、mixed-mode 或需要矩阵求解的方案，必须显式验证秩、条件数和质量传播。该 Core 是同步纯函数，不应用用户 CalSet；用户系统误差校正在后续 Correction stage 完成。
