## 阅读入口

### 30 秒摘要

- Save 冻结开始时的当前设置，产生新的不可变 `RecallSet`；写入期间用户可以继续编辑，完成后不会把当前设置改回旧版本。
- Recall 先在当前设置之外构造并验证完整候选，再停止和排空受影响的旧运行，最后一次性替换当前设置；设备 Prepare 是替换后的独立动作，Prepare 失败不回滚已替换的设置。
- 会话内实时当前与历史结果保存是两个正交决定。实时当前只使用有界内存结果槽，不要求先保存；旧会话或旧运行代次的结果不能覆盖新会话。

### 正常主线

1. **Save：**冻结一个 WorkingSet 版本 → 校验外部引用 → 发布不可变 RecallSet → 仅在会话归属仍匹配时推进保存基线 → 清理临时责任。
2. **Recall：**读取并验证工件 → 构造候选并试编译 → 关闭受影响的新准入并排空旧工作 → 原子替换 WorkingSet、保存基线和 SessionGeneration → 重新开放并按新设置准备设备。
3. **FinalCAS 之前失败：**候选不发布，旧 WorkingSet/保存基线/SessionGeneration 继续是权威设置；已 Stop 的旧运行只按恢复回执收口，不伪装成从未停止。
4. **FinalCAS 之后失败：**新 WorkingSet/保存基线/SessionGeneration 已是权威设置。后续设备 Prepare 失败只把对应 Channel 标记为 Empty/Unresolved/Fault、尚不可运行，必须新建 Prepare operation 重试；不得倒退已提交的 Recall。
5. **外部结果未知：**只查询或重放同一完整请求，或把完整责任 source-zero 移交给既有恢复者，不凭超时猜测成败。

## 9.3 保存、召回与运行切换事务

### 9.3.1 工件语义与哈希边界

RecallSet 是不可变设置工件，不是 live Session 的别名：

```text
RecallSetArtifact
  RecallSetId + RecallSetRevision + RecallSetContentHash
  schemaVersion + ArtifactIntegrityHash/checksum + migrationProvenance
  canonical SessionWorkingSet payload
  exact external references[]       // CalSetId/CalSetRevision/CalSetContentHash 等，不内嵌 Result
  outgoing pin + lineage receipts[] // Repository签发；不属于可伪造payload或content hash

RecallCandidate
  RecallOperationIdentity       // RecallOperationId + RecallRetirableLocator；不可拆分
  expected InstrumentSessionId + SessionRevision/SessionGeneration/WorkingSetRevision
  target RecallSetId/revision/hash
  RecallTargetOperationPin + candidate external-resource pins/lineage receipts
  candidate SessionWorkingSet + WorkingSetContentHash
  compiled Prepare/Rebind intents + unresolved-binding report + routing plan
  resource plan + DryRunReport
```

### 9.3.2 设置召回正常路径与线性化点（`Recall`）

同一 RecallSetId 的成功 Save 单调增加 RecallSetRevision；Save As 创建新 ID/revision 1。

`RecallSetContentHash` 与 WorkingSetContentHash 使用同一 canonical persistable payload + exact external refs 算法。它排除 artifact envelope、RecallSetId/revision、schemaVersion、save time、文件路径和压缩字节；`ArtifactIntegrityHash/checksum` 才覆盖实际序列化 envelope/schema。

#### 设置保存与迹线数据必须分开

ZNB 手册可以支撑的产品边界是“Recall Set 保存设置，Trace/Touchstone 数据另行导出”，不能由此推导厂商内部存储结构。VnaPro 因而固定三条产品规则：

| 对象 | 保存内容 | 召回时行为 |
| --- | --- | --- |
| `RecallSetArtifact` | 只保存设置和 exact external reference；不内嵌采样点、迹线数值或 `ResultArtifact` 字节 | 只替换 WorkingSet，不伪造一次新测量 |
| Trace Memory / Saved Result | 独立、带 NumericSchema 和 provenance 的 `ResultArtifact` | WorkingSet 中若有 exact ref，先验证并取 pin；不把数据复制进 RecallSet |
| Touchstone/厂商数据文件 | 适配器 profile 定义的外部工件 | 经 Import 用例转成独立结果，不由 Recall 隐式读取 |

Native profile 可以在设置中保留 Trace Memory 的 exact ref，这是 VnaPro 的显式设计，不宣称与 ZNB/SNA 状态文件等价。`ZNB/*` 或 `SNA/*` Recall 兼容 profile 只能序列化真机 transcript 已证明的字段和召回后效果；当前 `GAP-ZNB-RECALL-TRANSCRIPT-001` 与 `GAP-SNA-RECALL-TRANSCRIPT-001` 未关闭，所以两种兼容导出/召回均必须 `BlockedPendingEvidence`，不得静默丢弃 Trace Memory 引用后声称兼容。

读取后先验证 artifact 完整性，再迁移/规范化并重算内容 hash。catalog 声称的 revision/hash 与载荷不符即损坏，不能进入 dry-run。

`RecallTransition` 由 Session command executor 单写。下列四条分别处理互斥、清理、查询与替换，不得合并成一个含糊的“是否完成”判断：

- **active owner 互斥：**同一 Session 最多只有一个 active Recall owner。
- **解除互斥的条件：**只要上一份 Recall journal 尚未 `CleanupDone`，或仍持有 gate/Close/recovery claim，新 Recall 就必须在创建 candidate/gate 前稳定返回 `RecallAlreadyInProgress{active RecallOperationIdentity}`。`CleanupDone` 且责任归零后，才可创建新 transition。
- **旧 Ticket/receipt 查询：**旧 Ticket 或 receipt 仍在 Retained 重试窗口不构成业务互斥；它们可继续查询，不得阻止已满足上一条的新 Recall。
- **不支持 supersede：**V1 不提供 Recall-to-Recall supersede 或责任转移。新 Recall 要么因互斥被拒绝，要么在旧 owner 完全收口后以新 identity 开始。

#### 正常路径：准入与首个恢复引用

Recall admission 必须先从 `RecallRecoveryPool` 预留最坏 slice。该 pool 对 records、pin-slots、lineage-slots、candidate-bytes、cleanup-slots 和 quarantine-slots 都有硬上限。

随后分配完整 `RecallOperationIdentity{RecallOperationId, RecallRetirableLocator}`，再 fsync：

```text
RecallTransitionJournal
  complete RecallOperationIdentity
  state = StagingPrepared
  requested exact RecallSet target
  canonical semantic Recall request
  semanticRequestHash + fullOperationEnvelopeHash
  expected InstrumentSessionId
  expected SessionRevision + SessionGeneration + WorkingSetRevision
  expected Lifecycle + ClosingEpoch
  reserved budget
  empty target/candidate/grandfather pin ledger
  empty CatalogAdmissionLineage receipt ledger
  cleanup plan
```

在这次 fsync 之前，不得取得 `RecallTargetOperationPin`、普通 candidate pin、`GrandfatheredRecallCandidatePin` 或 lineage receipt，也不得建立 Gate。

artifact 实际外部引用超过预留上界时整次拒绝，不临时扩容。

Application journal 与 Repository pin ledger 不是伪装成一个跨库事务。

每枚 pin 调用前，Application 先在上述 journal 的预留槽写入并 fsync：

`PinAcquirePending{完整 PinAcquisitionIdentity, pin kind, exact target, owner=RecallOperationIdentity, canonical semantic request, semanticRequestHash, fullOperationEnvelopeHash}`。

Repository 只有在完整 identity 与 semantic hash 匹配，且 full-envelope hash 可重算时，才 create-if-absent 授予 pin 并保存反向 owner。ACK 后，Application 再写 receipt/`PinAcquired`。

#### 失败与恢复：保护引用调用窗口（`pin`）

崩溃在调用、ACK 或 journal 回填任一边界时，startup 以 Pending 的完整 identity 与两个 hash 查询原 decision：

- decision 存在：补记后释放或继续；
- decision 不存在：写 NoPin 并归还槽。

因此不会出现“Repository 里已有 pin、Recall 却没有可枚举 owner”的窗口，也不需要不可实现的跨-store 原子提交。

默认模式是全事务 `ReplaceWorkingSetAtomically`。结构、引用、迁移、资源门禁、旧运行排空或 final CAS 任一失败，候选整体失败；不允许“其余 Channel 先 Recall 成功”。

这里的原子边界是产品 `SessionWorkingSet + LoadedRecallSetRef + SessionGeneration`，不是不可回滚的设备 I/O。

RecallSet 只保存设置。因此，V1 Recall 不在 final CAS 前调用 L2 Hardware Prepare，也不把旧 generation 的 Handle 转给新 generation。新 Channel 先以 Empty/Unresolved deployment 发布，之后按显式策略另起 Prepare operation。

需要只导入未解析设置时，调用独立 `DetachedImport`。它只发布离线 artifact，不替换 live WorkingSet。只有显式 `ApplyAlteredCandidate` 才允许把经用户确认的 migration alteration 作为一个完整候选应用，并且必须保持 Dirty。

RecallSet 的 canonical payload 保存完整 `UserCorrectionBinding` union tag：

- `Unbound`：没有 external ref/pin/lineage。
- `Bound`：把 exact CalSet ref 列入 external references，并在 staging 取得携带已验证 CatalogAdmissionLineage 的 candidate pin。
- 显式已保存的 `MissingUnresolved`：只保留 requested ref/source provenance 作诊断内容，不得加入 reverse-reference index。

三种 tag 及各自语义载荷都进入 `WorkingSetContentHash/RecallSetContentHash`。pin id、lineage receipt、运行 compatibility/display 不进入内容 hash；但 pin/lineage receipt 必须进入 Repository 保护 envelope 和 Save/Recall journal，不能从 artifact payload 自行反序列化为权利。

原 artifact 中的 `Bound` 缺失精确 CalSet revision 时，普通 Recall 整次拒绝。DetachedImport 只能把该候选改为 `MissingUnresolved{requested exact ref, source provenance}`；该变体没有 pin/lineage、不可 Prepare，也没有结果/`DisplayedCorrectionState`。

tombstone 后的 grandfather 资格有且只有两条可验证来源：

1. RecallSet 在删除前已发布。Repository 保存 `RecallSet exact identity + pre-delete outgoing-pin PublicationReceipt + CatalogAdmissionOrder`，并可由此签发 `PreDeletePublicationRoot`。
2. 删除后由仍合法的 WorkingSet 保存。Repository 在 publication 时签发 `GrandfatheredSaveOutgoingPin + CatalogAdmissionLineageReceipt`；该 lineage 按 parent receipt 链递归可验证到早于 tombstone 的 `VisiblePermitRoot | PreDeletePublicationRoot` 之一。

两类 immutable outgoing pin 都永久归 RecallSet 所有，只作资格证明，绝不能 move/release 给 live WorkingSet。

#### 线性化点：既有合法候选转入当前设置工作区

普通 Recall 在 tombstone 后，必须让 Repository 完成以下一种验证：

- 验证直接 publication receipt，并据此建立 `PreDeletePublicationRoot`；
- 验证 `RecallSet outgoing pin → parent lineage receipts → (VisiblePermitRoot | PreDeletePublicationRoot)` 的完整链，并校验每跳 rootKind 不变。

两种路径都要求每跳 exact ref 一致，且根满足 `CatalogAdmissionOrder < TombstoneOrder`。验证通过后，Repository 才签发独立：

`GrandfatheredRecallCandidatePin{RecallOperationIdentity, exact ref, verified CatalogAdmissionLineageReceipt}`。

final CAS 只把 candidate pin 及同一 lineage 转成 WorkingSet binding pin，源 RecallSet outgoing pin 不动。失败则按 Recall cleanup receipt 释放 candidate pin。

#### 失败关闭：不得伪造引用合法性来源链

以下来源都不能取得 grandfather 资格，也不能借 Save/Recall 洗白：

- 删除后导入的外部 artifact；
- altered candidate；
- 自报 lineage 字段；
- `MissingUnresolved → Bound`；
- exact ref/BindingRevision 任一不匹配。

后续 `ApplyAlteredCandidate` 必须让用户逐项三选一：

1. 保留 `MissingUnresolved`；
2. 显式 Unbind 成 `Unbound`；
3. 选择一份存在的 exact ref 建立 `Bound{enable, policy}`。

第三种和任何显式 Bind 一样，必须先取得当前 Visible catalog revision 的 `CatalogBindingPermit`；tombstone 后明确失败。不得在不存在或已隐藏的新 ref 上只写 `DisabledByUser` 伪造 Bound。

只有未来新 Run 实际采用 `BypassUnbound` 或 `BypassDisabled` 后，那个新结果才是 CalOff。导入、候选或 Recall 本身都不能把旧结果重标 CalOff。

阶段顺序固定如下；每一阶段只允许下述出口。

#### 阶段 1：候选设置构建（`Staging`）

进入条件是 journal 已处于 `StagingPrepared`，且预算已预留。

1. 每次先 fsync 完整 `PinAcquirePending`，再用该 identity 取得或查询目标 `RecallTargetOperationPin`/candidate pin，并回填 receipt。
2. 读取 artifact，校验 checksum 与内容 revision/hash/schema，并执行纯迁移。
3. 只为 `UserCorrectionBinding::Bound` 及其他真实 exact external refs 取得 pin。
4. 对 tombstoned CalSet，Repository 验证直接 pre-delete publication receipt 或递归 lineage 链；再走相同 pending/receipt 协议，签发携带 verified lineage 的 `GrandfatheredRecallCandidatePin`。
5. Unbound/MissingUnresolved 不建立 pin/lineage。

全部 pending 均已决议，且 pin/lineage 与 candidate 摘要登记后，写 `Staged` 并进入 DryRun。失败则写 `RejectedBeforeGate`，按 journal 逐枚释放 target/candidate pins 与预留 cleanup；绝不释放或转移 RecallSet outgoing pin，现 Session 零变化。

#### 阶段 2：无副作用预检（`DryRun`）

校验 ID/TraceDisplayBinding/CalSet 精确引用，纯编译 routing/Channel 与未来 Prepare/Rebind intent，并计算 exact 软件资源；禁止设备 I/O。

结构或引用错误时整次拒绝。设备缺失或能力不支持时，记录为 Unresolved binding；可保留原设置，但不得静默量化。

#### 阶段 3：关闭新运行准入（`Gating`）

已有完整 journal 只从 `Staged` 推进到 `Gated`。CAS 匹配 expected InstrumentSessionId、Session/WorkingSet revision、SessionGeneration、`Lifecycle=Open` 与 `ClosingEpoch`，建立 `RecallGate{完整 RecallOperationIdentity}`，并关闭新设置、Prepare、Initiate、Trigger/AdvanceEvent/TargetBatch admission。

RecallGate 还必须与 Binding/Calibration 的 first-wins 边界处于同一 Application transaction coordinator，顺序固定为“冻结 exact 活动清单 → 验证各子 gate/attachment revision → 写子 fence → 发布 RecallGate”。整段使用同一 serializable commit，并验证 `ActiveBinding/CalibrationRegistryRevision`；任一新 admission 都要推进该 revision，因而不可以在“冻结清单”与“发布 gate”之间滑入：

- 每个受影响 Channel 的 `BindingTransitionGate` 必须是 `OpenFree`。若为 `Held`，包括产品已是 `Bound{TransferPending}` 的 Bind/rebind，Recall 本次 Gating 稳定返回 `RecallBindingTransitionBusy{BindingOperationIdentity, holderRevision}`，不建立 RecallGate；先让原 operation完成稳定 pin、拒绝并 release，或转入 quarantine。`Quarantined` 同样拒绝，直到资源/gate disposition已收口。
- `Bound{TransferPending}` 却找不到 matching Held journal/claim 是协议故障，关闭 Recall/Save/Prepare/Result admission，不能按 Bound 或 Unbound 猜测。Recall 不接管 BindingPinTransferClaim，也不把旧 pin cleanup复制进自己的 journal。
- 对每个 active `CalibrationAttempt`，冻结 `kind + CalibrationAttemptIdentity + CalibrationAttemptAttachmentRevision + ownerLedgerDigest`，再以 exact attachment revision 写 `RecallFence{RecallOperationIdentity, old SessionGeneration, attempt kind}`。Prepare/Capture/Solve/Verify/Publish 的 admission、后续外部调用与每个 Workspace CAS 都必须在同一 Application 单写域检查 RecallGate/fence absent；Workspace CAS 或 Evidence install 与 fence 在同一 attachment revision first-wins。

反向竞态也必须封闭：Bind/Unbind gate acquire检查 RecallGate absent；五类 Calibration attempt 的 admission 及其 recipe/Evidence/candidate/validation/publication 可见 CAS 检查 RecallGate/attempt fence absent。Binding `Held` 或任一 Calibration Workspace CAS 若先线性化，Recall Gating 必须因 revision 冲突失败并重新读取，不得用旧快照继续；Recall fence 先胜时，后到操作在外部副作用或 Workspace CAS 前拒绝。

同时记录旧 RunIntent/descriptor/routing rollback snapshot。CAS 冲突写 `RejectedRevisionConflictBeforeDrain`；Gate 不是首次创建恢复根。

#### 阶段 4：停止并排空旧运行（`StopAndDrain`）

对旧 generation 的精确 Initiation 执行 Stop/Abort，给 queued AdvanceEvent/evidence 明确 disposition，并继续消费已接纳 processing/ResultCommit。

已被 Recall fence 覆盖的 CalibrationAttempt 不能统一按 Evidence 收口，而必须按冻结 kind 执行[D4C 的 kind-specific disposition](./04C-校准工作流.md#召回期间按校准尝试类型收口)：

- Prepare：未发生外部副作用时写 no-side-effect receipt；否则收口 recipe/resource candidate 并写 source-zero cleanup/transfer receipt。
- Capture：Stop/排空已接纳 Run 与 ResultCommit；Evidence install 先胜时保留 install receipt，fence 先胜时写 no-install disposition，把 candidate 转 Historical/detached owner 或释放。
- Solve：停止或等待纯计算结束，不发布 candidate，写 candidate cleanup/transfer receipt。
- Verify：不推进 verification outcome，收口 check/validation report 并写 validation cleanup/transfer receipt。
- Publish：未调 Repository 时证明 no-request；已知 decision 时按原 receipt cleanup；decision unknown 时必须把未决 publication 及本地资源 source-zero 转给首次请求前已 durable 的 `CalibrationPublicationRecoveryRecord`，Recall 不等远端最终决定，也不创建新的恢复责任方。

若恢复同时看到 install receipt 与 fence receipt，按 attachment revision 验证 first-wins：install 较早表示原 Gating 不应成功，必须回到 Gating conflict并重做候选验证；同 revision 双赢则进入 ledger fault。attempt cleanup/terminal完成前不得移除 fence。

等待全部 WorkSet/CompletionFence。控制失败进入 rollback，不跳过 drain。

#### 阶段 5：等待旧完成栅栏（`AwaitingOldFence`）

等待每个旧 record 满足 InitiationPin=0、child Lease=0、resultCommitInFlight=0，且 terminal slot 已消费。Recall-fenced CalibrationAttempt 则按 kind 判定，不得一律查 Evidence：

| Attempt kind | `AwaitingOldFence` 必须看到的 durable 证明 |
| --- | --- |
| Prepare | `PrepareNoSideEffectReceipt + all reserved slots Unused`，或 `PrepareCandidateCleanupReceipt{sourceResponsibility=0}` |
| Capture | `CalibrationEvidenceInstalledReceipt` 在 fence 前先胜，或 `CaptureNoEvidenceDispositionReceipt{sourceResponsibility=0}`；已接纳 Run/ResultCommit 已 terminal |
| Solve | `SolveCandidateCleanupReceipt{sourceResponsibility=0}` |
| Verify | `VerifyValidationCleanupReceipt{sourceResponsibility=0}` |
| Publish | no-request/known-decision cleanup receipt，或指向既有 PublicationRecovery 的 `PublicationResponsibilityTransferredReceipt{sourceAttemptOwnerCount=0}` |

上表证明齐全、attempt owner ledger 归零、Ticket/terminal 已发布且 attachment fence 可释放后，该 attempt 才离开 `AwaitingOldFence`。Publish unknown 在 source-zero transfer 后即满足旧 generation fence；后续 recovery 可以独立消歧，但无权越过 SessionGeneration/Workspace revision 把结果回写到 Recall 后的 Workspace。

满足后进入 FinalCAS。deadline 由明确 Abort/Host 隔离收口，不能假定为空。

#### 阶段 6：最终比较并交换（`FinalCAS`）

再次匹配以下守卫：

- gate owner；
- `InstrumentSessionId + old SessionGeneration`；
- expected revisions；
- `Lifecycle=Open + unchanged ClosingEpoch`；
- 全部 fence；
- candidate hash/资源。

单一 Application 事务替换 WorkingSet/LoadedRecallSetRef/routing，并同时完成：

- target pin→LoadedBaselineRetentionPin；
- 仅 Bound/其他真实引用的 candidate pins 及其 verified lineage→WorkingSet；
- 释放旧 baseline/current/resource pins；
- 为 MissingUnresolved 发布不可 Prepare 的 Unresolved slot；
- 退役旧 record，并递增 SessionGeneration。

成功后，旧 Handle 只移给 cleanup owner。CAS 失败时，旧 descriptor/record/pins 不变；释放新 pins 并 rollback。

#### 阶段 7：重新开放运行准入（`Reopen`）

CAS `Lifecycle=Open + unchanged ClosingEpoch` 后打开新 generation ingress。默认 `DesiredRunState=Ready`，不自动恢复旧 Initiation；拒绝所有旧 generation late event。

操作结果、迟到事件与清理结果写入召回最终状态后，才释放准入门。后续设备预备使用独立的操作和凭证；关闭已经开始时禁止重新打开。

### 9.3.3 设置召回失败、会话关闭、恢复与退役（`Recall` / `Close`）

Recall/Close 都由 InstrumentSession command executor 单写。

- Recall FinalCAS 先提交：Close 观察新的 generation，并把 Recall 记为 `AppliedBeforeClose`。
- Close 先 CAS 推进 `ClosingEpoch`：同一事务把 RecallGate、target/candidate pins、旧运行 cleanup claim 和所有待释放责任转给 Close owner；Recall terminal 为 `CancelledByClose`。

后一个分支仍完成已开始的 drain/Handle cleanup，但绝不执行 FinalCAS、rollback resume 或 Reopen。Close 对接管资源逐项写 stable receipt，因而不会让候选 pin 留在无人负责的中间态。

Recall 的崩溃恢复以 durable `RecallTransitionJournal` 为准，不依赖旧进程内 gate。

它至少保存 `StagingPrepared → Staged → Gated → FinalCommitted | RolledBack | CancelledByClose → CleanupDone`、完整 RecallOperationIdentity、reserved budget、old/candidate WorkingSet 与 baseline refs/hash、SessionGeneration/SaveGeneration/ClosingEpoch、target/candidate/grandfather pin及CatalogAdmissionLineage receipt ledger、受影响 deployment/routing cleanup claims 和 product-CAS receipt。

journal在首枚pin前已经fsync，进入Gate只推进状态；FinalCAS 与 `FinalCommitted + product-CAS receipt` 在同一 Application state transaction 提交。

启动必须在新Recall/Session/校准 admission与物理回收前扫描所有未退役 Recall journal 及其冻结的 CalibrationAttempt journal：先逐个决议`PinAcquirePending`，以完整PinAcquisitionIdentity查询Repository，并重新验证lineage receipt链与exact ref；`StagingPrepared/Staged`没有产品commit时再逐receipt释放已取得的target/candidate/grandfather pins、归还预留预算并写`RolledBackOrphanStaging`，不按CalSet/RecallSet ID猜owner。

对已建立 RecallFence 的 attempt，startup 先用 attachment revision 判定 Workspace CAS 或 fence 谁先胜，再严格按 Prepare/Capture/Solve/Verify/Publish 分别补 no-side-effect、Evidence、candidate、validation 或 publication transfer receipt。任一 kind 的 source ledger 未归零都不得假定 `AwaitingOldFence` 完成。Close 若与 startup/Recall 竞态，只能以同一 attachment revision 接管胜出分支和其已选定的 cleanup target，不得重建 disposition。

若产品 generation/hash 匹配 commit receipt，就只补齐新侧 pin+lineage transfer、旧 Handle/route cleanup；若无 commit receipt，旧产品快照保持权威，释放 candidate pins，隔离旧进程 capability并写 `RolledBackAfterRestart`，不假装恢复已消失的 Initiation；若 ClosingEpoch 已胜出则按 CancelledByClose 交给 Close owner。

全部 gate/pin/lineage claim/预算有稳定 receipt并写 CleanupDone 前，不开放该 Session admission，也不允许 Save completion越过 journal 中冻结的 SaveGeneration。

CleanupDone 也不是永久保留整个 Recall 候选。每条 journal/OperationTicket 携带公开可重试的 `RecallRetirableLocator`；opaque RecallOperationId 不参与排序。

全部 resource receipt 和 RecallTerminal 已 durable、requester teardown ACK 已到、且无 Close/recovery claim 后，按 bounded journal epoch 写 `RetiredRecallEpoch{InstrumentSessionId, ledgerEpoch, maxIssuedSequence, terminalDigest}` 并删除 old/candidate payload与 pin明细。协商查询窗口内重放原 terminal；

越过 watermark 返回 ReceiptExpired，不再重放 product CAS 或资源动作。启动先恢复 locator issuer/head；反复 Recall 因而只留下有界窗口和 watermark。

Recall互斥与Ticket保留必须分开测试：A尚未CleanupDone时B稳定返回RecallAlreadyInProgress；A已CleanupDone且责任归零、但A的Ticket仍处Retained查询窗口时，B必须允许创建新transition，且查询A仍返回原terminal。Ticket是否compact不能成为新Recall的业务gate。

FinalCAS 同时推进 SessionRevision/WorkingSetRevision/SessionGeneration，并把 `LoadedRecallSetRef` 设为目标 `RecallSetId/revision/hash`。只有 candidate WorkingSetContentHash 与 baseline RecallSetContentHash 相同的精确加载才 dirty=false；迁移或 Detached alteration 导致 hash 不同时，终态必须是 `AppliedWithAlterations` 且 dirty=true，不能谎报 Clean。

FinalCAS 不创建 `CandidateOwnerRecord{kind=FullPrepare}` 或新 `InstalledDeploymentRecord`：它把新 generation 的每个 slot 发布为 `Empty`，或在设备/能力不可解析时发布为带完整原因的 `Unresolved`；同时把已无 Pin/Lease 的旧 record 标记 `RetiredNoAdmission`，将其 move-only Handle 恰好一次移给有界 cleanup owner。这样新 WorkingSet 从未引用旧 registry entry，也没有“软件 CAS 伪装成设备事务”。

cleanup 若失败，Recall 已应用且设备进入 Fault/Quarantine，终态必须诚实报告 `AppliedWithRuntimeFaults`，不能回滚已提交的产品快照。

若调用方显式选择 `PrepareAfterRecall`，它只在 Recall FinalCAS 成功后，针对新 `SessionGeneration` 启动普通 `PrepareChannelUseCase`；Prepare 可逐 Channel 成功或失败，不能倒退已经应用的 Recall。兼容性 profile 如需让一个 SCPI 命令等待两阶段，必须返回声明了 Recall 与后续 Prepare scopes 的组合 ticket，并经 ZNB/SNA transcript 解禁；不得把资料未证明的“Recall 与硬件多 Channel 原子 Prepare”写成公共保证。

| Recall terminal | 产品/运行时结果 |
| --- | --- |
| Applied | 新 WorkingSet/LoadedRecallSetRef/SessionGeneration 全部发布；Deployment slot 为 Empty/Unresolved，未隐式创建 successor |
| AppliedWithAlterations | 全事务发布经显式确认的 altered WorkingSet；LoadedRecallSetRef 仍指来源 artifact，但 hash 不等，Dirty 必为 true 并保存 alteration report |
| RejectedBeforeGate / RejectedRevisionConflictBeforeDrain | 旧产品与运行态均未变；候选资源释放 |
| FailedRestored | 新 WorkingSet 未发布；旧 WorkingSet/descriptor/routing 保持，按冻结旧 intent CAS 恢复 admission；已停止的 Initiation 不伪装成原 Handle 复活 |
| FailedWithRuntimeFaults | 新 WorkingSet 未发布且不存在部分新配置；Stop/Host/旧运行恢复失败的 Channel 显式 Fault，保留逐 Channel 诊断 |
| AppliedWithRuntimeFaults | 新产品快照已发布，但旧 Handle cleanup/Host 隔离失败；新 admission 关闭，设备 Fault/Quarantine，不回滚 WorkingSet |
| AppliedBeforeClose | Recall FinalCAS 已先线性化；Close 按新 generation 正常收口，不倒退 Recall |
| CancelledByClose | Close 先推进 ClosingEpoch并接管 gate/pins/cleanup；产品候选未发布，禁止 rollback Reopen |
| RolledBackAfterRestart | 无 FinalCommitted receipt；旧产品快照仍权威，candidate 已释放，旧进程 runtime capability 不复活，后续须显式 Prepare |

### 9.3.4 会话内实时当前结果

“当前结果”是当前 `InstrumentSession + RuntimeEpoch` 内、某个结果所属对象和读取位置上的最新有效测量。它不是 `ResultArtifact`，不要求先写入 `ResultRepository`，也不从历史索引反推。历史结果、Trace Memory 和导出文件继续使用稳定持久引用，与本节的实时结果槽分开。

#### 结果槽与发布能力

Application 为每个可查询结果所属对象和读取位置维护：

```text
SessionLiveResultStore
  InstrumentSessionId + SessionGeneration + RuntimeEpoch
  bounded LiveResultBufferPool
  LiveCurrentSlot[]

LiveCurrentSlot
  expected LiveCurrentKey
  LiveOrdinalHead + HeadRevision
  optional latest LiveResultOrdinal
  optional LiveResultRef
  SlotRevision

LiveCurrentKey
  InstrumentSessionId + SessionGeneration + RuntimeEpoch
  ResultOwnerKey + ProcessingAccessPoint
  ResultCompatibilityFingerprint + NumericSchemaId

LiveResultRef
  LiveCurrentKey + LiveResultOrdinal
  bufferId + bufferGeneration
  candidateContentHash + provenanceHash

AnalysisCurrentSlot
  expected AnalysisResultKey
  optional latest AnalysisResultEnvelope
  SlotRevision

AnalysisResultKey
  InstrumentSessionId + SessionGeneration
  stable analysis owner id + exact analysis definition revision
  WorkingSetRevision + AnalysisDefinitionRevision

AnalysisResultEnvelope
  AnalysisResultKey + AnalysisEvaluationOrdinal
  AnalysisInputVersionSetDigest
  ordered input slot versions[]
  status = Determinate | Indeterminate{reason}
  value/marker/test outcome + provenanceHash
```

`ResultOwnerKey` 至少区分 ChannelStage、Measurement 和 Trace；Marker 与限值检查/纹波/带宽输出使用独立 `AnalysisResultKey`，不能伪装成一次新测量量（Measurement，例如 S11/S21）或占用测量顺序号。`ProcessingAccessPoint` 区分原始、校正后和其他具名处理位置。兼容判断不能只保存一个没有定义的 hash 名称。L5 按已安装方案形成版本化 `ResultCompatibilityDescriptor`，L7 用 [D1 §2.2.6](./01A-公共阅读规则与L0契约.md#226-通用哈希和验证边界)的业务规范编码产生指纹：

```text
ResultCompatibilityDescriptor
  descriptor schema/version
  exact ResultOwner kind + owner semantic revision
  ProcessingAccessPoint
  actual ordered AxisSchema + axis digest
  NumericSchema + quantity/representation/unit
  effective acquisition + processing plan content hashes
  calibration binding/apply decision + CompatibilityProof hash
  provider/factory conditioning fingerprint
  reference-plane/topology/port mapping
  stateful stage closure revision, when applicable
```

DisplayPane 布局、TraceDisplayBinding 样式、显示名称、Marker 位置和客户端选择不进入该 descriptor；任何影响数值、轴、校正、参考面或 state closure 的字段都必须进入。未知必需字段、descriptor version 不支持、字段缺失或重算不一致一律 fail closed。跨 L5/L7 的 golden/negative vectors要分别证明“纯布局变化保持 key”和“频率、校准、conditioning、参考面、schema 或访问点变化一定换 key”。

L7 在冻结 `RunIntentSnapshot` 时，为需要实时当前交付的输出签发 opaque `LiveCurrentCapability`。它绑定完整 key、允许的 ordinal reservation、结果大小等级、Session/Runtime 代次和 capability revision。L6 只校验并转发这枚能力，不解析 Channel、Measurement 或 Trace，也不读取 Application 当前状态。

`LiveResultOrdinal` 的唯一签发者是 `SessionLiveResultStore` 内、以 exact `LiveCurrentKey` 为键的 `LiveOrdinalHead`，不是 Initiation、Run 或 frame count。签发能力时，L7 以 expected `HeadRevision` 单调预留一个 ordinal；取消和失败只把该 ordinal记为 burned，不复用、不回退。两个并发 Initiation 即使局部计数都从 1 开始，也只能取得不同的 slot-global ordinal。新 SessionGeneration、RuntimeEpoch 或新兼容 key 建立新的 head；旧 head 只在全部 capability、reservation 和读租约归零后退役。

#### L6 端口与 L7 实现

`LiveResultPort` 接口定义在 L6，由 L7 `SessionLiveResultStoreAdapter` 实现并在组合根注入：

```text
tryReserve(LiveCurrentCapability, ResultSizeClass)
publish(LivePublishReservation,
        FrozenResultEnvelope,
        move-only ResultBufferLease)
cancel(LivePublishReservation, reason)
```

目标运行在启动硬件前调用 `tryReserve`，同时取得候选结果缓冲、终态槽和一次合并通知槽。预留失败在 target admission 阶段按冻结批次策略拒绝或跳过；不得启动硬件后等待临时扩容。

`publish` 在 L7 单写域内一次性比较完整 key、expected slot revision 和 ordinal，并原子完成槽更新与 `ResultBufferLease` 责任转移。闭集结果为：

| 结果 | 槽变化 | Run 侧责任 |
| --- | --- | --- |
| `PublishedCurrent` | ordinal 更新，slot 取得新 `LiveResultRef`，旧 ref 进入读者排空 | 同一事务归零 |
| `SupersededByNewer` | 不变 | 候选缓冲释放；正常处置 |
| `InvalidatedByControl` | 不变 | 必须匹配已提交的 Recall/Reconfigure/Close/RuntimeEpoch 围栏，候选缓冲释放 |
| `Conflict` | 不变 | 相同 key/ordinal 出现不同内容或 capability 伪造；锁存 ProtocolError |

相同 key/ordinal/ref 的重放返回原处置。较小 ordinal 永不覆盖较大 ordinal；相同 ordinal 的不同内容不能退化为“较旧结果”。

L7 具体实现依赖 L6 的端口抽象，L6 不依赖 L7 concrete。这是依赖反转，不是允许 L6 直接调用 `InstrumentSession`。

#### 产品分析输入快照与输出发布

L7 `TraceAnalysisService` 在同一个 `SessionLiveResultStore` 单写域内一次冻结：

```text
AnalysisInputSnapshotLease
  InstrumentSessionId + SessionGeneration + RuntimeEpoch
  StoreSnapshotRevision
  ordered input slots[] =
    Present{LiveCurrentKey, SlotRevision, LiveResultOrdinal, schema, content digest, immutable buffer view}
    | Missing{NoCurrent | Deleted | StaleGeneration | Incompatible}
  AnalysisInputVersionSetDigest
  lease identities + expiry
```

同一 `StoreSnapshotRevision` 只表示“这些槽在同一次存储快照中被观察”，不宣称它们来自同一次物理扫描。跨通道成员可以携带不同 Run、Sweep 和 `LiveResultOrdinal`；求值期间不得再次读取“最新值”替换其中任一成员。任一必需槽缺失时，快照仍立即完成，L6 产生 `Indeterminate`，不等待通道运行或设备重新扫描。

`TraceAnalysisService` 把冻结输入与不可变 plan 交给 L4 纯求值后，通过 L7 自己的 `publishAnalysis` 发布。一次 CAS 必须同时比较完整 `AnalysisResultKey`、当前产品对象是否存在、exact analysis definition revision、`WorkingSetRevision + AnalysisDefinitionRevision` 和 expected slot revision。闭集结果为 `PublishedCurrent | SupersededByNewer | SupersededByProductRevision | Conflict`；旧 plan lease 可以算完，但产品已删除或任一 revision 已改变时，其迟到输出只能得到 `SupersededByProductRevision`，槽修改次数为零。

产品 CAS 在同一 L7 临界区替换 plan 并使旧发布资格失效；旧 revision 的分析槽不再作为当前设置的当前判定返回。随后 `TraceAnalysisService` 对上述冻结 current 主动刷新；即使设备从未启动、通道未运行、处于 Ready 或 Held，或已经停止且没有活动测量运行任务，也无需等待硬件。刷新完成前查询返回 `Refreshing/NoCurrent`，不得把旧结果贴上新 revision 标签。输入全缺失时发布新 revision 的 `Indeterminate`。

#### 有界缓冲、读者与通知

当前槽拥有一份 `LiveResultLease`。UI、SCPI Data 查询和自动化通过 L7 查询用例取得带期限和连接配额的 `LiveResultReadLease`；它们不取得 Run lease，也不创建持久 `ResultLease`。

新结果替换旧结果后，旧缓冲在现有读者归还前处于 `RetiredWithReaders`，但产生它的 Run 已经归零。每个 Session 冻结：

```text
LiveResultRetentionPolicy
  maxSlots
  maxBuffers
  maxBytes
  maxReaderLeases
  maxReaderLeaseDuration
  maxConflatedNotifications
  maxAnalysisSlots + maxResidentAnalysisPlans
  maxAnalysisInputSnapshotLeases + maxAnalysisInputSlotsPerSnapshot
  maxTraceAnalysisWorkers + maxAnalysisRefreshQueue
  maxRetiredAnalysisOutputsWithReaders
```

通知只携 `LiveCurrentKey + SlotRevision`，相同槽的未消费通知合并；查询者再读取最新 ref。读者用尽窗口时只能等待、收到 `ResyncRequired`、取消流或断开，不能让每个 Sweep 排一条大数组消息。所有额度耗尽都在下一 target admission 前背压或拒绝，不写磁盘兜底。

#### 设置召回、重新配置、会话关闭与进程重启（`Recall` / `Reconfigure` / `Close`）

Recall FinalCAS 推进 `SessionGeneration`，Runtime 重建推进 `RuntimeEpoch`；处理方案改变则发布新的 expected `LiveCurrentKey`。三者均在 Application 单写域先关闭旧 capability admission，再原子清空或替换受影响槽，最后释放旧 slot-owned lease。Recall/Close 还必须使旧分析输入快照和 `AnalysisResultKey` 失效；进程重启从当前 WorkingSet 重建 L7 内存 plan，不复活旧 worker/lease。

普通 Configure、Bind/Unbind、Trace source 修改或 deployment install 同样遵守以下规则：

1. 先由字段级失效矩阵计算受影响的 `LiveCurrentKey` 集合；
2. 在提交产品 revision 的**同一个 L7 事务**中执行 `Keep | RekeyAndClear | InvalidateAndRemove`；
3. 让旧 capability fence、旧槽处置和新 expected key 与产品 CAS 一起生效，不能先发布新设置、稍后异步清理旧 current。

Marker/MarkerCoupling/限值检查/纹波/带宽定义提交也在同一产品 CAS 中完成。该提交会推进 `AnalysisDefinitionRevision`、替换 L7 内存 plan，并使旧分析输出资格失效；作为输入的复数迹线 current 保持不变，随后主动刷新。

仅改变 DisplayPane 布局、TraceDisplayBinding 或 `TraceAnalysisDisplayBinding.visible/style` 时：

- 两类 key 都不变；
- 不调用 L5/L4；
- 不清空复数测量结果或判定值。

围栏提交前已完成的 publish 保持其事实；围栏提交后到达的旧 capability 稳定返回 `InvalidatedByControl`。不存在 Repository ACK、ProjectionPending、apply-fence 或 projection quarantine 参与这个竞态。

实时当前结果属于进程内运行状态：

- 进程重启后槽为空，旧 `RuntimeEpoch` capability 永远失效；
- 不从 `ResultRepository.latest`、历史查询或旧 `ResultArtifact` 猜测恢复 current；
- 崩溃前的 Continuous Initiation 和默认实时 Average/Hold 状态不复活；
- startup 只需回收本进程共享内存/缓冲代次，不为 live-only 结果扫描 [D4D §9.5.5](./04D-持久化结果与恢复.md#955-持久交付的唯一提交与恢复协议)的 WAL 或 recovery record。

#### 显式保存当前结果

`SaveCurrentResult` 是独立 L7 用例，不属于原 Run 的重新打开：

1. 用 expected `LiveCurrentKey + SlotRevision` 取得一份一致 `LiveResultReadLease`；
2. 冻结候选内容、NumericSchema、完整 provenance 和新的 durable delivery identity；
3. 通过 [D4D §9.5.5](./04D-持久化结果与恢复.md#955-持久交付的唯一提交与恢复协议)的历史结果持久端口提交；
4. 持久端口已接管候选或明确拒绝后，释放 read lease；
5. 本操作用自己的 Ticket、最终执行状态和完成屏障报告结果。

历史保存失败不撤销合法 live current；历史恢复以后明确成功也不得回头改写 current 或原 Run terminal。

#### 验证

最低测试包括：

- 两个 Run 乱序完成，高 ordinal 保持 current，低 ordinal 得到 `SupersededByNewer`；
- 同 ordinal 同 ref 幂等、同 ordinal 异内容 ProtocolError；
- Recall/Reconfigure/Close 与 publish 两侧竞态，围栏后旧结果调用槽修改次数为零；
- Repository 未启动、磁盘只读或持久池耗尽时，live-only Single/Continuous 仍可更新 current；
- 慢读者占满全部 reader lease 时 RSS 有界，下一 Run 在硬件 start 前背压或拒绝；
- 24 h Continuous 中 ResultArtifact、持久 ResultLease、[D4D §9.5.5](./04D-持久化结果与恢复.md#955-持久交付的唯一提交与恢复协议)的 WAL/recovery record 和磁盘字节增量均为零；
- 重启后 current 为空，历史 latest 查询次数为零。
- 设备从未打开、通道从未运行、处于 Ready 或 Held、或已经停止且没有活动测量运行任务时修改 Marker 或三类测试定义，均以当前不可变迹线结果完成新 generation 主动刷新，硬件 start/arm/stop/prepare 调用次数均不增加；
- 跨通道联动输入使用不同 Run/Sweep/ordinal 仍形成一个冻结 `AnalysisInputVersionSetDigest`；缺失成员立即 `Indeterminate`，不等待设备；
- 产品 CAS 与 plan lease 交错：旧 lease 可完成旧 revision，CAS 后新 lease 只取得新 revision；旧 revision 或已删除 owner 的迟到发布槽修改次数为零；
- 分析 plan、输入快照、任务、刷新队列和 retired readers 在 exact budget 可完成，少一单位同步拒绝或合并，24 h 压力下 RSS 与槽数有界。

### 9.3.5 保存正常路径、引用来源链与保存基线线性化点

Save 不需要 Runtime drain。每次Save在冻结大snapshot/首次Repository调用前，先从process级`SaveRecoveryPool{maxRecords,maxSnapshotBytes,maxTempBytes,maxUnknown,maxLineageClaims}`预留最坏record+snapshot/temp+pin/lineage/Close-registration slice；pool满就不创建operation、不做文件I/O并返回ResourceExhausted。

Session随后分配单调SaveGeneration，并分配三个正交 identity：业务 `SaveOperationIdentity`、Repository `PublicationOperationIdentity`以及 caller-side `SaveRecoveryIdentity{SaveRecoveryId, SaveRecoveryRetirableLocator}`。locator 是 recovery identity 的必选部分，不得在故障后补发或由 SaveOperationId 推导。

之后冻结`InstrumentSessionId + SessionGeneration + StartSessionRevision + WorkingSetRevision + WorkingSetContentHash + previous baseline ref + Lifecycle=Open + ClosingEpoch`，并对snapshot内每个`Bound`冻结 `ChannelId + exact BindingRevision + ExactCalSetRef + source BindingPinId/pinRevision + CatalogAdmissionLineageReceipt`。完整 snapshot/request 先写入下节的独立 `SaveRecoveryRecord`，该 record durable 前不得取得 pin/lineage claim、写 temp artifact 或调用 Repository。

不能只保存可伪造的binding payload。若某Bound仍只有permit临时pin或`BindingPinTransferClaim`、尚无稳定binding pin+lineage，Save必须在冻结前等待该Bind mandatory fence，或稳定返回`BindingProtectionNotStabilized`，不得把pending permit当grandfather来源。

canonical semantic repository request及`semanticRequestHash`除candidate hash、expected repository revision和语义选项外，还必须覆盖按Channel/exact ref规范排序的`BindingRevision + source pin revision + CatalogAdmissionLineage proof digest`；`fullOperationEnvelopeHash`再绑定完整 PublicationOperationIdentity 与 SaveRecoveryIdentity。

由此同identity重试不能换一条资格链，完成冻结后才允许写临时对象并请求Repository publication。

若 exact ref 已经 tombstone，Repository 只有在同一 lineage-issuance 决策中证明以下条件后，才可 create-if-absent grandfather 记录：

- 源 binding pin 仍为 `Live@expected pinRevision`；
- 其 owner tuple 与冻结的 `ChannelId + BindingRevision + ExactCalSetRef` 完全一致；
- CatalogAdmissionLineage 每跳签名、receipt、exact ref 均可验证；
- 最终根的 tag 只能是 `VisiblePermitRoot | PreDeletePublicationRoot`，且 `CatalogAdmissionLineageRoot.CatalogAdmissionOrder < TombstoneOrder`。

创建内容为 `GrandfatheredSaveOutgoingPin{PublicationOperationIdentity, RecallSet candidate hash, exact ref, source pin/BindingRevision, lineage root digest}` 和新的 `CatalogAdmissionLineageReceipt{parent receipt}`。

该decision在源pin上安装有界`GrandfatheredSaveSourceClaim`，使并发Unbind/rebind cleanup只能等其publication/no-commit receipt后释放源pin；源binding pin本身始终留给WorkingSet/cleanup owner，绝不move给RecallSet。Repository原子发布RecallSet revision时把这枚outgoing pin与lineage receipt一并持久化；若publication明确NoCommit则释放claim/pin。

Visible ref也把已验证lineage随普通outgoing pin登记。任一pin不live、BindingRevision/exact ref不匹配、根不早于tombstone、链缺失/篡改，整次Save在发布前失败，不能把import/altered/伪造ref洗成grandfather资格。

Repository 成功后，baseline CAS 要求 InstrumentSessionId/SessionGeneration 未被 Recall 替换、Lifecycle/ClosingEpoch 未变、没有更新的 Save 已提交，且没有更晚 RecallGate。它不要求当前 WorkingSetRevision/hash 仍等于被保存快照。

CAS 成功时，在同一 pin-transfer 协议中把 operation pin 转为 LoadedBaselineRetentionPin、释放旧 baseline pin，更新 LoadedRecallSetRef，并只推进 SessionRevision；并发普通编辑仍保留，并据 hash 派生 Dirty。

若更新 Save/Recall/Close 抢先，operation pin 转普通 retention，artifact 及其 outgoing lineage 仍保留，并返回 SavedArtifactDetached；不得倒退 baseline。

### 9.3.6 设置保存失败、恢复与退役（`Save`）

业务 Save journal 和 recovery record 是两个可独立枚举、独立退役的 durable owner，不是同一条记录的两个名字。前者拥有 Session baseline CAS、业务 Ticket 与未转移的 attempt 资源；后者从首次 Repository 请求前就拥有 publication decision recovery 根，并在 detach 后成为唯一的资源、cleanup 和 terminal-delivery owner。

每次 Save 在任何 publication/lineage 调用前先写业务 journal：

```text
SaveTransitionJournal
  SaveOperationIdentity + PublicationOperationIdentity + SaveRecoveryIdentity
  SaveGeneration + SaveAttemptAttachmentRevision
  ExpectedLifecycle + ClosingEpoch
  exact WorkingSet snapshot ref/hash + recovery payload digest
  per-Bound frozen ChannelId + BindingRevision + ExactCalSetRef
  source BindingPinId + pinRevision + CatalogAdmissionLineageReceipt
  previousBaselineRef
  attempt-owned resource ledger + expected owner revisions
  business terminal/baseline/cleanup/transfer receipts
  state
```

随后用预先签发的 recovery identity 写入独立、自包含的 recovery record：

```text
SaveRecoveryRecord
  complete SaveRecoveryIdentity{SaveRecoveryId, SaveRecoveryRetirableLocator}
  SaveOperationIdentity + PublicationOperationIdentity + SaveGeneration
  InstrumentSessionId + SessionGeneration + StartSessionRevision + WorkingSetRevision
  exact WorkingSet snapshot bytes/ref + WorkingSetContentHash + schema/integrity hash
  previous baseline ref + frozen per-Bound exact refs
  source BindingPin identities/revisions + complete lineage proofs/digests
  canonical semantic Repository request + expected repository revision
  semanticRequestHash + fullOperationEnvelopeHash
  SavedArtifact candidate/temp refs + operation/outgoing pin manifest
  lineage pending/source-claim manifest + exact owner revisions
  reserved records/snapshot/temp/pin/lineage/cleanup/Close bytes
  resourceOwnerLedger{item, currentOwnerRef, ownerRevision, disposition}
  repositoryRequesterClaim = SaveRecoveryIdentity
  attemptAttachment{SaveOperationIdentity, SaveAttemptAttachmentRevision}
  ProcessInstanceId + OwnerEpoch + recoveryOwnerRevision
  resolutionDeadline + state + receipts + optional immutable resolution terminal
```

这份 record 必须在首次 Repository 调用前 fsync，它所含 snapshot、request、pins/lineage manifests、预留 bytes 和 locator 足以在源 Save journal 不存在时独立查询决定、清理并退役。`resourceOwnerLedger` 使每项资源在任一时刻只有一个 owner；在 detach 前标为 `SaveTransitionJournal@ownerRevision`的项目仍归业务 attempt，不因 target record 已存在就变成双 owner。

每次 temp/pin/lineage/publication 调用前，record 都要先写完整 pending identity、canonical request/hash、预期 owner revision 和可用的 cleanup slot，ACK 后再回填原 decision/receipt。业务 journal 只保存该 pending/receipt 的稳定 ref 和自己的 owner tag，不是第二份恢复账。

第一次 Repository 请求必须声明 `callerKind=SaveRecovery` 且 `currentRequesterOrRecoveryClaim=SaveRecoveryIdentity`。Repository 未收到请求或完全不可达不会破坏本地恢复根；已有 requester claim 时则必须与 record 中 identity 一致。SaveTransition 只能以 record 的 executor lease 代理发送/查询，不是第二个 publication owner。

#### 两个唯一责任方的闭集状态

业务 SaveTransition 状态闭集为：

```text
Staged → PreparedToSend → DecisionUnknown
                         ↘ RejectedNoCommit{VersionConflict|StorageFailure|ValidationFailure|...}
DecisionKnownCommitted → BaselineApplied | Detached | SavedArtifactDetachedByClose
DecisionUnknown → OutcomeUnknownTransferred | TransferredByClose
Staged/PreparedToSend → CancelledByClose
all business-terminal branches → CleanupDone → RetiredSaveEpoch → Compacted
```

SaveRecoveryRecord 状态闭集为：

```text
ReservedDurable → AttemptAttached/PreparedToSend → AttemptAttached/DecisionUnknown
AttemptAttached/PreparedToSend|DecisionUnknown → ResolvedCommitted | ResolvedNoCommit | ResolvedConflict
AttemptAttached/DecisionUnknown → DetachedByDeadline | DetachedByClose
DetachedByDeadline|DetachedByClose → ResolvedCommittedDetached | ResolvedNoCommit | ResolvedConflict
any owner/ledger conflict → Quarantined
resolved branches → CleanupDone → RetiredSaveRecoveryEpoch → Compacted
```

`SaveRecoveryResolutionTerminal` 也是闭集：`Committed{PublicationReceipt}`、`NoCommit`、`Conflict` 或 `Quarantined{QuarantineIdentity}`。它一旦写入不得改写；commit 是否可以进入 baseline 另由 immutable attachment/ClosingEpoch receipt 决定。Detached 后才获得的 commit 只产生 retained detached artifact 及 outgoing-pin/lineage receipts，绝不再调 baseline CAS；旧 SaveTerminal 也不从 `OutcomeUnknownTransferred/TransferredByClose` 改成成功。

已知 NACK/本地 fsync 失败进入 `RejectedNoCommit`，清 temp、按完整 pending identity 查询并释放 operation/GrandfatheredSave outgoing pin 与 source claim、归还预留 slice 并发布失败 SaveTerminal。VersionConflict 的重试必须同时创建新 SaveOperationIdentity、PublicationOperationIdentity、SaveRecoveryIdentity 和 expected revision，三个旧 terminal/decision 都不复活。

#### 期限、关闭与责任原子移交

DecisionUnknown 只用原 `PublicationOperationIdentity + semanticRequestHash + 可重算 fullOperationEnvelopeHash` 查询。deadline 与 Close 共用 recovery record 内的 `SaveAttemptAttachmentRevision`，对 `AttemptAttached → DetachedByDeadline|DetachedByClose` 做 first-wins durable CAS；两者不得各创建一份 recovery record。

胜出事务先确认 target `SaveRecoveryRecord` 已经 durable、完整 payload digest/locator 匹配，再以每项 expected owner revision 把 source journal 仍拥有的 snapshot/temp bytes、artifact/operation pins、lineage pending/source claims、cleanup slice、requester ACK 和 terminal-delivery 责任一次性 move 给该 record，并写：

`SaveRecoveryResponsibilityTransferredReceipt{source SaveOperationIdentity/attachment revision, target SaveRecoveryIdentity/recoveryOwnerRevision, PublicationOperationIdentity, targetPayloadDigest, moved resource identities/revisions, sourceResponsibility=0, targetResponsibility=1}`。

这次 source-owner transaction 是转移的唯一线性化点。target record 存在、deadline 到期、Close 已登记、executor ACK 或只有 target pointer 都不算转移。事务前崩溃仍由 source 负责；事务后只有 SaveRecoveryOwner 可取得 executor lease。ACK 丢失时双方用原 source/target identity 查询同一 receipt。

只有 transfer receipt durable 后，deadline 分支才能发布 `OutcomeUnknownTransferred{SaveRecoveryIdentity}`，Close 分支才能发布 `TransferredByClose{SaveRecoveryIdentity}`，完成业务 Ticket/Fence。CAS 失败者只读取胜者 receipt。Close 在 Repository 调用前可 `CancelledByClose`；遇 DecisionUnknown 不能伪装 known NACK。

Save baseline CAS 若先线性化，Close 观察新 baseline pin；Close 若先推进 ClosingEpoch，已知 commit 只能 `SavedArtifactDetachedByClose`。deadline/Close detach 先胜时，之后才解析出的 commit 由 recovery terminal 记录为 detached，无权绕过 attachment receipt 改 baseline。

#### 独立启动恢复

startup 在新 Save admission 与 物理回收 前分别枚举：

1. 全部未退役 `SaveTransitionJournal`、`GrandfatheredSaveLineageAcquirePending` 和 source claims；
2. 全部未退役 `SaveRecoveryRecord`，不以 source journal 是否存在为条件；
3. [D4D §9.5.4](./04D-持久化结果与恢复.md#954-反向引用发布记录与物理回收)的全部未退役 PublicationLedgerRecord 与 CatalogAdmissionLineage ledger。

恢复顺序固定：

1. 对齐 source/target attachment revision 与 transfer receipt；
2. 取得唯一 recovery executor lease；
3. 查询 Repository，并完成资源 disposition。

异常分支按下列规则收口：

- target 仍为 `ReservedDurable` 且 source 仍拥有资源时，只恢复 source，或以原 attachment CAS 补同一 transfer；
- source receipt 已证明归零而 target 状态尚未回填时，按 receipt 补成 target-owned；
- 没有 source-zero receipt 时，不得因 source 超时或看不到进程就强行接管；
- source journal 已消失且无 transfer receipt 属于 ledger fault：关闭新 Save/物理回收，并转 quarantine。

attached record 获得已知 decision 时把 receipt 交给业务 Save 完成 baseline/detached CAS；detached record 则独立写 immutable recovery terminal，并只做 detached artifact/no-commit/conflict cleanup。任何分支都不从 snapshot payload 重建 lineage，只用 record 中冻结 proof 和 pending identity 查询原 decision。

Repository 永久不可达时，DecisionUnknown record 保留在有硬上限的 pool 并以水位关闭新 Save；既有 in-flight slice 保证 Close 无需临时分配即可 first-wins transfer。

#### 最终状态、退役、压缩与过期

业务 Save journal 与 SaveRecoveryRecord 使用两个不同 locator issuer/watermark。业务 journal 的 `CleanupDone + SaveTerminal + requester teardown ACK` durable 后，仍只有两个退役分支：

- 未发生 recovery transfer：本 attempt 的 pin/lineage-claim/temp 全部有 release/retention receipt，且已取得 Repository `PublicationRetiredReceipt`；
- 已发生 recovery transfer：target SaveRecoveryRecord 的完整 identity/locator/payload 已 durable，`SaveRecoveryResponsibilityTransferredReceipt` 证明源 journal 的所有未决资源、cleanup 与 delivery 责任为零，且 target=1。

第二分支中，只有 target pointer、`ReservedDurable` 状态或一条无 source-zero 证明的 ACK 都不能写 `RetiredSaveEpoch`。源 journal 先 compact 而 target/receipt 不完整是必须隔离的 ledger fault。

SaveRecoveryRecord 只有在 resolution terminal 已 durable，snapshot/temp/pin/lineage/source-claim/bytes 全部 release 或转给自包含 quarantine successor，Repository `PublicationRetiredReceipt` 已到或完整 publication claim 已 source-zero 转移，requester/Close ACK 齐全且无 live executor/query claim 时，才能按 `SaveRecoveryRetirableLocator` 写 `RetiredSaveRecoveryEpoch`。`DecisionUnknown` 与无 successor receipt 的 `Quarantined` 绝不退役。

两类记录在各自有界 retry window 内重放原 terminal/transfer receipt；compact 只删除 payload 明细，不跨过 watermark。窗口外的完整 SaveOperationIdentity 只返回 `SaveReceiptExpired{terminalDigest}`，完整 SaveRecoveryIdentity 只返回 `SaveRecoveryReceiptExpired{terminalDigest}`，不重发请求、pin 或 lineage claim。

Repository publication decision/outgoing pins/lineage receipts或明确 NoCommit、source-claim disposition、当前 requester/recovery ACK 及无 claim 齐全后，另按 PublicationRetirableLocator 写 RetiredPublicationEpoch；窗口外完整 publication identity 只 ReceiptExpired，且不创建 revision/pin。

#### 精确故障注入

除 known NACK、VersionConflict 三 identity、pool 满和 24 h 守恒外，必须在下列每个持久化边界两侧 kill/restart：

1. SaveRecoveryIdentity/locator 签发、source journal fsync、`ReservedDurable` recovery record fsync、首枚 temp/pin/lineage pending 与首次 Repository 请求；
2. Repository requester claim、DecisionUnknown 记录、deadline 与 Close 的 attachment first-wins CAS，target payload digest 验证；
3. 每项 resource owner revision CAS、最后一项 source 归零、`SaveRecoveryResponsibilityTransferredReceipt` fsync/ACK、target-owned 回填；
4. `OutcomeUnknownTransferred|TransferredByClose` SaveTerminal、业务 CompletionFence/CleanupDone、RetiredSaveEpoch、source compact；
5. recovery 重启 executor lease、Repository 决定查询、immutable resolution terminal、outgoing-pin/lineage/source-claim disposition、snapshot/temp/bytes cleanup；
6. PublicationRetiredReceipt 或 quarantine transfer、RetiredSaveRecoveryEpoch、recovery compact、retry-window watermark 与两类 Expired 返回。

每个注入点都要断言：只有一个 publication identity/requester claim；每项资源 owner 计数始终为 1 或已有唯一 release receipt；没有 source-zero receipt 时源不退役；detach 后 commit 只成为 detached artifact；业务、recovery 和 Repository 三类 ledger 按任意顺序退役/compact 都不丢 identity/request 且最终有界。



### 9.3.7 设置保存与召回验证（`Save` / `Recall`）

- 首枚target/candidate/grandfather pin前kill
- 每枚pin/lineage claim取得与journal两侧kill
- `StagingPrepared/Staged` orphan重启释放和pool耗尽
- hash/schema/迁移/断引用
- TraceDisplayBinding 冲突
- 任一 Channel dry-run 失败的全事务回滚
- 设备/能力缺失形成 Unresolved
- Recall 期间零 Hardware Prepare
- WaitingForAdvance Pin
- processing/ResultCommit 在途
- old fence exact/少一个计数
- Prepare/Capture/Solve/Verify/Publish 五类 admission 与 RecallFence 在同一 attachment revision first-wins
- 五类 Workspace/外部副作用 CAS 先胜导致 Recall 重试，以及 RecallFence 先胜后迟到 CAS 稳定拒绝
- Prepare no-side-effect/candidate cleanup、Capture Evidence/no-install、Solve candidate cleanup、Verify validation cleanup 分别缺一张 receipt 时 `AwaitingOldFence` 不得通过
- Publish unknown 在围栏后只能 source-zero 转给已有 PublicationRecovery，不等远端终态也不新建 owner
- 在 RecallFence CAS、每类 disposition、source-zero transfer、AttemptTerminal、fence release 与 `AwaitingOldFence → FinalCAS` 两侧 kill/startup
- Recall×Close×startup 仅有一个 attachment 胜者，败者只读原 cleanup target/receipt
- Stop/Recall/Close/CAS 竞态
- late old-generation Frame/Result/terminal 隔离
- 旧结果历史查询不串入会话实时当前结果
- RuntimeProjection 不扰动 Recall CAS
- 旧 Handle cleanup 失败
- 显式 PrepareAfterRecall 失败不回滚 WorkingSet
- Save 时并发编辑后 baseline 更新但 Dirty
- 更新 Save/Recall 导致 SavedArtifactDetached
- Repository 响应丢失幂等重试，以及终态后 Gate/Pin/Lease/Credit/RecallRecoveryPool 全归零。

必须有两组独立端到端用例：

- 正例：`Bound→CatalogDelete→Save→Unbind→Recall` 仍成功，且 Recall 所得 binding lineage 递归回到删除前 root；
- 反例：删除后导入/altered/伪造 ref、错误 BindingRevision、已释放源 pin 或 lineage root 不早于 tombstone，都必须在 publication 前失败，不能通过 Save 再 Recall 取得 grandfather 资格。

Save×Unbind/rebind竞态还要断言：lineage issuance先胜则cleanup等待source claim且artifact可发布，pin release先胜则Save稳定NoCommit，源binding pin从不move给RecallSet。
