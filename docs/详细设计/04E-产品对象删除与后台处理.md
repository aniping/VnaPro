# 详细设计 04E：产品对象删除、目录移除与后台处理

本篇只定义产品对象删除、校准数据集从可选目录移除，以及责任移交后的后台状态查询。会话、命令、操作票据、部署和校准绑定的通用协议仍由 [D4A](./04A-应用会话与事务.md) 唯一维护。

## 阅读入口

### 30 秒摘要

- 删除不是“从容器移除一个元素”，而是冻结完整引用闭包，关闭会改变该闭包的新写入，再等待运行、部署、校准引用、迹线内存和外部地址各自安全收口。
- 删除迹线、删除测量量和删除测量通道的影响不同；只有纯显示关系可同步删除，改变处理图或采集计划时必须完成相应重绑定或通道重配置。
- 校准数据集从可选目录移除不等于物理回收。旧的合法精确引用可按来源链继续受保护，物理内容只由存储库后台回收器处理。
- 原操作把责任移交后台后，调用者通过强类型恢复身份只读查询；查询不会还原对象，也不会猜测 ZNB/SNA 厂商命令。

2. 再读 [§9.1.4](#914-校准数据集的目录移除)，分清目录移除、旧引用保护和物理回收。

## 9.1.3 产品对象删除与结果责任收口

#### 正常路径：产品对象及其引用关系删除

对象基数和删除规则属于 Application，不交给 UI 猜测。

`DisplayPane` 只拥有布局。`TraceDisplayBinding{TraceDisplayBindingId, DisplayPaneId, TraceId, placement/style revision}` 是独立引用对象，但其生命周期从属于显示窗口。

`TraceAnalysisDisplayBinding{exact TraceDisplayBinding ref, exact analysis ref, visible/style revision}` 是它的分析呈现子关系，使同一迹线可在不同窗口分别显示或隐藏测试图形。

标记、限值检查、纹波检查和带宽检查的求值定义是迹线的组成对象。标记可精确引用参考标记；`MarkerCouplingDefinition` 可按显式兼容迹线集、测量通道或显示窗口作用域联动多个标记。

迹线还可能被派生迹线引用，或以 `StoredResult` 持有精确结果引用的存储库固定引用。这些关系不能互相代替。

- 删除 DisplayPane：在同一个领域事务中自动删除其 TraceDisplayBinding 和 TraceAnalysisDisplayBinding，并在地址簿中墓碑化该窗口地址；若它是会话当前选择则清空该选择。以该 DisplayPane 为作用域的 MarkerCoupling 是产品引用：默认 `RejectIfReferenced`；显式 `CascadeDelete` 才删除这些耦合定义并热切换其成员分析计划。
- 删除迹线：自动删除它拥有的全部标记、限值检查/纹波检查/带宽检查求值定义、关联的 `TraceAnalysisDisplayBinding` 和引用它的全部 `TraceDisplayBinding`，但不删除其测量量（`Measurement`）来源；实际提交须走下述“仅处理图重绑定”路径。
- 删除 Marker：若没有参考/差值 Marker 或 MarkerCoupling 引用它，可随 owning Trace revision 原子删除；否则默认 `RejectIfReferenced`，返回按引用种类、引用者 exact identity/revision 排序的完整清单。显式 `CascadeDelete` 删除依赖该参考点的 Marker，并按下一条规则处理耦合组；不得把差值 Marker 静默改成普通 Marker，也不得改绑到同编号或同名 Marker。
- MarkerCoupling 的显式成员引用按 exact Trace/Marker revision 处理；显式级联可删除待删成员，但必须冻结删除前后有序成员摘要。按 Channel/DisplayPane 作用域派生的成员集也必须从同一 post-delete 快照确定展开，不能在提交后按“当前显示迹线”重算。任一组低于 profile 最小成员数、作用域被删或兼容规则不再满足时，级联结果是删除整个 MarkerCouplingDefinition，而不是保留半有效组或夹紧到邻近迹线。
- 产品 CAS 前，旧在途求值只使用旧冻结分析计划；新候选要么引用完整有效成员，要么删除对应定义。若旧计划的输入因既有数据质量而无效，限值检查/纹波检查/带宽检查结果只能按 [D2B §6.7](./02B-校准变换迹线与数值验证.md#67-迹线数值核心vnatracenumericcore) 写为 `Indeterminate{reason}`；删除流程不能把它改写成通过/失败，也不能用“未显示”冒充未求值。
- 若任一 DerivedTrace 直接或间接引用待删 Trace，默认 `RejectIfReferenced` 并返回按 `downstream TraceId/TraceRevision + edge` 排序的完整闭包。显式 `CascadeDelete` 必须回传同一闭包摘要，随后递归删除全部下游 Trace；跨 Channel 的下游引用同样处理，不能只检查目标 Channel。
- 每条被删 Trace 的 Marker、三类测试定义、跨迹线 MarkerCoupling 关系、显示关系、Trace Memory ResultRef/pin、结果所属键和协议地址都必须进入预览与结果。剩余 Trace DAG 与分析计划必须重新编译；不能留下断引用，也不能把 DerivedTrace 的输入或耦合成员静默改成剩余子集。

删除仍被迹线引用的测量量（`Measurement`），或删除含被引用测量量的测量通道时，V1 默认 `RejectIfReferenced`，并返回完整的“迹线身份/修订 + 来源关系 + 所属测量通道”冲突清单。只有显式 `CascadeDelete` 携带预期受影响 ID、标记、参考/差值引用、标记耦合、三类求值定义、分析显示关系、下游迹线关系与外部引用清单时，才按冻结的递归闭包删除迹线、标记、分析定义、绑定与测量量。运行时执行顺序可以分阶段，但产品对象关系只有一个最终提交点；分析图形是否可见不改变求值定义是否进入闭包。

所有产品删除还必须在同一 L7 提交中处理两项会话索引：`ProfileAddressBook` 对每个被删测量通道、测量量、迹线和显示窗口写不可复用的地址墓碑并推进一次 `AddressBookRevision`；`SessionCurrentSelection` 对指向被删对象或已失效父对象的槽写 `None` 并推进一次 `SelectionRevision`。未受影响选择保持原精确引用，绝不改绑到“最近”“最小编号”或同名对象。连接级 `ScpiSelectionContext` 仍由 L8 原样保留旧令牌；下一条消息只能得到 `ScpiSelectionTargetDeleted | ScpiSelectionStale`，L7 删除事务不得代替连接修改它。

没有标记联动作用域引用时，显示窗口（`DisplayPane`）、迹线显示绑定（`TraceDisplayBinding`）、迹线分析显示绑定（`TraceAnalysisDisplayBinding`）和纯布局/样式修改是真正的仅视图事务；可见性/样式修改不调用 L5/L4。标记、标记联动或三类求值定义的变化走下述 L7 产品分析计划替换，零 L6/L2、零停止/准备。迹线含数值来源和处理图，`DeleteTrace` 必须走 [D2C §7.6](./02C-通道编译绑定与失效.md#76-版本修订与失效传播revision) 的仅处理图重绑定；测量量决定硬件计划，`DeleteMeasurement`/对应级联走完整测量通道重配置。

##### 标记与求值定义删除：L7 产品分析计划替换

这条路径只改变产品分析消费者，不能复用 ChannelReconfigure 的运行排空。L7 先在同一 WorkingSet 快照中解析 Marker 参考/差值闭包，并把 MarkerCoupling 的 ExplicitCompatibleTraceSet、Channel 或 DisplayPane selector 展开为有序 exact Trace/Marker 成员与 selector/member-set digest。L5 只消费 exact 成员和已完成迹线输出描述，不读取 DisplayPane 或 TraceDisplayBinding。

执行合同固定为：

1. 产品副作用前，L5 纯编译不可变 `CompiledAnalysisPlan`；L7 `TraceAnalysisService` 预留 plan、输入快照、求值、输出、scratch 和旧 lease 退休额度。任一资源少一单位，删除同步拒绝，旧产品和旧 plan 都不变。
2. L7 应用单写者以 expected ProductGraph/WorkingSet revision 一次 CAS 提交冻结闭包、Marker/求值定义删除、MarkerCoupling 精确成员变化、结果键 delta，并推进 `WorkingSetRevision + AnalysisDefinitionRevision`；同一临界区使旧输出资格失效并替换 service 的 immutable plan pointer。
3. CAS 前已取得旧 `TraceAnalysisPlanLease` 的求值可完成；发布时 revision 或 owner 不匹配即稳定丢弃。CAS 后新任务只取得新 revision，并立即从 `SessionLiveResultStore` 冻结当前迹线输入主动重算；跨通道输入可来自不同 Sweep/Run/ordinal，缺失直接 `Indeterminate`。
4. 该路径不建 durable Ticket/journal，不调用 L6/L2，不 Stop、不关闭 Hardware deployment，也不等待下一次扫描。进程重启只从当前 WorkingSet 重建内存 plan，旧 worker/lease/output 不恢复。

`TraceAnalysisDisplayBinding.visible/style` 只由 L7 校验 exact TraceDisplayBinding/analysis ref 并提交关系 revision，L8 独立刷新和预算绘图资源。删除 Analysis 或 TraceDisplayBinding 时自动删除这些子关系；厂商 trace-level show/hide 由 profile 展开为当前显示绑定集合的一次原子修改。该路径不重编分析 plan，L5/L4 调用数必须为 0。

表驱动测试至少覆盖：编译失败、各类内存额度 exact 与少一单位、产品 CAS 冲突、旧 lease 与新产品 CAS 交错、停止设备后的立即刷新、跨通道不同 ordinal 的冻结输入 digest、成员缺失得到 Indeterminate、删除/重建 ABA、进程重启和连续数百次修改后的稳定水位。每例都断言 L6 调用及 Hardware Prepare/Start/Stop/Abort/InstalledDeployment admission-close 次数为 0。窗口 A 隐藏、窗口 B 显示及厂商 trace-level 批量隐藏另断言 L5/L4 调用数为 0、求值结果不变、只更新精确 TraceAnalysisDisplayBinding 集合。

任何硬件准备、`ProductMutationFence` 或运行关门之前，同一已接纳事务必须持久化操作日志、恢复/隔离目标、完整身份/定位信息、预留、操作凭证/完成屏障和最坏资源切片。任一项不足就在零副作用时拒绝；`PreparedTarget` 在责任原子移交（source-zero/target-one）完成前，不拥有候选、Handle、围栏或清理责任。

执行顺序固定为：

1. 在没有产品副作用时构造全部受影响测量通道的新修订候选，并递归验证迹线有向无环图、标记参考/差值、标记耦合、三类求值定义、分析显示关系、协议地址、会话当前选择和迹线内存外部引用。删除迹线时只编译 `RebindCandidate`，不调用 L2；删除测量量后仍有 `1..N` 个有效测量量定义的通道，用各自预建子身份完成硬件准备候选；变为 0 时写 `NoPrepareRequired`。若删除后可路由目标集合变化，还要离线编译待发布路由计划；
2. 候选已可安装后，执行以下动作：
   - 先用 ReconfigureAttachmentRevision 只选出唯一执行责任方；
   - 再以 ExpectedProductGraphRevision、完整受影响集合摘要和 scoped write set，在 L7 `ProductMutationGateRegistry` 安装 `ProductMutationFence{operation=ChannelReconfigure}`；
   - 同一事务关闭受影响 binding/ResultRef 的新 Save/publication source-claim admission，并冻结已接纳 claim/Save identity；
   - 围栏必须覆盖跨 Channel Trace edge、Marker 参考/差值、MarkerCoupling 的作用域与成员、三类求值定义、TraceDisplayBinding/TraceAnalysisDisplayBinding、地址项、会话选择、外部 ResultRef 引用和 routing relation。

   围栏 CAS 与 revision/集合比较不命中时尚未关闭任何运行入口，稳定返回 `ReconfigureFailedNoProductChange`；
3. 只有围栏回执持久化后，才按测量通道 ID 升序关闭旧测量运行任务：
   - 路由闭包为空的通道，由本操作按每项预期运行意图修订/声明修订取得 `SuccessorClaimReceipt` 和 `OldParentRuntimeDrainReceipt`；
   - 路由闭包非空的通道，把声明的唯一责任方冻结为下一步的 `RoutingHandoffIdentity`，本操作不另签声明；
   - 回执持久化前崩溃时，只接受 [D3B 运行排空协议](./03B-测量生命周期与完成.md)绑定原声明、父任务、冻结集合，以及 bootstrap 的旧进程终止、软件围栏和物理状态处置联合证据的 `PriorProcessIsolationNoOldParentEvidence`。它不是新运行周期重建的声明或回执；
4. 若路由闭包非空，以预建 `RoutingHandoffIdentity` 进入 [D3C §8.5.5](./03C-触发多通道调度与验证.md#855-运行中路由切换routing-handoff)的关门阶段，并成为这些通道的唯一后继声明责任方。旧快照被排空或标记为待 `CancelledReconfigured`；门内每份证据已由唯一账本/资源额度责任方接管，剩余通道的待发布后继已就绪。只有 `RoutingHandoffJournal@Gating` 的预期日志修订、待发布计划及哈希、逐绑定代次、后继声明/旧父任务排空回执和完整逐证据账本摘要全部精确匹配时，才能继续；逐份证据的最终处置仍由移交终态后的清理屏障证明；
5. 每个受影响 Channel 都已有旧父 drain/no-old-parent 回执后，才对其精确 InstalledDeployment record 取得 `InstalledDeploymentAdmissionClosedReceipt + InstalledDeploymentPinLeaseDrainReceipt`。默认让已接纳工作完成当前逻辑测量单位后 Stop，deadline 后才 Abort；Continuous 不得在旧 revision 上创建下一目标批次；
6. 最终 L7 产品与安装事务同时验证全部旧修订、当前责任方、各重配置代次、活动产品写入围栏、逐通道运行与部署关门回执、候选回执，以及地址、选择、外部引用和路由闭包。事务一次完成：
   - 删除冻结的迹线、标记、限值检查/纹波检查/带宽检查求值定义、`TraceDisplayBinding`、`TraceAnalysisDisplayBinding` 和测量量，按冻结计划删除或推进 `MarkerCouplingRevision`，发布全部新 `ChannelRevision`；
   - 写地址墓碑、清空失效会话选择，把待释放的 Trace Memory 保护责任从 WorkingSet 移给本操作，失效旧实时结果键，并安装新描述符或已准备句柄；
   - 路由闭包非空时，同时成为 [D3C 路由移交协议](./03C-触发多通道调度与验证.md#855-运行中路由切换routing-handoff)的产品提交点，发布预备路由并推进 RoutingRevision 与 BindingGeneration；
   - 写 `ProductMutationFenceReleasedReceipt{ChannelReconfigureCommitReceipt,...}`。只改处理图的通道复用旧生效计划；采集变化安装新 Handle；零测量量时发布 `ConfiguredNoRunnableMeasurement`。
7. 旧 immutable revision、旧 deployment、旧实时 reader和历史/工作流交付按原 pin/lease/计划收口。Repository cleanup 只能在 final CAS 已把外部 pin 责任移出 WorkingSet 后，以稳定 identity 释放；若该源 pin 上已有先胜的 Save/publication source claim，先等待其 publication/no-commit receipt，不能提前释放。routing handoff 还要完成旧 snapshot、逐 evidence、claim/queue Credit 清理。新 admission 只有在每个受影响 Channel 的稳定 terminal 与 routing terminal（如适用）都 durable 后开放；
8. 产品写入围栏或任一运行关门回执一旦提交，旧入口永不重新打开。此后遵守三条固定规则：
   - 最终提交冲突、崩溃或后续失败只能继续同一操作，或凭“目标已持久、来源已归零”的回执转给后台处理、关闭或隔离；不得再写 `ReconfigureFailedNoProductChange`；
   - 关闭、重试、超时和启动恢复只用 `ReconfigureAttachmentRevision` 竞争执行责任。接管者沿用同一产品围栏、后继申领、关门和路由身份及已有回执，不重建候选、不重复准备或安装，也不把责任方切换修订当成 L6/L7 准入修订；
   - 操作终态为 `TraceProcessingRebound | Installed | ConfiguredNoRunnableMeasurement | ReconfigureFailedNoProductChange | TransferredToRecovery | CancelledByClose`。完成围栏还要等待旧工作与句柄、迹线内存保护、路由、结果键清理和请求者交付，随后才按定位信息退役记录。

状态边界因此只有两段：`CandidateBuilding → ReconfigureFailedNoProductChange` 属于零关门副作用；`ProductMutationFenced → RuntimeClosing → DeploymentAdmissionClosed → Installing → Installed/Configured/Transferred/CancelledByClose` 属于不可回开段。第二段若无法完成或移交，只能保持有界 quarantine 并关闭该 Channel 的产品/运行入口，不能伪造“配置没变所以可继续运行”。

转后台时，附着关系、`ProductMutationFence` 的唯一责任和完整责任账本必须在一个本地事务中完成责任原子移交：

- 操作来源责任清空；
- 预建恢复目标成为唯一责任方；
- 预留进入 `Begun`；
- 写 `ChannelReconfigureResponsibilityTransferredReceipt`。

已经释放的围栏只作为证据，不得复活。只有该回执持久化后，原操作凭证才能写 `TransferredToRecovery{ChannelReconfigureRecoveryIdentity}`。

恢复记录只能收口为 `TraceProcessingRebound | Installed | ConfiguredNoRunnableMeasurement | TransferredToClose | TransferredToSuccessor | Quarantined`。每个结论都要有对应的最终 CAS 或移交回执，不能根据当前配置外观猜测。

资源状态闭集与另外两类后台处理一致，但身份不能混用：

1. 预留记录只有 `ReservedBeforeNeed → Begun | Unused`。
2. 恢复记录的主路径只有 `PreparedTarget → Owned → Resolving → ResolvedTraceProcessingRebound | ResolvedInstalled | ResolvedConfiguredNoRunnableMeasurement | ResolvedToClose | ResolvedToSuccessor | ResolvedToQuarantine → CleanupDone → Retired`；未命中恢复目标时只能走 `PreparedTarget → UnusedTarget → CleanupDone → Retired`。
3. 正常安装/仅配置完成、围栏前 `ReconfigureFailedNoProductChange`，或没有发生责任移交的关闭，必须在同一事实事务写 `reservation=Unused`、`target=UnusedTarget` 和唯一切片释放回执。
4. 只有责任移交胜出时才写 `Begun/Owned`；该切片此后只能由恢复记录或经责任原子移交取得责任的后继释放。

**隔离前置。** 到达 `recoveryResolutionDeadline` 后，如果仍不能证明最终安装、Handle/宿主结果，或外部组件已永久不可达，恢复流程不得继续停在 `Resolving`。

**移交动作。** 恢复流程把活动的 `ProductMutationFence`、原 `SuccessorClaim`、候选/Handle/宿主声明、全部截止/排空/清理责任和剩余资源额度，原子移入预建隔离记录。移交回执固定为 `ChannelReconfigureQuarantineTransferReceipt{source recovery identity/revision, target quarantine identity/revision, exact owner-ledger/affected-set digest, sourceResponsibility=0, targetResponsibility=1}`。

**成功结果。** 回执提交后，恢复记录进入 `ResolvedToQuarantine`；隔离记录保持该测量通道的产品修改与运行准入关闭。

**后续恢复。** 只有显式修复，或再次通过责任原子移交把责任交给关闭/后继流程，才能解除该约束。不得为了释放容量丢弃围栏或 Handle；状态查询和记录退役必须等待活动隔离引用最终释放。

容量门禁分别对 operation/recovery/quarantine records、candidate/Handle claim bytes、owner-ledger、transfer/Close/successor 和 terminal-delivery slots 做 exact/少一单位测试；任一少一必须在首次 Hardware Prepare/ProductMutationFence 前拒绝。连续成功、围栏前失败、转后台、Close、quarantine、startup、retirement/compact 循环中，除真实 live quarantine root 外，各池高水位只能围绕配置窗口波动，不能随 DeleteTrace/DeleteMeasurement 次数线性增长。

startup 在开放该 Channel 的产品写、Prepare 或运行准入前枚举全部未退役 reconfigure operation/recovery/quarantine records，并按原 operation/claim/close identity 查询已有回执。operation 与 recovery 分别按自己的 retirable locator 推进 watermark；resolution terminal、ownerLedger=0 或稳定后继 transfer、requester ACK 与 slice release 齐全前不得 compact。窗口外只返回 `ChannelReconfigureRecoveryReceiptExpired{terminalDigest}`，不重做 Prepare、关门或 install CAS。

这条复合操作的 Handle 所有权、child install CAS 和 cleanup 回执复用 [D4A 持久操作责任交接中的 DeploymentInstall 协议](./04A-应用会话与事务.md#持久操作的责任交接)，产品候选复用 [D4A §9.2 原子设置事务](./04A-应用会话与事务.md#92-事务与撤销undo)，但 composite identity/journal/attachment 只由本节拥有。任何实现若在旧 deployment 仍可接纳工作时直接删 Trace/Measurement，必须在门禁中失败。

校准数据集不复用这条级联删除规则。`CatalogDeleteCalSet` 是公开应用用例：它允许仍有旧精确引用时先写目录墓碑，阻止新绑定。物理回收不属于公开命令；它只能由 [D4D §9.5.4 的存储库后台回收器](./04D-持久化结果与恢复.md#954-反向引用发布记录与物理回收)在所有保护引用归零后执行。

普通空闲 Channel 通常仍有 Ready deployment，因此 V1 `DeleteChannel` 是明确的异步流程，而不是要求用户调用不存在的“取消准备”。预览必须来自一份一致的 `ChannelDeleteImpactSnapshot`，并向调用者返回规范化影响对象清单及其摘要；请求没有回传同一摘要，或显式级联清单与该快照不一致时，不创建操作。

`canonicalAffectedObjects` 的范围固定如下：

- 对象：待删的测量通道、测量量（`Measurement`）、迹线、标记、标记耦合、限值检查、纹波检查、带宽检查、`TraceDisplayBinding` 和 `TraceAnalysisDisplayBinding`。
- 关系：迹线归属、递归下游迹线、测量量来源、迹线引用、标记参考/差值、耦合作用域/成员，以及显示、路由、地址和选择关系。
- 结果：由上述对象派生的 `ResultOwnerKey/LiveCurrentKey`。

删除 Channel 时，无论 Trace source 判别分支为何，都必须包含该 Channel 拥有的全部 Trace、Marker、三类求值定义和分析显示子关系，并包含跨迹线耦合关系的删除前后成员摘要。外部 ResultRef pin 和校准 binding protection 以自己的 exact identity/revision 进入同一摘要，实际资源处置仍放在 cleanup plan/ownerLedger。全体条目按稳定的 kind、identity、revision、relation 排序；输入顺序不同但集合相同，摘要必须相同。

路由引用必须按配置语义展开，不能只搜索 `channelIds[]` 字段：

1. `TriggerOwnerKey=Channel`、通道序列成员边、`BoundChannel/ExplicitSet`、`ChannelDispatchOrderSnapshot`，以及会随可运行通道集合变化的 `AllEligible/NextEligible`，都属于影响闭包。
2. 默认 `RejectIfReferenced` 对显式责任作用域、目标和序列引用返回完整冲突清单。
3. 显式 `CascadeDelete` 必须携带同一 `RoutingAffectedSetDigest`，并采用确定性差量：删除由目标通道拥有的来源绑定；从显式集合、序列和派发顺序中移除该通道；集合因此为空的绑定一并删除；对 `AllEligible/NextEligible` 重新计算剩余目标。
4. 任何语义改变都推进对应 `BindingGeneration`，整份配置推进一次 `RoutingRevision`，并且必须通过 [D3C 路由移交事务](./03C-触发多通道调度与验证.md#855-运行中路由切换routing-handoff)发布，不能原地修改活动订阅。

地址与选择策略也不允许由适配器猜测。删除事务对被删 Channel 及其所有子对象写 exact `AddressTombstone`，同一 SessionGeneration 内不得复用号码；会话当前选择凡指向被删对象或无效父对象都明确变为 `None`。`ScpiSelectionContext` 不在影响集合、围栏或写集内，因为它是 L8 连接级易失状态；旧 token 的下一次解析按 [D5A 外部适配器协议](./05A-外部适配器.md)返回 target-deleted/stale。

`TraceAnalysisDisplayBinding` 默认不是独立 SCPI 地址对象，删除或改 visible/style 不得误删 Trace/DisplayPane 地址，也不推进 AddressBookRevision。若某 profile 显式把分析显示关系导出为可寻址对象，其 exact AddressEntry/墓碑必须进入同一影响摘要；厂商 trace-level show/hide 仍由 L7 展开为绑定集合，不能由 L8 临时搜索窗口后逐个写入。

运行时工作、部署和计划交付义务身份另存于冻结清理计划与责任账本（`ownerLedger`），不属于 `AffectedSetDigest`。它们在排空中从待处理变成稳定处置是正常进展，不算影响集合缩小；只有产品对象、引用边或责任方/键成员关系变化才触发影响集合冲突。预览是只读信息，不是锁，真正的并发围栏在下述准入事务中建立。

产品对象关系写围栏由 L7 单一产品事务协调器拥有，并保存在每个会话一份的登记表中：

```text

  key = InstrumentSessionId + SessionGeneration
  ProductMutationGateRevision
  activeFences[]

ProductMutationFenceRecord
  complete ProductMutationFenceIdentity
    { ProductMutationFenceId, ProductMutationFenceRetirableLocator }
  operation = ChannelDelete { complete ChannelDeleteOperationIdentity }
            | ChannelReconfigure { complete ChannelReconfigureOperationIdentity }
  ExpectedProductGraphRevision + AffectedSetDigest
  protectedObjectIds[] + protectedRelationKeys[] + protectedResultOwnerKeys[]
  protectedRoutingKeys[] + protectedAddressKeys[] + protectedSelectionKeys[]
  protectedBindingKeys[] + protectedExternalReferenceKeys[]
  owner = Attempt | Recovery | Close | Successor | Quarantine
  ownerIdentity + ownerRevision
  state = Active | Released
  optional releaseReceipt
```

所有产品对象关系写命令都只能经该协调器提交，并在一个事务中 CAS `ProductGraphRevision + ProductMutationGateRevision`。命令先把自身写集合规范化为：

- 对象 ID 与关系端点；
- 结果所属键；
- 路由、地址与选择键；
- 绑定键与外部引用键。

若写集合与任一活动围栏相交，或会改变受保护测量通道的引用闭包，就在副作用前返回 `ProductMutationFenced`。通道删除、通道重配置、路由移交、绑定/解绑、地址重排和当前选择更新都遵守同一重叠判断。

两个操作只在保护集合不相交时可同时拥有活动围栏。后一个操作因全局修订前进而快照过期时必须重新预览；新预览证明闭包不相交后可以接纳。相交时，后一个操作在首次副作用前冲突；无关通道不因另一条围栏被拒绝。

围栏责任移交必须在登记表和责任账本的同一事务中，以预期责任方修订/围栏修订完成，并写 `ProductMutationFenceOwnershipTransferredReceipt{source=0, target=1, before/after gate revision, AffectedSetDigest}`；不能复制活动记录。

围栏释放规则如下：

- 通道删除只在产品/实时结果存储 CAS 的同一事务中，以 `ProductDeleteReceipt` 释放围栏；
- 通道重配置只在产品/安装 CAS 的同一事务中，以 `ChannelReconfigureCommitReceipt` 释放围栏；
- 两者统一写 `ProductMutationFenceReleasedReceipt{commitReceiptRef, before/after gate revision, final ProductGraphRevision}`；
- 会话关闭只能凭完整 `SessionClosedCleanupReceipt` 释放。

隔离记录仍是活动围栏的唯一责任方，不能为了释放配额而开门。

启动恢复必须先枚举这张登记表再开放产品写入：每条活动围栏恰有一个可枚举责任方；已释放记录有唯一释放回执；责任账本与围栏修订必须相互匹配。孤儿围栏、双责任方、无回执的已释放记录或重叠的活动围栏，一律关闭相关会话的产品修改。已释放明细只在操作/恢复查询窗口结束、请求方确认齐全且所有引用归零后按定位信息退役；窗口外只保留回执摘要，不复活围栏。

运行准入登记表、事件尚未成批时的责任、跨通道批次原子提交和截止竞态，唯一字段源见 [D3A：通道删除的运行准入截止端口](./03A-运行对象职责与端口.md#通道删除的运行准入截止端口)。本篇的 L7 删除协调器不读取或修改 L6 登记表，只负责四件事：关闭应用命令/准备/部署安装准入、安装产品对象关系写围栏、调用 L6 截止端口、持久化端口返回的事件前置责任摘要与运行排空摘要。

围栏关闭后到达的部署安装 CAS 必须检查 L7 `ProductMutationFence`，只能写 `InvalidatedByChannelDelete` 并把候选/Handle 交给冻结的清理责任方；不得发布新的已安装部署。删除期限前仍无法取得 L6 截止回执时，必须隔离旧运行时/设备执行入口后转入恢复或隔离，不能先删产品对象。这样 L6 保持为运行热路径的唯一责任方，L7 只持一次性截止回执和删除协调责任。

每次接纳都分配两个不可拆分的完整 identity：

- `ChannelDeleteOperationIdentity{ChannelDeleteOperationId, ChannelDeleteOperationRetirableLocator}` 属于本次 Ticket/attempt；
- `ChannelDeleteRecoveryIdentity{ChannelDeleteRecoveryId, ChannelDeleteRecoveryRetirableLocator}` 属于预建的独立恢复责任方。

`ownerLedger` 是**可持久协调责任**的唯一账本。它覆盖：

- L7 应用准入关闭；
- 调用 L6 截止、批次前处置、排空、路由移交端口，并观察冻结运行时身份集回执的协调义务；
- 产品对象关系写围栏、候选、已安装 Handle/宿主声明；
- 校准绑定保护、迹线外部结果引用保护、计划内持久交付与反向引用；
- 产品 CAS、清理资源额度和终态交付。

测量运行任务、目标批次、通道测量任务、队列、游标和资源额度本身仍由 L6 唯一拥有；L7 只保存身份摘要、期望回执和调用责任，不接管或复制运行时对象。

日志只有在收到责任原子移交回执后，才能把一项协调责任改记给新责任方；不允许“尝试记录和恢复记录各记一份”。

实时当前结果不进入这本持久责任账本。尝试记录只冻结要在产品事务中失效的 `LiveCurrentKey` 和预期槽修订；槽持有的内存缓冲、能力围栏与读者租约始终由 `SessionLiveResultStore` 本地管理，不创建固定引用、墓碑、恢复或隔离责任方。

`ChannelDeleteRecoveryRecord` 和对应 `ChannelDeleteQuarantineRecord` 都在 admission 时以 `PreparedTarget` durable 建立；后者包含完整 quarantine identity/locator、同一资源 digest 与最坏 ledger 容量。`PreparedTarget` 不拥有资源，只有命中精确 transfer receipt 才能进入 `Owned`；未命中则必须 `UnusedTarget → CleanupDone`。

reservation 的状态闭集只有 `ReservedBeforeNeed → Begun | Unused`。这两个终态与 normal completion/Close 对同一 revision first-wins；`Begun` 后只有恢复责任方 能释放该 slice，`Unused` 后任何迟到 transfer 都只返回原 Unused receipt。pool 容量、完整 identity/locator 或任一最坏 slot 不足时，整个 admission transaction 失败，不创建 Ticket，也不改 Channel。

接纳还必须在首次产品副作用前通过以下引用保护门禁：

- `BindingTransitionGate` 必须是匹配预期修订的 `OpenFree`。若绑定/解绑正在保持、保护仍为 `TransferPending`，或准入门已隔离/关闭，删除通道稳定返回 `BindingTransitionBusy | BindingProtectionNotStabilized`；先让原操作完成、释放或完成责任原子移交后再重新预览，删除流程不得接管仍活动的绑定操作；
- 稳定 `Bound` 要冻结 `BindingRevision + ExactCalSetRef + BindingPinId/pinRevision + CatalogAdmissionLineageReceipt`。已经先胜的 `GrandfatheredSaveSourceClaim` 可以继续到 publication/no-commit；删除只能在 final CAS 将 WorkingSet 的 pin cleanup 责任移给本 operation，随后等待该 claim 的稳定 disposition再释放；
- 每条迹线内存引用要冻结精确的“结果引用 + 引用修订 + 固定引用/租约修订”。已有存储库发布/来源声明先胜时，同样先完成其决策；引用清理责任未能通过责任原子移交交给操作、恢复或隔离记录时，不得删除产品来源，也不得让垃圾回收看见无保护窗口。

#### 线性化点、首次副作用与状态闭集

`AcceptedDurable` 之前的预览、配额计算和上述预留都不是 Channel 副作用。**首次可观察副作用**只能是一个 L7 产品事务；它必须同时完成以下操作，缺一项就整体不提交：

1. 按冻结的 `ExpectedProductGraphRevision + ExpectedRunIntentRevision` 重新计算规范化影响集合，逐项核对产品、Trace DAG、Marker 参考/差值、MarkerCoupling、三类求值定义、TraceAnalysisDisplayBinding、routing、address、selection、binding、external-reference identity/revision/relation，并要求 `AffectedSetDigest + RoutingAffectedSetDigest` 与请求完全相同；
2. 按 expected `ChannelAdmissionRevision` 把 Channel 置为 `DeletionRuntimeAdmissionClosing`，关闭新的 Prepare/Initiate、DeploymentInstall，以及受影响 binding/ResultRef 的 Save/publication source-claim admission；冻结当前全部 Prepare/Candidate/DeploymentInstall/Save/source-claim identity。源 pin claim 只能由这条 L7 入口签发，围栏后到达的 Repository 请求不得绕过已关闭 admission；
3. 按 expected `ProductMutationGateRevision` 安装 `ProductMutationFence{ProductMutationFenceIdentity, ChannelDeleteOperationIdentity, AffectedSetDigest, scoped write-set predicate}`；
4. 写 `ChannelDeleteApplicationAdmissionClosedReceipt{before/after revisions, ProductMutationFenceIdentity, AffectedSetDigest, ApplicationWorkSetDigest}`。

所有能改变该影响集合的产品命令，都必须先向 L7 提交规范化 write set，并与同一 `ProductGraphRevision` 一起检查活动围栏。围栏至少覆盖：

- Measurement、Trace、Marker、MarkerCoupling、TraceTestDefinition、TraceDisplayBinding 和 TraceAnalysisDisplayBinding 的创建、删除、移动或重绑；
- Trace DAG、Marker 参考/差值、耦合作用域或成员；
- 路由、地址、会话选择、校准绑定、迹线内存引用、结果所属对象/键和持久交付关系。

与目标 Channel 引用闭包无交集的修改仍可继续。L7 产品事务先关闭新命令、Prepare 和 DeploymentInstall，再安装 ProductMutationFence；L6 随后用 `closeAndFreezeRuntimeAdmission` 关闭运行准入。两步之间已开始的证据匹配、测量推进、待提交批次、Continuous 或触发注册，由 L6 截止端口线性地纳入事件前置责任集或运行排空集，因此不要求热路径写 L7 WAL。

若步骤 1～3 的任一预期修订、对象集合或摘要在事务提交前不匹配，只能写 `RejectedBeforeSideEffect{AffectedSetConflict}` 并释放预留；不得用“最新集合”静默重试。围栏关闭后，如果最终 CAS 仍发现受保护对象、关系、结果所属键集合扩大/缩小或逐项修订漂移，说明协议、索引或存储已失配：不得自动扩展级联范围，也不得删除冻结集合的子集；必须进入下述 `AffectedSetConflictAfterAdmission` 恢复/隔离分支，并保持应用、运行时和产品对象关系修改入口关闭。无关对象提交导致全局 `ProductGraphRevision` 前进本身不是冲突。

`ChannelDeleteApplicationAdmissionClosedReceipt` 持久化后，跨组件顺序固定如下：

1. 首次交付只能向 L6 幂等调用 `closeAndFreezeRuntimeAdmission`。
2. 取得判别联合 `RuntimeDeleteClosureReceipt` 后，L7 把它写入操作记录，并将测量通道推进为 `DeletionPendingNoAdmission`；它与应用关门回执合成 `ChannelDeleteAdmissionClosureBundle`。正常分支引用 `RuntimeDeleteCutoffReceipt`；若崩溃发生在首次 L6 截止前，只允许引用覆盖整个旧进程的 `PriorProcessIsolationClosureEvidence`，不得伪造空截止。该证据由 bootstrap 组合 OS 单例所有权、旧进程终止、精确 `DeviceSession/HostGeneration` 软件围栏，以及 `PhysicalQuiescent | PhysicalStateUnknownQuarantined` 处置；V1 不建立 L2 持久执行全集，也不引入独立 Runtime 监督服务。
3. 该组合回执持久化后，L7 只调用 [D3A `resolveDeletePreBatch`](./03A-运行对象职责与端口.md#通道删除的运行准入截止端口)。cutoff 分支按 `PreBatchSetDigest` 逐项回滚仍可撤销的接纳；整周期隔离分支只接受 executor、队列、游标、容量配额与上述联合证据。它可以关闭旧软件删除责任，但 `PhysicalStateUnknownQuarantined` 仍禁止复用精确设备。L7 只保存完整 `DeletePreBatchResolutionReceipt`，不直接操作队列、游标或容量配额。
4. 只有前置责任全部有处置，才可向 `DrainSetDigest` 冻结清单交付首个 Stop/Abort。前置集或运行集为空时，分别写 `NoPreBatchWorkReceipt`、`NoDrainNeededReceipt`。
5. 两个集合都为空时，首个设备外部调用才是 `RevokingDeployment` 的句柄撤销或主机隔离。不得在 `AcceptedDurable` 阶段提前 Stop 或撤销部署。

attempt 状态是下列闭集：

- 正常：`AcceptedDurable → ApplicationAdmissionClosing → ApplicationAdmissionClosed → RuntimeAdmissionClosing → RuntimeAdmissionClosed → PreBatchClosing → Draining → RevokingDeployment → ProductAndLiveStoreDeletePending → ProductDeletedReadersDraining → CleanupDone → Retired`；
- 首次副作用前的 revision race：`AcceptedDurable → RejectedBeforeSideEffect → CleanupDone → Retired`；
- 围栏已关闭后的影响集合冲突：任一 `ApplicationAdmissionClosed..ProductAndLiveStoreDeletePending` 活动态 `→ AffectedSetConflictAfterAdmission → TransferredToRecovery | CancelledByClose`；不得直接返回正常 Deleted；
- 删除结果未提交时的责任移交：任一 `AdmissionClosing..ProductAndLiveStoreDeletePending` 活动态 `→ TransferredToRecovery | CancelledByClose → CleanupDone → Retired`；没有 durable transfer receipt 不得进入这两个 terminal。
- product/live-store CAS 已提交但可持久 cleanup 失败：`ProductDeletedReadersDraining → DeletedCleanupTransferred → CleanupDone → Retired`；业务 terminal 保持 `Deleted`，CompletionFence 必须等待 cleanup source-zero 移给同一预建 recovery target。实时 reader 只由本地 store 排空，不随该 transfer 移交。

recovery target 状态闭集为 `PreparedTarget → Owned → Resolving → ResolvedDeleted | ResolvedToSuccessor | ResolvedToClose | ResolvedToQuarantine`，每个 `Resolved*` 再且只能 `→ CleanupDone → Retired`；未激活分支只能 `PreparedTarget → UnusedTarget → CleanupDone → Retired`。只有 ledger 损坏才可 `Resolving ↔ ForensicHold`；普通 I/O 失败、超时或 Repository/Host 不可达不得滥用 ForensicHold。状态不得逆行，`Resolved*` 后不得重做 Stop/revoke/product CAS。

#### 删除测量通道（`Channel`）的执行顺序

删除接纳先按同一个 `RunIntentRevision` 判定，不要求用户预先把通道手工切回 Ready：

| 当前运行意图 | 删除接纳 | drain 规则 |
| --- | --- | --- |
| `Ready` | 接纳 | 仍按冻结清单核对是否存在迟到工作；为空才写 `NoDrainNeededReceipt` |
| `Held` | 接纳 | Hold 已完成时应为零 live，只关闭 Channel gate 并取得 `NoDrainNeededReceipt`；若旧 Hold 尚在排空则加入该旧父排空，绝不恢复或新建父任务 |
| `Initiated` | 接纳 | 关闭新 admission，正常 Stop；到 deadline 才升级 Abort |
| 已有 `DeletionRuntimeAdmissionClosing` 或 `DeletionPendingNoAdmission` | 只允许同一操作/恢复身份幂等查询或加入 | 不创建第二个删除责任方 |
| Session/Channel 已 Closing、Deleted 或 revision 不匹配 | 拒绝 | 不产生副作用 |

这里关闭的是 Channel admission，不把 `DesiredRunState` 扩充成第二套删除状态。`Ready/Held/Initiated` 只决定 drain 动作，不能阻止进入删除专用 workflow。

接纳后只按以下顺序收口：

1. 在同一 L7 产品事务验证精确 `RunIntentRevision/ExpectedProductGraphRevision/AffectedSetDigest`，关闭新命令/Prepare/DeploymentInstall，冻结 Application work set，并安装 ProductMutationFence。
2. 以同一 operation identity 调用 L6 `closeAndFreezeRuntimeAdmission`；把返回的 `RuntimeDeleteClosureReceipt` 持久写入 admission closure bundle。它只能是正常 cutoff，或“首次 cutoff 前崩溃后整个旧运行周期已隔离”的完整证明。
3. 以同一 operation identity 和 closure receipt 调用 L6 `resolveDeletePreBatch`：
   - 正常分支逐项取消尚未提交为 TargetBatch 的 matcher/evidence claim、MeasurementAdvanceCandidate/cursor/acceptance、PendingBatchMembership 和 BatchTargetReservation；
   - cutoff 后崩溃可用绑定原 cutoff 与精确 subject set 的 aggregate；
   - 首次 cutoff 前崩溃分支必须引用整个旧运行周期隔离证明，不得伪造 subject set。

   L7 只在 `DeletePreBatchResolutionReceipt` 的对应覆盖分支完整后继续。多 Channel pending batch 必须整体取消，不能删除一个目标后继续提交剩余目标；已经原子提交的 AdvanceEvent/TargetBatch 只进入下一步，不在这里重复释放。
4. 以预建 `DeploymentAdmissionCloseOperationIdentity` 对精确 InstalledDeployment record CAS，取得 `InstalledDeploymentAdmissionClosedReceipt{closeContext=ChannelDelete}`，先关闭新 Pin/Lease admission；再按 ApplicationWorkSetDigest 和 DrainSetDigest 的完整 identity 清单 Stop 并排空已有 Initiation/TargetBatch/Run，取消或收口 Prepare/Candidate/DeploymentInstall。只有正常 Stop 超过已冻结 deadline 才对同一精确 Handle 升级 Abort。
5. 等全部已签发固定引用/租约归零并取得 `InstalledDeploymentPinLeaseDrainReceipt` 后，才把唯一 Handle 交给清理责任方，并取得撤销/宿主隔离回执，使部署槽进入 `NoActiveDeployment`。只读计数为零不是证明；没有准入关闭回执时不得撤销。
6. routing closure 非空时，以 journal 中唯一 `RoutingHandoffIdentity` 将受影响 ingress 置 Gating，按旧 snapshot 逐份排空、取消或排队 evidence，并为剩余 Channel 准备 successor/rollback。只有 `RoutingHandoffJournal@Gating` 的 expected journal revision、staged plan/hash、逐 binding generation 和 ingress evidence ownership-ledger digest 全部匹配，才可进入 final L7 事务；不得先改 TriggerRoutingConfiguration 再补 handoff。
7. final L7 事务只为验证不变量而重算受保护闭包；产品、Trace DAG、Marker 参考/差值、MarkerCoupling、三类求值定义、TraceAnalysisDisplayBinding、routing、address、selection、binding、external-reference 与 owner-key 各自 revision 必须与 journal 中冻结值逐项相同，不得据此增加或删减对象。无关对象可使全局 ProductGraphRevision 前进；受保护闭包变化则进入冲突恢复。核对通过后，在一个线性化点完成：
   - 删除精确 Channel、递归冻结的 Trace/Marker/三类求值定义/TraceDisplayBinding/TraceAnalysisDisplayBinding/Measurement；按冻结计划删除或推进 MarkerCouplingRevision，并重新验证剩余 Trace DAG、Marker 参考和耦合成员均无断引用；
   - 应用冻结 routing delta，推进 RoutingRevision/受影响 BindingGeneration，并让该提交成为 [D3C 路由移交](./03C-触发多通道调度与验证.md#855-运行中路由切换routing-handoff)的 product-CAS receipt；
   - 为全部被删产品地址写墓碑并推进 AddressBookRevision，将失效的会话当前选择写 `None` 并推进 SelectionRevision；连接级 `ScpiSelectionContext` 不写；
   - 将稳定校准 binding pin/lineage 与 Trace Memory ResultRef pin/lease 的 cleanup 责任从 WorkingSet source=0 移到 ChannelDelete owner target=1，写规范化 resource digest；已有 Save/publication source claim 保持其先胜权；
   - 对每个冻结的 `LiveCurrentKey` 关闭旧 capability、清除实时槽并推进 SlotRevision，写 `ProductDeleteReceipt + LiveCurrentInvalidationReceipt`，同时解除本 operation 的 ProductMutationFence。
8. final CAS 后，routing handoff 依据同一 product-CAS receipt 收口为 Applied 并清理旧 snapshot/queue/claim；Repository cleanup owner 按稳定 release identity 等待先胜 source claim 的 publication/no-commit 后释放 binding 与 Trace Memory pin/lease。等待这些 release/transfer receipt、旧 reader lease、Runtime/`PlannedDeliveryObligation` fence，以及 recovery/quarantine 责任全部稳定处置，再完成 ChannelDelete CompletionFence。任何 pin、routing evidence，或 Marker/MarkerCoupling/测试定义/address/selection delta 少一个 disposition 都不能完成 Fence。

operation owner 每推进一步都先用 expected `ownerRevision` 申领执行权，再用冻结 identity 发起幂等调用，最后写 receipt。ACK 丢失只查原 identity/receipt，不再次 Stop、释放 pin 或 revoke 新 Handle。

#### 超时、关闭、重试与后台责任接管

正常执行、deadline、Close 与重试共用 `ChannelDeleteAttachmentRevision`。attachment 只能从 `AttachedToAttempt{operation identity, revision}` first-wins 到 `ResolvedByAttempt | AttachedToRecovery | AttachedToClose | AttachedToSuccessor`；败者只读取胜者 receipt，不得新建 cleanup owner。

副作用后到达 `operationResolutionDeadline` 或确认当前进程无法继续时，先验证 attachment/attempt owner revision 和 reservation=`ReservedBeforeNeed`，再按 product/live-store CAS 是否已经提交走两个互斥事务分支：

- **CAS 前移交。** 在同一本地事务完成以下动作：
  1. 把完整剩余计划、资源账本、部署固定引用、Handle/宿主声明、持久交付、产品 CAS、活动 `ProductMutationFence` 和终态交付责任移入已存在的 `ChannelDeleteRecoveryRecord`。
  2. 清空尝试记录的 `ownerLedger`，把恢复目标改为 `Owned`、预留改为 `Begun`、附着状态改为 `AttachedToRecovery`，并保持测量通道已有的 `DeletionRuntimeAdmissionClosing | DeletionPendingNoAdmission` 状态。
  3. 在 `ProductMutationGateRegistry` 中按预期修订，把活动围栏的唯一责任方从尝试记录改为恢复记录。
  4. 写入包含围栏前后修订的 `ChannelDeleteResponsibilityTransferredReceipt{..., sourceResponsibility=0, targetResponsibility=1}`。
- **CAS 后 cleanup 移交。** ProductMutationFence 已由 final CAS 变为 Released，事务只把尚未完成的 Handle/Host cleanup、durable delivery、reader 以外的可持久清理与 terminal-delivery ledger 移给 recovery；`ProductDeleteReceipt + ProductMutationFenceReleasedReceipt` 作为不可变完成证据随 ledger 引用，不转移、不复活，也不再对 ProductMutationGateRegistry 做 owner CAS。Channel 与 `Deleted{ProductDeleteReceipt}` terminal 保持不变，attempt 进入 `DeletedCleanupTransferred`。

两支都必须在同一事务清空 source ledger、激活预建 target、推进 reservation/attachment，并写精确 ledger/slice digest；只有 source-zero/target-one receipt durable 才算移交。CAS 前分支随后写 `ChannelDeleteTerminal=TransferredToRecovery{complete recovery identity}`；CAS 后分支只让 OperationCompletionFence 等待 cleanup transfer receipt。timeout、target ACK、一条 journal 指针或只建好 `PreparedTarget` 都不算移交。

- Close 先胜时，必须先有预留完整 slice 的 CloseJournal target，再以同类 source-zero/target-one receipt 把 ledger 移给 Close，同一事务把 recovery reservation 写 `Unused`。recovery 已胜时，Close 只绑定 exact recovery identity 作 waiter，由 recovery 完成删除或再 source-zero 移给 Close，不能从 attempt 第二次接管。
- 用户显式重试必须先创建新 `ChannelDeleteOperationIdentity`/Ticket 及其自身 recovery reservation。
  - 若旧 recovery 仍拥有责任且冻结影响集合没有冲突，新 attempt 只能用 attachment CAS 和 source-zero/target-one `ChannelDeleteRecoveryToSuccessorReceipt` 接管**同一 AffectedSetDigest** 的旧 ledger。
  - 同一事务以 successor 已预留的 operation 容量接管实际责任，并把旧 recovery Credit 以唯一 release receipt 归还；新 attempt 的 recovery reservation 仍保持 `ReservedBeforeNeed`，供后续故障使用。
  - CAS 失败者把本次新 attempt 的 reservation 写 `Unused` 并观察胜者。
  - 新 attempt 从冻结阶段续跑，不重开 admission、不重做已有 receipt 的副作用，也不复活旧 terminal。
  - `AffectedSetConflictAfterAdmission` 明确禁止走 successor 分支。
- startup 在开放任何 Channel/Trigger/Prepare/Delete admission 前联合枚举 attempt、attachment、reservation、recovery/quarantine/Close target 与 Runtime/Deployment/durable-result facets；`SessionLiveResultStore` 在新 RuntimeEpoch 为空，不参与持久恢复扫描。执行权只能用 expected `ownerRevision` 转给新 OwnerEpoch；任一可持久资源双 owner、零 owner 但无 release receipt、`Begun` 无 target 或 `Unused` 却有 transfer receipt 都关闭 admission 并进入 ledger-fault 处置。

后台 recovery 只能得到一个不可改写的 `ChannelDeleteRecoveryResolutionTerminal`：

- `Deleted{ProductDeleteReceipt}`：完成原顺序，Channel tombstone 与全部 release receipt 齐全；
- `TransferredToClose{CloseTransferReceipt}` 或 `TransferredToSuccessor{SuccessorTransferReceipt}`：recovery ledger 已 source=0；
- `Quarantined{DeleteQuarantineTransferReceipt}`：到达恢复期限仍不能证明宿主/存储库结果，或命中 `AffectedSetConflictAfterAdmission` 时，把未决 Handle/声明、冻结集合、资源、重试责任与尚需的清理额度移入准入时已预建的稳定隔离目标。产品 CAS 未提交时，一并通过责任原子移交转交活动的产品对象关系写围栏；已提交时只携带 `ProductMutationFenceReleasedReceipt` 作为证据，不转移围栏。来源恢复记录在该回执后不得再释放已移交额度。

`AffectedSetConflictAfterAdmission` 不能由恢复流程或新尝试自动接受新集合，也不能用后继操作替换旧围栏后继续删除。因为旧围栏、L6 截止、批次前/排空摘要和预留容量都不覆盖集合差异，该分支固定通过责任原子移交转入隔离/人工修复，并保持产品与运行入口关闭。只有人工处置先证明旧责任全部收口、显式释放旧围栏，并恢复到可重新预览的稳定产品状态后，用户才可发起全新的删除；没有删除成功证据时不得预写通道墓碑，也不得把冲突冒充已删除。

`DeletionPendingNoAdmission` 只允许在某个可枚举责任方的有期 `Resolving` 期间存在；普通故障达到恢复期限后必须进入上述三类稳定结论。若产品删除尚未提交，进入隔离的同一产品事务把状态稳定为 `DeletionQuarantinedNoAdmission{QuarantineIdentity, AffectedSetDigest}`，保留产品对象关系写围栏但不冒充已删除；若删除已提交，则只隔离剩余清理。两种情况都不能把测量通道重新开放为可运行状态，查询必须明确显示已隔离。

#### 启动恢复、记录退役与验证

启动恢复按上述联合 ledger 进行，不按“Channel 还在/不在”猜测 owner。attempt retirement 分支各自闭合：

| 分支 | 退役前置证明 |
| --- | --- |
| 成功 | `ProductDeletedReadersDraining → CleanupDone`；cleanup 转 recovery 时还要 reservation=`Begun` 与 source-zero receipt |
| Rejected | `NoSideEffect + resources=0` |
| CancelledByClose | 完整 Close target durable + source-zero receipt |
| TransferredToRecovery | reservation=`Begun`、recovery=`Owned`且 transfer receipt 的 ledger/slice digest 一致 |

未使用 recovery 的正常、Rejected 或 Close 分支，还必须同事实写 reservation=`Unused`、target=`UnusedTarget/CleanupDone` 与唯一 slice-release receipt。再加 immutable terminal、CompletionFence 和 Ticket teardown ACK 后，只有 operation issuer 可按 `ChannelDeleteOperationRetirableLocator` 写 `RetiredChannelDeleteEpoch{maxIssuedSequence, terminalDigest}` 并 compact attempt。

recovery issuer 只能在 resolution terminal 已提交、ownerLedger=0 或已有稳定 successor/Close/quarantine transfer receipt、预留 slice 已由 recovery 唯一释放或以 source-zero receipt 转给后继 owner、requester/Close ACK 齐全且无仍活动的 forensic claim 时，按 `ChannelDeleteRecoveryRetirableLocator` 写 `RetiredChannelDeleteRecoveryEpoch`并 compact。最近固定窗口重放原 terminal/transfer receipt；超过 watermark 的完整旧 identity 只返回 `ChannelDeleteReceiptExpired{terminalDigest}` 或 `ChannelDeleteRecoveryReceiptExpired{terminalDigest}`，绝不重做 CAS/revoke/release。

`CascadeDelete` 使用同一日志冻结并回报完整受影响 ID、标记参考/差值边、标记联动作用域与删除前后成员摘要、限值检查/纹波检查/带宽检查定义、跨测量通道的迹线引用边、路由/地址/选择增量、校准绑定/迹线内存保护引用、各自修订和 `AffectedSetDigest`；调用者缺少其中任一项都必须重新预览，不能按新闭包继续。

ChannelDelete 的故障注入按三组检查，避免把执行步骤和验收结论混在一段中：

1. **逐点中断。** 覆盖准入事务、预留与预建后台目标、L7 产品写入关门、L6 运行准入截止、首次 Stop/Abort、每个排空回执、部署撤销与主机隔离、触发路由移交、最终产品提交与实时槽失效、校准绑定和迹线内存引用释放、地址墓碑、当前选择清空、能力失效、读租约排空、责任方切换、终态、完成围栏、记录退役与压缩的前后。
2. **并发变化。** 分别在 L7 关门前、L7 与 L6 截止之间、L6 截止同时和截止后，尝试注册连续扫描或触发工作，并尝试创建、删除、重绑或移动受影响对象及引用。至少覆盖新增差值 Marker、删除其参考 Marker、MarkerCoupling 增减成员或改变 Channel/DisplayPane selector、某一 TraceAnalysisDisplayBinding 隐藏但求值继续、三类求值定义改版，以及普通集合增大/缩小、仅输入顺序变化、对象 ID 相同但修订变化和无关全局修订前进。
3. **固定判定。** 真实受保护闭包在首次副作用前变化时拒绝；围栏后异常只能把责任完整移交给后台处理或隔离。只有输入顺序变化可规范化为同一摘要，无关提交允许最终比较读取新的全局修订后继续。

每个中断点重启后都要断言：每份可持久资源恰好有一个责任方；已有释放回执的动作不会重做；没有删除预览之外的对象；只保存实时当前结果的连续扫描不产生预写日志或结果存储库字节，进程重启后实时当前结果为空，也不会进入 [D4D §9.5.5](./04D-持久化结果与恢复.md#955-持久交付的唯一提交与恢复协议)的恢复扫描。

引用闭包并发基准另至少覆盖：

- DeleteChannel × RoutingHandoff × queued evidence：旧/新 binding 的每份 evidence 恰有一个处置。
- DeleteChannel × Bind/Unbind × `GrandfatheredSaveSourceClaim`：先胜 publication/no-commit 后才 release，无 pin 泄漏或提前 GC。
- DeleteTrace × Artifact GC/ResultLease：final CAS 前 ref 有保护，CAS 后 cleanup owner 唯一。
- Trace DAG chain/fan-in × 并发新增/改写 edge：默认完整拒绝或显式递归全删，不留断边。
- DeleteMarker × 并发新增 reference/delta：默认完整拒绝或级联精确删除。
- DeleteTrace × 跨迹线 MarkerCoupling：成员摘要稳定，组保持有效、整组删除或拒绝三者只能命中冻结分支。
- 被删 Trace 的 Marker、三类求值定义、TraceDisplayBinding、TraceAnalysisDisplayBinding 和地址在同一摘要与提交中消失；`evaluationEnabled=true` 的定义无论各窗口是否可见都进入闭包。
- 删除 × 地址重排 × 同一 SCPI program message 的旧 selection token：产品地址墓碑与会话选择原子更新，连接选择只稳定返回 stale/target-deleted。

容量测试对 journal records/bytes、owner-ledger entries、Marker/MarkerCoupling/三类测试定义闭包条目与成员摘要、受影响 key/slot-invalidation receipt slots、Close/successor/quarantine transfer slots 和 terminal-delivery slots 分别运行 `exact required` 与 `required-1`：exact 必须可接纳，并在 Deleted/Close/successor 可收口分支回到原水位；任一 minus-one 必须在首次副作用前拒绝且 reservation/target/credit 零泄漏。Quarantined 用例只保留一个有界 recovery root，后续解除隔离后再回到原水位。

另做 final product/live-store CAS 两侧竞态：围栏前已经完成的 live publish 可以先成为 current，随后被同一删除事务清除；围栏后到达的一律 `InvalidatedByControl` 且 slot 写次数为零。旧 Run 的 durable history disposition 在两侧都按原计划完成或移交，历史 `ResultArtifact` 不删除。持有旧 buffer 的 reader 可读到租约结束，但删除后新查询不能再取得该 slot。

连续 `kill → startup → deadline → recovery/Close/retry → retire → compact` 跨越至少两个 issuer epoch，高水位只能围绕配置的 active+retry 窗口波动，不得随删除次数线性增长。再连续 create/delete 同名外部对象超过两个窗口，断言旧 capability 全部失效、live slot/head/reader 归零，且不存在随次数增长的 Result owner tombstone/recovery 记录。

#### 结果所属对象与实时当前结果同事务收口

实时槽、发布能力、读租约和四种稳定处置的唯一合同见 [D4B §9.3.4](./04B-保存召回与运行切换.md#934-会话内实时当前结果)；本节只定义对象删除如何与它原子衔接。

删除迹线、测量量、测量通道或任何拥有结果的对象时，应用层在预览快照中枚举完整受影响 `ResultOwnerKey` 集合，并在同一预期修订的 L7 删除事务中只做精确复核。这里的结果所属键用于实时当前结果失效；迹线的 `StoredResult` 所持 `ResultRef`/固定引用是另一条持久引用，必须按上文的责任归零清理规则同时收口，二者不能互相替代：

- 迹线删除：包含自身 `TraceOwner`；
- 测量量级联删除：包含自身及被删 `TraceOwner`；
- 测量通道级联删除：还包含全部 `ChannelStageOwner`/`MeasurementOwner`/`TraceOwner`。

若结果投影为标记快照（`MarkerSnapshot`）、限值检查结果（`LimitEvaluation`）、纹波检查结果（`RippleEvaluation`）或带宽检查结果（`BandwidthEvaluation`）并分配独立 `ResultOwnerKey`，它们必须随所属标记/检查定义进入同一集合；若产品投影规定它们共用 `TraceOwner`，则仍逐项列出被清除的分析输出槽。采用哪种键形态由 [D4A 产品与结果投影](./04A-应用会话与事务.md#91-仪器会话instrumentsession)固定，本节不另建一套身份模型。

同一事务必须完成三件事：

1. 再次验证 SessionGeneration、当前 ProductGraphRevision、受保护对象/关系的逐项 revision、ProductMutationFence 所有权和冻结的受影响集合摘要；全局 revision 可因无关对象前进，受保护闭包的任何增删才进入冲突恢复；
2. 在 `SessionLiveResultStore` 对每个受影响 `LiveCurrentKey` 关闭旧 capability admission、清除当前槽并单调推进 SlotRevision；槽原先拥有的 buffer 进入有界 reader-drain 集合；
3. 删除产品对象并写 `ProductDeleteReceipt + LiveCurrentInvalidationReceipt{affected owner/key digest, before/after SlotRevision}`。

这是产品删除和实时 current 失效的同一个线性化点。实时槽不创建任何持久 pin、tombstone、pending/recovery 或 quarantine 记录；现有 `LiveResultReadLease` 只按期限在 `SessionLiveResultStore` 排空，最后一个 reader 归还后 buffer 回到池。进程崩溃后 store 本来就是空的，startup 不扫描 [D4D §9.5.5](./04D-持久化结果与恢复.md#955-持久交付的唯一提交与恢复协议)的 WAL 来恢复它。

已接纳旧 Run 的两类交付必须分开处理：

- 原计划中的 `DurableDelivery=RetainHistory | WorkflowEvidence` 继续按冻结的 `PlannedDeliveryObligation` 完成或稳定移交。已经或随后提交的历史 `ResultArtifact` 独立保留，可按其持久引用查询，不因产品 owner 删除而回滚；
- 围栏之后到达的旧 live publish 携带旧 capability，只返回稳定 `InvalidatedByControl`，释放 candidate/reservation，槽写入次数必须为零。它不能重建已删 owner，也不能把历史提交结果重新填成 current。

Cascade 预览和结果同时列出受影响 owner/key、现有 live slot、已签发 capability、active reader 数和未稳定的 durable obligations，使 UI 能区分“实时槽已清除”和“旧历史交付仍在收口”。

完整 live owner 身份由 `SessionGeneration + RuntimeEpoch + ResultOwnerKey + owner semantic revision` 共同限定；重新创建同名对象必须取得新的单调 owner revision/兼容 key，因此旧 capability 永远不能命中新槽。删除围栏只需在有界 capability/reader 窗口内保留；引用归零后可随 LiveOrdinalHead 一起退役。进程重启又由新 RuntimeEpoch 使旧能力失效，所以不需要维护随 create/delete 次数无限增长的 ResultOwner tombstone 表。

## 9.1.4 校准数据集的目录移除

[详细设计 02](./02C-通道编译绑定与失效.md#74-校准绑定与显示状态)只说明 Channel 绑定请求、`Bound/Unbound/MissingUnresolved` 兼容性和校准应用语义。`CatalogDeleteCalSet` 的 Application/Repository journal、gate、route、lineage、恢复与退役协议以本节为唯一字段级事实源。

#### 正常路径

1. Application 先从有硬上限的 `CatalogDeleteRecoveryPool` 一次预留 operation、Repository closure 上限内的全部 route、Close/recovery、稳定 quarantine、terminal-delivery 与 retirement 最坏容量。
2. 同一本地 transaction 分配并 fsync `CatalogDeleteOperationIdentity{CatalogDeleteOperationId, CatalogDeleteOperationRetirableLocator}`、`CatalogDeleteRecoveryIdentity{CatalogDeleteRecoveryId, CatalogDeleteRecoveryRetirableLocator}`、Ticket/Fence、operation journal、recovery/quarantine targets 和 identity reservation。任一 identity/locator、record/byte 或 slot 建立失败都无副作用拒绝。
3. 在首次 Repository gate 请求前，本地事务先把 reservation 从 `ReservedBeforeNeed` 改为 `Begun`、recovery target 改为 `FacetArmed`，把 designated recovery identity 登记为远端 facet 的初始唯一 claimant。这张 armed receipt durable 后才可调用 Repository。
4. Repository gate 关闭后收口 closure receipt 冻结的每个 permit/transfer/quarantine route：已经产品 CAS 的 permit 只能完成 `CommittedToBound`，其余只能 `Aborted` 或 source-zero 移交给精确 quarantine owner。
5. route 全部有稳定 disposition 后，Repository 写 `CatalogTombstoneReceipt` 和 facet receipt；Application 再写不可改的 `CatalogDeleteCalSetTerminal=CatalogRemoved{CatalogTombstoneReceipt}`。该 terminal 只表示已从可选目录移除，不表示内容已经物理回收。

##### 目录墓碑回执

`CatalogTombstoneReceipt` 是目录移除和后续 Repository 内部物理回收共同使用的唯一证明；不存在 `CatalogDeleteReceipt`、`TombstoneReceipt` 等省略身份或版本的别名。字段固定为：

```text
CatalogTombstoneReceipt
  ExactCalSetRef { CalSetId, CalSetRevisionId, ContentHash }
  complete CatalogDeleteOperationIdentity
  complete CatalogDeleteRecoveryIdentity
  CatalogEntryRevisionBefore + CatalogEntryRevisionAfter
  CatalogGeneration
  CatalogDeleteGateClosureReceiptRef + ClosureSetDigest
  RouteTerminalSetDigest
  CatalogAdmissionOrderCutoff + TombstoneOrder
  RepositorySnapshotRevision
  RepositoryLedgerRevisions
    { Catalog, BindingPermit, ReverseReference, Lineage, Token }
  RepositoryReceiptDigest

CatalogDeleteOperationJournal
  complete CatalogDeleteOperationIdentity + designated complete CatalogDeleteRecoveryIdentity
  canonical exact request + semantic/full-envelope hashes
  CalSetId + expected CatalogEntryRevision/catalogGeneration
  initially observed refs + repository closure upper bound
  CatalogDeleteAttachmentRevision + operationResolutionDeadline
  ProcessInstanceId/OwnerEpoch + ownerRevision + RequesterDescriptor
  ownerLedger[] { local route/notification/delivery responsibility, owner/revision, disposition }
  recoveryReservationRef + state + per-route/terminal/transfer receipts

CatalogDeleteRecoveryRecord
  complete CatalogDeleteRecoveryIdentity + source operation identity
  canonical exact request + semantic/full-envelope hashes
  exact CalSet/revision/generation + designated Repository claimant declaration
  reserved route/cleanup/Close/retry/delivery records and bytes
  recoveryResolutionDeadline
  preallocated complete CatalogDeleteQuarantineIdentity
    { CatalogDeleteQuarantineId + CatalogDeleteQuarantineRetirableLocator }
  exact quarantine-record locator + transfer slot
  ProcessInstanceId/OwnerEpoch + ownerRevision
  ownerLedger[] { Repository facet, local responsibility after transfer }
  state=PreparedTarget

CatalogDeleteRecoveryIdentityReservation
  complete recovery identity + exact recovery-record locator
  exact route/cleanup/transfer/quarantine slice digest
  state=ReservedBeforeNeed
```

这些字段的含义为：

- `CatalogEntryRevisionBefore/After` 必须是同一次 Repository 墓碑提交的 CAS 两侧；
- `ClosureSetDigest` 与 `RouteTerminalSetDigest` 分别证明关门时冻结了哪些路由、这些路由最终如何收口；
- `CatalogAdmissionOrderCutoff < TombstoneOrder` 是删除后 lineage 校验的固定边界；
- `RepositoryLedgerRevisions` 证明**墓碑提交当时**各账本来自同一 Repository snapshot。

旧 binding、Save/Recall lineage 后续正常释放会推进这些单调 revision，物理回收时不得要求仍等于墓碑时刻。

`RepositoryReceiptDigest` 覆盖上述全部字段。任何 identity、exact revision、generation、order 或墓碑时刻 ledger revision 不一致都不是“同一回执”。[D4D 后台回收器](./04D-持久化结果与恢复.md#954-反向引用发布记录与物理回收)只消费这份回执，不重建或缩写它。

operation journal 与 recovery record 分别记账：首次 gate 请求后 Repository facet 始终归 recovery identity，operation 只是持 ownerRevision 的当前执行代理；route 观察、tombstone 通知和 terminal delivery 在正常期仍归 operation，超时/Close 时才以 source-zero receipt 移给 recovery。两边不得同时声称同一责任。

recovery 和 `CatalogDeleteQuarantineRecord` 都在 admission 时以 `PreparedTarget` durable 建立；quarantine target 带完整 identity/locator、同一 gate/route digest 与最坏 owner-ledger 容量。它在 source-zero/target-one receipt 前不是 claimant owner，未命中时只能收口为 `UnusedTarget → CleanupDone`。

reservation 的闭集只有 `ReservedBeforeNeed → Begun | Unused`。从未发出 gate 请求才可在无副作用事务中写 `Unused`；一旦 `FacetArmed`/`Begun`，slice 只能由恢复责任方 最终释放，正常 operation 也不能自行归还。

操作记录和恢复记录使用不同的状态闭集：

- **操作主路径：** `AcceptedDurable → RecoveryArming → GateOutcomeUnknown → GateClosed → Routing → TombstonePending → CatalogRemoved → CleanupDone → Retired`；同步响应可以跳过 `GateOutcomeUnknown`。
- **操作分支：** `AcceptedDurable → RejectedBeforeGate → CleanupDone → Retired`；或 `RecoveryArming | GateOutcomeUnknown → CatalogStillVisibleNoGate → CleanupDone → Retired`；任一已经进入门关闭流程的活动状态还可以走 `→ TransferredToRecovery → CleanupDone → Retired`。
- **恢复主路径：** `PreparedTarget → FacetArmed → Resolving → ResolvedCatalogRemoved | ResolvedNoGate | ResolvedToQuarantine`，每个 `Resolved*` 之后只能进入 `CleanupDone → Retired`。
- **恢复未激活分支：** 只能走 `PreparedTarget → UnusedTarget → CleanupDone → Retired`。
- **终态约束：** 进入任一 `Resolved*` 后，不得重做验收门 CAS、路由释放或目录墓碑写入。

#### 线性化点与引用来源链语义

Repository 以 expected entry revision 做唯一 gate CAS：

`Visible → ClosingForNewBindings{catalogGeneration, CatalogDeleteOperationIdentity, designated CatalogDeleteRecoveryIdentity}`。

同一事务写：

`CatalogDeleteGateClosureReceipt{delete identity, recovery identity, closed catalog revision/generation, exact in-scope permit/transfer/quarantine refs}`。

这个 CAS 是“不再接纳新 Bind”的线性化点。closure 集超出预留 route slots 时，CAS 整体失败，entry 仍为 `Visible`。

这个 gate 请求是 CatalogDelete 的首次外部副作用。从该请求起，Repository facet 的 claimant 就是 armed receipt 中的 designated recovery identity；operation/Ticket 只是执行代理与观察者，不允许在断网后再临时抢 claimant。正常路径由 operation 代理完成远端 facet 时，要在 recovery record 写 `CatalogDeleteFacetResolvedByOperationReceipt`，才能让该 target 进入 `ResolvedCatalogRemoved`。

Catalog tombstone 只从默认发现和未来新 Bind 中隐藏 CalSet，不消灭精确 immutable revision。删除前已经合法建立的 `Bound`、RecallSet outgoing pin 或递归可验证的 `CatalogAdmissionLineageReceipt` 仍可保护精确引用；删除后不得从 payload 自报 lineage。Save/Recall 如何从这些根签发 grandfather 资格，由[D4B §9.3](./04B-保存召回与运行切换.md#93-保存召回与运行切换事务)定义。

`CatalogAdmissionLineageRoot` 不是第三种宽泛根类型；合法根的闭集固定为下列 tagged union，字段名在 [D2C 通道绑定](./02C-通道编译绑定与失效.md)、[D4A 应用事务](./04A-应用会话与事务.md)和 [D4B 保存召回](./04B-保存召回与运行切换.md)中必须完全相同：

| 根类型 | 何时建立 | 必须由 Repository 签名的字段 |
| --- | --- | --- |
| `VisiblePermitRoot` | catalog entry 仍为 Visible 时，Bind permit 成功发布为稳定 binding protection | ExactCalSetRef、CatalogEntryRevision、CatalogBindingPermitIdentity、CatalogAdmissionOrder、root receipt digest |
| `PreDeletePublicationRoot` | RecallSet 在 tombstone 前已经原子发布并拥有 outgoing pin | ExactCalSetRef、RecallSet exact identity、PublicationReceipt、CatalogAdmissionOrder、root receipt digest |

删除后两种根都必须满足 `CatalogAdmissionOrder < TombstoneOrder`。`CatalogAdmissionLineageReceipt` 只能携带 `rootKind = VisiblePermitRoot | PreDeletePublicationRoot` 和可逐跳验证到该根的 parent receipt；不存在名为 `CatalogAdmissionRoot` 的别名，也不能由 artifact payload、导入报告或当前引用计数伪造。

#### 超时、关闭、重试与启动恢复

- gate 前失败只允许 `RejectedBeforeGate{reason}`，必须同事实证明 `NoGateMutation + ownerLedger=0`、reservation=`Unused` 且 target=`UnusedTarget`。已经 armed 的请求即使 Repository 无响应也不得伪装成 gate 前拒绝。
- 已 armed 请求若收到 Repository 可认证的同步 `NoMutationReceipt{exact request identity, expected/actual CatalogEntryRevision, exact Visible revision, gateApplied=false}`，必须在一个本地事务把 recovery 写为 `ResolvedNoGate`、operation attachment 写为 `ResolvedByOperation`、operation terminal 写为 `CatalogStillVisibleNoGate{NoMutationReceipt}`，清空两侧 ownerLedger，并由 recovery 唯一释放 `Begun` slice。该分支不写 tombstone、不进入 `RejectedBeforeGate`，也不要求先伪装成 TransferredToRecovery；resolved recovery 在 operation terminal/requester ACK 前不得退役。
- 正常完成、`operationResolutionDeadline`、Close 与 retry 共用 `CatalogDeleteAttachmentRevision`。attachment 只能从 `AttachedToOperation{operation identity, revision}` first-wins 到 `ResolvedByOperation | AttachedToRecovery`；败者只读胜者 receipt。Repository facet 已经归 recovery identity，Close 和 retry 都不得另建第二个远端 claimant。
- gate 结果未知、本地 route 无法继续、达到 deadline 或 Close 请求收口时，Application 只做本地 first-wins transaction：验证 recovery=`FacetArmed`、reservation=`Begun` 和两个 ownerRevision，把 operation 的 route 观察、tombstone 通知、requester/terminal-delivery 与剩余 cleanup ledger 全部移入该 recovery record，清空源 ledger，把 attachment 改为 `AttachedToRecovery`，并写 `CatalogDeleteResponsibilityTransferredReceipt{source operation identity/revision, target recovery identity/revision, attachment revision, exact gate/route/slice digest, sourceResponsibility=0, targetResponsibility=1}`。该事务不调用 Repository。
- 只有 transfer receipt durable 后，原 operation 才可写 `TransferredToRecovery{complete CatalogDeleteRecoveryIdentity}` 并完成 Ticket/`*OPC`/`*WAI`/Close；该 terminal 不表示已删除。只有 timeout、target ACK 或 journal 指针都不是责任移交。
- Close 在 gate 前可赢得 no-side-effect 分支；gate 已 armed 后只能驱动上述 recovery transfer。CloseJournal 记 exact recovery identity/waiter receipt 后即可收口自身 Fence，不等待 Repository，也不释放 recovery slice。
- 用户显式重试必须使用新 operation identity/Ticket。若 active recovery index 已指向原 recovery identity，新命令只能写 `CatalogDeleteRetryJoinedReceipt`，把自己未使用的 recovery reservation/target 收口为 `Unused/UnusedTarget`，并返回 `TransferredToRecovery{original complete recovery identity}`；不再 gate、不接管资源、不改写旧 terminal。只有原 resolution=`NoGate` 且 entry 已证明回到 exact `Visible` revision，才能用新 recovery identity 重新删除。
- startup 在新 Bind/Unbind/CatalogDelete 和 物理回收 前联合枚举全部未退役 operation journal、attachment、reservation、recovery/quarantine record、binding quarantine 与 Repository facet。`PreparedTarget` 只能依 reservation 进入 `UnusedTarget`或补成 `FacetArmed`；`Begun` 必须找到同 identity 的 facet/armed receipt，`Unused` 必须证明没有 gate 请求。执行权只能用 expected `ownerRevision` 转给新 OwnerEpoch；任一双 claimant、无 receipt 的零 claimant 或 source/target digest 不一致都关闭上述 admission。

恢复责任方 按原 gate identity/request 查询和收口，只能写一个不可改的 `CatalogDeleteRecoveryResolutionTerminal`：

- `CatalogRemoved{CatalogTombstoneReceipt}`：全部 closure route、精确目录墓碑和 Repository facet receipt 齐全；它不表示物理回收；
- `NoGate{NoMutationReceipt, exact Visible revision}`：Repository 可验证地证明 gate 未生效，当前 entry 仍可用新 identity 重试；
- `Quarantined{CatalogDeleteQuarantineTransferReceipt}`：recovery resolution deadline 时仍无法证明 gate/tombstone，将远端 claimant capability、所有 route/cleanup 责任和预留 Credit 以 source-zero/target-one receipt 移给 admission 时已预建的稳定 `CatalogDeleteQuarantineRecord`。catalog entry 保持不可新 Bind/物理回收，但不再存在无 owner 的 Pending。

Quarantined 不冒充 CatalogRemoved。它是可枚举、有硬配额的稳定责任终点：旧 Ticket/Close 已完成，但 quarantine target 在 Repository 可用并得到 tombstone/no-gate 证明前一直占用配额，不得 compact 成丢失 claimant 的摘要。这是对真实外部不可达的有界背压，不是用永久 Pending 拖住请求。

#### 记录退役、压缩与验证

| 分支 | Application operation 退役前必须证明 | recovery/facet 后续 |
| --- | --- | --- |
| `CatalogRemoved` | `CatalogTombstoneReceipt`、全部 route receipts、Repository facet resolved、immutable terminal、CompletionFence 与 requester teardown | recovery=`ResolvedCatalogRemoved`，由 recovery 唯一释放 Begun slice |
| `RejectedBeforeGate` | `NoGateMutation + ownerLedger=0`、reservation=`Unused`、target=`UnusedTarget`、terminal 与 requester teardown | slice 只按 Unused receipt 释放一次 |
| `CatalogStillVisibleNoGate` | armed request 的可认证 `NoMutationReceipt`、attachment=`ResolvedByOperation`、immutable terminal、CompletionFence 与 requester teardown | recovery=`ResolvedNoGate`，由 recovery 唯一释放 Begun slice；不得退役早于 operation ACK |
| `TransferredToRecovery` | 纯本地 `source=0 + exact recovery target durable`、terminal delivery 与 requester teardown | 原 operation 不等 Repository；recovery 进入三类 resolution 之一 |

只有 Application operation issuer 可按 `CatalogDeleteOperationRetirableLocator` 写 `RetiredCatalogDeleteEpoch{maxIssuedSequence, terminalDigest}`；且只有独立 recovery issuer 可按 `CatalogDeleteRecoveryRetirableLocator` 写 `RetiredCatalogDeleteRecoveryEpoch`，Repository 无权写这两个公开 watermark。

recovery 只有同时满足以下条件，才可进入 `CleanupDone`：

- resolution terminal 已提交；
- ownerLedger=0；
- slice 已唯一释放，或已 source-zero 转给稳定 quarantine；
- 所有 requester/Close ACK 齐全。

这些条件仍不自动允许退役。若 quarantine 还引用 recovery identity 作 Repository claimant，该 locator 必须保留为 live root，直到后续 tombstone/no-gate 收口释放该引用。只有无 live claimant/transfer/forensic ref 时，才可写 recovery watermark 并 compact。

最近固定窗口可重放原 receipt；watermark 之外的完整 identity 只返回 `CatalogDeleteReceiptExpired{terminalDigest}` 或 `CatalogDeleteRecoveryReceiptExpired{terminalDigest}`，绝不重做 gate/release/tombstone。

精确 kill-point 覆盖：admission transaction、reservation/PreparedTarget、`Begun/FacetArmed` 事务、首次 gate delivery、同步 NoMutation response、`ResolvedNoGate + CatalogStillVisibleNoGate` 同事务、gate CAS/closure receipt、closure 集从初观察扩展到上限、每个 route disposition、tombstone/facet receipt、attachment CAS、source-zero transfer、operation terminal/Fence、resolution/quarantine transfer、watermark/compact 的前后，并单独覆盖首次 gate 后 Repository 持续不可达。每点 restart 后都断言 Repository claimant 只有 designated recovery identity，本地责任也恰有一个 owner。

容量测试对 operation/recovery records/bytes、closure route slots、owner-ledger entries、Close/retry/quarantine transfer slots 和 terminal-delivery slots 分别运行 `exact required` 与 `required-1`：exact 必须可接纳，并在 CatalogRemoved/NoGate 可收口分支最终回到原水位；任一 minus-one 必须在 armed/首次 gate 前拒绝，且无 gate mutation、identity/record/Credit 泄漏。Repository 持续不可达的 Quarantined 用例必须精确保留一个有界 live root，待后续收口后再回到原水位。

连续 `kill → startup → deadline/Close/retry → resolution → retire → compact` 必须跨越至少两个 operation/recovery issuer epoch；除仍真实持有外部 claimant 的有界 quarantine roots 外，record/bytes/route/receipt 高水位只能围绕配置的 live+retry 窗口波动，不得随目录移除次数线性增长。断言还要证明成功返回后无迟到 Bound，Transferred/Quarantined 不冒充 CatalogRemoved，且 release/Credit 均不双释。

兼容层裸 `DeleteCalSet` 固定映射 `CatalogDeleteCalSet`，不得按当前引用计数在目录移除和物理回收之间摇摆。最后一个 live Channel Unbind 只释放自己的 binding pin，不触发物理回收；`CascadeDelete` 也不得原地改写 RecallSet、ResultArtifact 或 CalSet。

物理内容回收是 [D4D §9.5.4](./04D-持久化结果与恢复.md#954-反向引用发布记录与物理回收)中 Repository 后台回收器的内部维护动作。它没有 Application Command、OperationTicket、UI/SCPI/Automation 入口；本节只生产它所需的精确 catalog tombstone、lineage 与保护引用事实。

## 9.1.5 删除后台处理状态查询

`DeleteRecoveryIdentity` 是显式判别联合：

`ChannelDelete{ChannelDeleteRecoveryIdentity} | CatalogDelete{CatalogDeleteRecoveryIdentity} | ChannelReconfigure{ChannelReconfigureRecoveryIdentity}`。

第三种只用于 DeleteTrace/DeleteMeasurement/CascadeDelete 触发的通道重配置。tag 必须进入序列化与授权判断，不能把三个域中外观相同的 ID 互换。

任一 `TransferredToRecovery{...}` 只表示原 Ticket 已把责任交给后台处理责任方，不表示对象已删除或新配置已安装。

Application 必须提供公开、只读的 `QueryDeleteRecoveryStatus(DeleteRecoveryIdentity)`。完整 recovery identity 就是查询键，不能要求调用者猜内部 journal locator。

查询在同一一致快照中读取活动 identity 索引、recovery record、resolution terminal 和 retirement watermark，只返回下列闭集：

| 查询结果 | 对外含义 | 最少字段 |
| --- | --- | --- |
| `RecoveryActive` | 唯一后台处理责任方仍在确认或收口 | 完整 identity、`ChannelDelete | CatalogDelete | ChannelReconfigure`、当前 phase、`RecoveryObservationRevision`、最后稳定 receipt 摘要、是否保持产品/目录/运行 admission 关闭 |
| `RecoveryResolved` | 后台工作已有不可改写结论 | 完整 identity、精确 `ChannelDeleted | CatalogRemoved | CatalogStillVisibleNoGate | TraceProcessingRebound | ReconfiguredInstalled | ConfiguredNoRunnableMeasurement | TransferredToClose | TransferredToSuccessor | Quarantined` 结论、terminal digest、完成 revision；只返回适用于该 tag 的分支 |
| `RecoveryReceiptExpired` | 明细已越过公开重试窗口 | 完整 identity、retirement watermark、terminal digest；不得重做删除或重新建立 owner |
| `RecoveryIdentityNotIssued` | 该完整 identity 从未由当前 authority 签发 | authority/locator 校验结果；不得退化为新建后台处理任务 |

同一 `RecoveryObservationRevision` 的重复查询必须字节稳定；查询不取得执行 lease、不延长记录寿命、不改变 Ticket terminal，也不替 恢复责任方 重试外部副作用。调用者只有对应 Session/operation 的读取权限时才可观察；日志和诊断默认只显示脱敏 identity 与 terminal digest。

UI、VnaPro 原生 API 和 Automation 必须直接映射这个 typed query，并把 `RecoveryActive` 显示为“已转后台处理”，不能显示成成功或失败。V1 没有 undelete/Restore 合同，本查询只观察原操作，不会还原对象。ZNB/SNA 厂商 SCPI 是否存在相应查询、错误码和结果外观必须由精确 profile transcript 解禁；没有证据时不得发明厂商命令。适配器字段级映射见 [D5A §10.2.1](./05A-外部适配器.md#1021-删除后台处理状态的呈现与原生-api-映射)。
