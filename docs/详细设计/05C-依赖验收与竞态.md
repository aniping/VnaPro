## 12. 依赖与编码门禁

### 12.1 静态边界

- CMake 对每个生产 target 声明层级与 `PUBLIC/PRIVATE/INTERFACE` 依赖；未登记 target、未能解析的 alias/generator expression 和表外依赖一律失败关闭。
- Core API 全部可在无设备、无线程、无文件系统的单元测试运行。
- 每个公开结构有 schema/version 或仅限同进程 ABI；动态 ABI 只用 C POD、size 和显式所有权。
- 任何新 `shared_ptr<vector<complex>>`、Frame 级单一 WaveDomain、裸回调 Sink、未带 revision 的 latest result、以 Channel 号调用 HAL，都必须在评审中阻断。
- 新功能先写纵向场景与失效矩阵，再决定落在哪个现有模块；禁止为了匹配图而创建只转发的空层。

此外，L5 目标不得直接链接 L2/L3，L4 不得链接线程/文件/Repository，L6 不得包含 Driver ABI、SCPI 或 QWidget。L5 拥有纯数据 `BoundChannelPlanDescriptor`；`VnaDeploymentAccessPorts` 合同拥有 `InstalledDeploymentDescriptor`，组合 L0 deployment identity、L2 公开执行值和 L5 描述符。L7 只拥有 `InstalledDeploymentRecord`、opaque handle/transaction；concrete move-only L2 Handle 由 `VnaApplicationHardwareOwner` 独占。若代码把 Handle 放进 L0/L5 类型、可序列化 descriptor、Pin 或 Lease，依赖检查必须失败。

<a id="dd-target-dependency-policy"></a>

#### 12.1.1 构建目标直接依赖白名单

这是 production target 的**直接依赖白名单**，不是“层号更高就可以依赖所有较低层”。同层边、测试 target、代码生成器和第三方库也必须另有逐 target 登记；没有登记即禁止。`VnaCompositionRoot` 是唯一组装例外，只能产生最终可执行程序并做对象装配，不能被其他 production library 链接，也不能承载业务判断。

| 构建目标或目标组 | 归属层 | 允许直接依赖的内部层/目标 |
| --- | --- | --- |
| `VnaContracts` | L0 | 无内部 target |
| `VnaDriverSdk` | L1 | L0 |
| `VnaDriverHost` | L1 | L0、`VnaDriverSdk` |
| `VnaHardware` | L2 | L0、L1 |
| `VnaAcquisition` | L3 | L0、L2 |
| `VnaProviderConditioningCore`、`VnaObservationCore`、`VnaNetworkModelCore`、`VnaCalibrationCore`、`VnaTransformCore`、`VnaTraceCore` | L4 | L0 |
| `VnaChannelCore` | L5 | L0、L4 |
| `VnaRuntimePorts` | L6 稳定合同 | L0 |
| `VnaDeploymentAccessPorts` | L6 部署访问合同 | L0、L2 公开执行合同、L5 公开部署描述合同 |
| `VnaRuntime` | L6；含唯一的 `RuntimeStageStateStore` | L0、L2、L3、L4、L5、`VnaRuntimePorts`、`VnaDeploymentAccessPorts` |
| `VnaRuntimeJournalAdapter` | L6 出站基础设施适配器 | L0、`VnaRuntimePorts` 的 `GroupActivationSourceJournalPort` |
| `VnaApplication` | L7 | L0、L5、`VnaRuntimePorts`；同层 sibling 必须逐 target 登记 |
| `VnaApplicationHardwareOwner` | L7 出站基础设施适配器 | L0、L2、`VnaDeploymentAccessPorts`、`VnaApplication` 的 `HardwarePreparationOwnerPort` |
| `VnaScpi`、`VnaUi`、`VnaAutomation`、`VnaFileIo`、`VnaDataService` | L8 | L0、L7 Application ports |
| `VnaCompositionRoot` | 组装根 | 表内全部 target 的显式清单 |

“允许依赖某层”仍不是通配：CI 中每个 target 保存 exact target allowlist，表中层集合只是上界。比如 `VnaAcquisition → VnaHardware` 合法，不代表它可以绕过 L2 直连任意 L1 target；`VnaRuntime` 能组合 L2–L5 能力，也不能包含这些层的私有头。入站适配器只能调用上层用例端口；`VnaRuntimeJournalAdapter`、`VnaApplicationHardwareOwner` 这类出站适配器只能实现所属层定义的窄端口，不能主动发起业务、选择目标或拥有第二套状态机。

V1 只部署一个承载 L6/L7 的主进程。主 bootstrap 取得 OS singleton、生成 `ProcessEpoch`，并在开放新准入前通过 L1/L2 围栏旧 exact DriverHost `HostGeneration/DeviceSession` 的软件能力，同时取得 `PhysicalQuiescent | PhysicalStateUnknownQuarantined` 处置；它组合 `PriorProcessIsolationEvidence` 供 Session Close/Channel Delete 的恢复使用。软件围栏不证明设备静止，状态不可知的精确设备仍禁止 Open/Prepare/Arm/Start/复用。这里不新增 Runtime 服务、authority ledger、私钥、公钥证书或 generation-fence IPC。普通 Sweep、TargetBatch、Run 和运行控制保持零 WAL，进程重启后终止旧运行而不重放。

#### 12.1.2 L0–L4 产品类型禁用表

L0 是基础表示，不是“所有层都可能用到的 DTO”仓库。允许进入 L0 public API 的类别闭集只有：单位与量纲、基础数值表示、通用强类型 identity/revision/generation 原语、时间/deadline、Status/Error、Quality、Schema/span、hash 和 Credit/ownership 原语。带 Channel、Measurement、Trace、DisplayPane、SCPI、Repository、Save/Recall 或工作流语义的类型由真正拥有它的层定义；不能为了消除 include 就下沉到 L0。

| 作用范围 | public header / AST 中禁止的上层类型族 | 应使用的边界 |
| --- | --- | --- |
| L0 `VnaContracts` | `ChannelDefinition`、`MeasurementDefinition`、`TraceDefinition/TraceId`、`DisplayPaneDefinition`、`TraceDisplayBinding`、`ProfileAddressBook`、`ScpiSelectionContext`、`ResultRef/ResultArtifact`、Repository/File DTO | 仅使用前述基础表示闭集；业务类型留在 L5/L7/L8 所有者 |
| L1 `VnaDriverSdk/VnaDriverHost` | `Channel*`、`Measurement*`、`Trace*`、`DisplayPane*`、`ProfileAddress*`、`Scpi*`、`Repository*` | 版本化设备命令、能力、实际执行值、波块和终态 ABI |
| L2 `VnaHardware` | 产品 ID/聚合、Trace/Calibration/Result/SCPI/UI 类型 | `AcquisitionRecipe`、设备能力、`EffectiveExecutionPlan` 和物理执行事件 |
| L3 `VnaAcquisition` | Channel 调度、Measurement/Trace/DisplayPane、ResultRef、Repository、SCPI/UI 类型 | Prepared execution、WaveSchema、完整 `RawWaveFrame` 与 Acquisition terminal |
| L4 数值 Core | `TraceId`、产品 Trace/Measurement/Channel DTO、`ResultRef/ResultArtifact`、Repository、`ProfileAddressBook/ScpiSelectionContext`、线程与文件类型 | 已准备数值算子、NumericSchema、只读数值视图和不可变数值结果 |

“通用强类型 identity 原语”只指不带业务含义的实现构件；`TraceId` 等业务标签本身不因此获得进入 L0/L4 的豁免。若一个新 L0 类型不能在评审中归入上述闭集，或只是为了让上层 DTO 跨更多 target 传播，静态门禁必须拒绝。

#### 12.1.3 CI 如何机械检查

1. R2 配置阶段只从 CMake File API codemodel 读取 production target 的**直接** link edge，与本节 exact target allowlist 比较；未知 target、未登记直接边或无法求值的依赖表达式失败。
2. R2 保留少量高价值 compile-negative fixture：L5 直接链接 L2、L6 直接链接 L7 concrete、descriptor 含 raw Handle/L2 concrete、L8 绕过 L7。每个 fixture 必须稳定编译或配置失败，并输出具体非法边或类型。
3. R2 另运行 DeploymentAccessPort contract test 和 capability-owner property test，证明 Handle 在 candidate、installed、retirement 之间始终唯一所有，且 `InstalledDeploymentDescriptor` 不拥有 Handle。
4. 完整传递闭包、`compile_commands.json + clang-scan-deps` include graph、Clang AST 禁用类型扫描和 L0 public API 分类清单可在 S1 作为可选治理项加入，用来提高审查覆盖率；它们不是 R2 阻断条件，也不得伪装成已经存在的检查器。

本文只定义策略与验收输入，不假定当前源码已经有上述检查器。脚本、CMake 属性和负例 fixture 真正进入受审仓库前，`DEP-OWNERSHIP@R2` 仍是 `DraftPendingReview`，不能因表格存在就视为通过。

跨层契约与依赖证据按以下边界组织：

- L0 只提供 identity/revision/generation 等基础原语；`BoundChannelPlanDescriptor` 作为 L5 的公开编译输出留在 `VnaChannelCore`。`VnaDeploymentAccessPorts` 定义 `InstalledDeploymentDescriptor`，组合 L0 identity、L2/L5 公共值；它不因“跨层使用”下沉成 L0 DTO，也不归 L7 所有。
- `VnaRuntimePorts` 保持 L0-only；`DeploymentAccessPort` 单独由 `VnaDeploymentAccessPorts` 拥有，该 target 显式依赖 L2 公开执行合同和 L5 公开部署描述合同。`VnaApplicationHardwareOwner` 实现该端口；同一适配器的私有 Installed record 唯一保存 Handle 并接收 `start/arm`。任何将 L2/L5 类型复制进 `VnaRuntimePorts` 或 L0 的影子 DTO 都必须在 CI 失败。
- CMake/include-graph 门禁必须证明 VnaRuntime 不 include/link VnaApplication concrete。
- `PreparedExecutionHandle` 不得出现在 L6 公共头、descriptor、Pin/Lease 布局或序列化 Schema 中。
- L6 的 fake `DeploymentAccessPort` 契约测试只覆盖 acquire/retire CAS、`AtomicAdmission` 零部分 Lease、`PerTargetAdmission` 单 target 和 descriptor hash 不匹配失败关闭；它不持有真实 Prepared Handle，不能证明 move transfer。
- move-only Handle 的 success payload → CandidateOwnerRecord → InstalledDeploymentRecord、supersede、rebind 与 retirement/install transfer，由 composition-root owner adapter 模型测试和 L2↔L7 跨层 property/fault-injection 负责。断言是任一时刻唯一 owner、失败路径回到零或旧 owner，而不是让 L5 单元测试伪造 Handle。

### 12.3 架构验收门（Gate）

以下 16 个 Gate 是**候选发布阻断条件**，用于约束后续实现和证据准备，不是当前已经生效的发布结论。整套新文档与校验器尚未纳入受保护的发布基线，仓库也没有受保护的 Git commit/tag、CI run 或审批记录，因此当前统一状态只能是 `DraftPendingReview`：`gate_eligible = false`、所有阶段均未完成，尤其不能把 `R0/R1/R2/S*` 的范围标签解释成“该阶段已通过”。

正式启用后，每个适用范围必须同时提交“未触发阻断条件”的结果和列出的必需证据；只有测试通过而缺少可追溯输入、identity 或资源守恒证明，仍视为未通过。尚未激活的后期范围才可在正式评估中标为 `NotApplicable`，不能反向阻塞较早阶段。

<a id="dd-gate-evaluation-contract"></a>

#### 12.3.1 验收门评估键与回执

Gate 状态不是按 `GateId` 保存的全局布尔值。一次可复用的评估必须由完整 `GateEvaluationKey` 定位：

```text
GateEvaluationKey = {
  GateId,
  AssertionScopeId,
  AssertionScopeVersion,
  AssertionScopeDefinitionHash,
  AssertionScopeSerializationId,
  CodeRevision,
  BuildRevision,
  RuntimeProfileRevision,
  DeviceProfileRevision,
  StorageProfileRevision,
  ProtocolProfileRevision,
  ExactCapabilityRevision,
  EvidenceAndTestBundleHash
}
```

- 正式发布后，`AssertionScopeId` 必须来自受审的 `ScopeRegistry`；version 和 definition hash 均不得为空，也不得用 Gate 家族名代替 scope。候选表未经受保护提交、CI 与审批，不能据此实例化有效评估键。
- 四类 profile revision 必须分别写本次 VnaPro runtime、device、storage 和 Native protocol profile 的规范身份；`ExactCapabilityRevision` 必须绑定探测并冻结的能力快照。没有参与本范围的字段也写显式 `None@version`，不得省略形成通配。
- `EvidenceAndTestBundleHash` 覆盖测试清单、用例参数、oracle/golden vector、测试二进制、原始输出和资源/故障注入摘要的规范 manifest。
- `CodeRevision`、`BuildRevision`、任一 profile/capability revision、断言范围版本或 bundle 内容变化，都会形成新键。旧回执只能保留审计，不能给新键提供 `Passed`。

正式发布后的 `GateEvaluationReceipt` 至少保存完整 key、`Passed|Failed|Blocked|NotApplicable`、逐断言结果、开始/结束时间、执行器身份、内容哈希，以及受保护 Git commit/tag、CI run 和人工审批记录引用。`Passed` 只对精确 key 有效；一个切片通过要求此前仍适用和本片新激活的每个 scope 都有当前回执。校验器只验证字段结构和内容哈希，不能自行宣称 CI/审批可信，也不会生成或模拟通过回执。正式启用后特别禁止以下复用：

- 用 R1 的 TYPE 回执证明 S1 Conditioning/NetworkModel；
- 用 R2 的 CHAIN 回执证明 S1 Channel/Measurement/Trace；
- 用 `NUM-CAL@S3` 证明 `NUM-MATRIX@S4` 或 `NUM-XFORM@S6`；
- profile 或 capability revision 改变后沿用旧回执。

未来的 `ARCH-*` 回执只评价 VnaPro 内部契约、内部 `GAP-*` 和测试。若要声明厂商兼容，发布清单还必须按域附加精确 profile 回执；内部 Gate 与厂商兼容 Gate 使用不同的 key 空间，不能互相代替。定义哈希一致只说明文档定义未自相矛盾，不是任何一种回执。

##### 验收范围规范登记表（`ScopeRegistry`）

**候选定义｜DraftPendingReview**

本表是 19 个内部断言范围的**候选定义源**。[A06](../架构设计/06-架构约束与验收索引.md)只解释拟议的激活顺序，其他文档只能引用这里的候选 ID，不能另起别名或重定义范围。当前注册表生命周期是 `DraftPendingReview`；这意味着内容仍可评审整改，不能生成 Gate 通过回执，也不能充当发布基线。

19 行候选定义共同使用 `AssertionScopeSerializationId = vnapro.scope.internal-gfm-list-item.draft1`。它只定义当前草稿的确定性哈希字节，不代表冻结或签发：

1. 以严格 UTF-8 读取本文件，拒绝 BOM，把 CRLF 和裸 CR 规范为 LF；不做 Unicode NFC/NFKC 或大小写转换。
2. 使用仓库固定的 GFM 解析器识别 assertion；每条 assertion 必须是唯一、可见的顶层无序列表项。哈希输入取该列表项的原始 Markdown 字节，仅移除解析器返回值末尾的 LF；fenced code、HTML comment、blockquote、raw HTML 或缩进代码中的同名文本均不算定义。
3. 按 registry 行中的 AssertionId 顺序组成字段：`ScopeId`、`Version`、各 assertion block。字段之间插入精确五字节 `0A 2D 2D 2D 0A`，即 LF + `---` + LF；不加终止换行。任何字段包含该保留分隔符时校验失败。
4. 对上述完整字节串计算 SHA-256，以 64 位小写十六进制写入 `DefinitionHash`。生命周期、规划权威标签、激活阶段和表格排版不进入 hash；它们由 registry 结构校验单独约束。

[确定性校验器](../reference/verify_scope_registry.py)是上述规则的可执行参考。

**运行与依赖**

- 在仓库根目录运行 `python3 docs/reference/verify_scope_registry.py`，检查 19 个内部候选定义、4 个兼容候选定义、空的正式发布历史、8 个待采集 profile 状态，以及 SCPI 地址/准入与 target 依赖/类型禁用四张候选策略表是否自洽。输出统一使用 `definition-integrity`，不得解释成 Gate、厂商兼容或源码依赖检查已经通过。
- 加 `--manifest` 输出确定性 JSON；顶层必须明确包含 `lifecycle = DraftPendingReview`、`gate_eligible = false`、`vendor_compatibility_passed = false`、`vendor_address_mapping_eligible = false` 与 `source_dependency_check_executed = false`，每个 ZNB/SNA profile 域都必须是 `Pending`。清单只证明候选定义自洽，不是发布批准记录，也不表示源码依赖已经扫描。

##### 厂商兼容评估键

正式启用厂商兼容评估后，不使用内部 `GateEvaluationKey`，而使用单域的 `CompatibilityGateEvaluationKey`。以下是未来回执的目标 schema，不表示当前已存在正式评估：

```text
CompatibilityGateEvaluationKey = {
  ProductProfileKey,
  CompatibilityDomain,
  CompatibilityGateId,
  TransportProfileRevision,
  ProtocolProfileRevision,
  RuntimeProfileRevision,
  StorageProfileRevision,
  CompatibilityAssertionScopeId,
  CompatibilityAssertionScopeVersion,
  CompatibilityAssertionScopeDefinitionHash,
  CompatibilityAssertionScopeSerializationId,
  CodeRevision,
  BuildRevision,
  ExactCapabilityRevision,
  TranscriptAndTestBundleHash
}
```

状态表按以下规则携带 key 和回执：

- 完整 key 使用上述 15 个字段的同序单行表示：`Field=value;Field=value`。字段名不可省略、重复或换序；值不得为空，也不得含未转义的空白、分号、等号或占位符。
- 六个可变 revision 字段统一使用 `<id>@sha256:<64-hex>`：transport、protocol、runtime、code、build 和 exact capability；Recall 的 storage 也使用该格式，其他三域的 storage 只能是显式 `None@compat-storage-v1`。`latest`、`default`、裸版本名或其他无法按内容复核的别名都不是精确 revision。
- `Passed` 与 `Failed` 都使用固定八字段回执：`ReceiptSerializationId`、`Outcome`、`EvaluationKeyHash`、`EvidenceBundleHash`、`EvaluationDefinitionHash`、`ProtectedGitRef`、`CiRunRef`、`ApprovalRecordRef`。Outcome 必须等于状态表终态；三个 hash 分别绑定完整 key、证据 bundle 和本次评估定义；后三个引用必须指向受保护提交或 tag、CI 运行和人工审批记录，不能填 `latest` 或自由文本。
- 当前没有任何 `Passed` profile，因此现有八行均明确写 `NotIssued`，不能用空白表达。

当前仓库还没有可移植 bundle resolver、canonical EvidenceBundleHash 实现、受保护兼容发布 tag、CI run 与审批记录。定义完整性校验器对任何 `Passed` 或 `Failed` 无条件失败关闭；它只能验证结构与哈希，不能自行宣称外部 Git 保护、CI 或审批记录可信。上述设施和错 bundle/错定义/错 outcome/非受保护来源反例同时落库后，才能启用评估终态。项目不自建密码学验收基础设施。

`CompatibilityDomain` 是 `Trigger | SCPI | DCL-Status | Recall` 闭集，并与一个 `CompatibilityGateId` 一一对应。运行与存储配置不是可省略的上下文，而是按域冻结的依赖向量：

| 兼容域 | RuntimeProfileRevision | StorageProfileRevision | 原因 |
| --- | --- | --- | --- |
| Trigger | 本次运行配置的精确 revision | `None@compat-storage-v1` | 接纳、排队、合并、停止和完成规则受运行配置影响，本域不执行保存/召回 |
| SCPI | 本次运行配置的精确 revision | `None@compat-storage-v1` | recognition/effect、WAI/OPC 与命令执行顺序依赖运行配置；文件与召回另属 Recall 域 |
| DCL-Status | 本次运行配置的精确 revision | `None@compat-storage-v1` | DCL 对在途命令和状态寄存器的结果依赖运行配置，本域不读取持久化配置 |
| Recall | 本次运行配置的精确 revision | 本次存储配置的精确 revision | Recall 同时改变当前设置、活动运行、校准引用、文件工件和旧/当前结果可见性 |

两个字段必须在每个 key 中各出现一次；不参与的维度只能写表中的显式 `None@...` 版本，不能缺省、空置或当作通配。任一精确 revision 或 `None@...` 策略版本变化都形成新 key，旧回执不得复用。

正式发布后，相同 scope/version/hash 仍必须与精确 ProductProfileKey、代码/构建/能力 revision 共同形成不同 key，不能跨 profile 复用。四个域分别评估、分别保存回执；只有受保护发布记录中的 `CompatibilityClaimCompositionManifest` 明确列出多个完整 key、组合版本、CI run 和审批记录时，才对这些回执做合取。默认不把 SCPI 与 DCL-Status 合取，也不把 Trigger 与 Recall 合取。

兼容 scope 的候选 ID、version/hash、断言、关联 Decision 和逐 profile 待采集状态由[商用品行为证据 §2](../架构依据/01-商用品行为证据.md#兼容性验收门的唯一状态与断言)维护。该来源目前同样属于 `DraftPendingReview`；其中“唯一事实源”“已发布”等字样只能按候选 schema 阅读，不能越过本节的发布前置。当前约束是：

- 校验器固定四个候选 scope 的 Domain/Gate/Assertion/Decision 归属与顺序，并复算表内 hash；它不保存“已签发 current manifest”，也不产生兼容结论。
- 候选期断言或证据义务变化可以沿用候选 version 并重算 hash，不登记伪历史。首次正式发布后，才要求升版、登记真实旧定义/变更原因/回执处置并维护 replacement DAG。
- 删除或伪造候选行、stored/computed hash 不一致、隐藏受保护 GFM 结构、缺失 profile 行、把 pending source 标成评估终态，均失败关闭；但这些检查通过后 `vendor_compatibility_passed` 仍固定为 `false`。

运行 `python3 docs/reference/verify_scope_registry.py --self-test` 可执行这些代表性反证。

#### 12.3.2 类型与全链边界

- **`ASSERT-TYPE-L0-L3-001`**（`ARCH-TYPE-01 / TYPE-L0-L3@R1`）
  - 阻断条件：Raw 缺逐 series/span WaveSchema，span 有洞或重叠；Driver ABI/实际执行值无法表达冻结语义；Quantity、Correction、ReferencePlane、AccessPoint 混用。此 scope 不包含 Conditioning 或 NetworkModel。
  - 必需证据：ABI/schema/span 契约、逐段 property test、设备量化与实际值回传测试。
- **`ASSERT-TYPE-COND-NET-001`**（`ARCH-TYPE-01 / TYPE-COND-NET@S1`）
  - 阻断条件：Conditioning operation/placement 不闭合，NotRequired 改变 CorrectionState 或产生 transition，Observation→NetworkModel 后载荷没有匹配 Schema。
  - 必需证据：Conditioning exactly-once/NotRequired 与 NetworkModel bind 测试；不得要求 S3 校准或 S4 矩阵证据。
- **`ASSERT-CHAIN-RUNTIME-001`**（`ARCH-CHAIN-01 / CHAIN-RUNTIME@R2`）
  - 阻断条件：没有通过真实公共边界走通 `Simulator Driver → Hardware → Acquisition → Runtime → generic Observation/Result port`。
  - 必需证据：R2 公共 ABI/port 全链测试；层内 Fake 不得替代边界。
- **`ASSERT-CHAIN-PRODUCT-001`**（`ARCH-CHAIN-01 / CHAIN-PRODUCT@S1`）
  - 阻断条件：Channel、Measurement、Trace 没有经同一公共端口接入，或以层内 Fake 绕过产品链；Channel 配置不能合法保持 `0..N` MeasurementDefinition，或 Prepare/Initiate 在零个有效 MeasurementDefinition 时仍产生设备、Run 或结果交付副作用；Marker、MarkerCoupling、限值检查、纹波或带宽分析没有归属 L7 `TraceAnalysisService`，绕过产品 CAS/不可变当前迹线输入直接进入 L6、硬件或显示层。
  - 必需证据：S1 产品对象到通用结果端口的全链测试；Channel 配置 `0..N` 的产品事务，空/全无效集合在副作用前稳定拒绝，以及 `1..N` 有效 MeasurementDefinition 的 Prepare/Initiate 正例；另以当前不可变迹线结果走通 L7 Marker/限值/纹波/带宽最小分析链，断言 L6 和硬件调用增量为零。这里不要求 S2 Continuous、S6 完整数值 oracle 或 S7 持久化。

#### 12.3.4 Trigger、运行与结果提交

Trigger 的四个 Gate 在 S1、S2、S5 形成 12 条独立断言。每条只消费所属 scope 的 bundle；当前阶段仍要保留此前 scope 的有效回执，但不会把后期断言并入前期 key。

##### 单次扫描（`Single`）：`TRG-SINGLE@S1`

- **`ASSERT-TRG-ROUTE-SINGLE-001`**（`ARCH-TRG-01 / TRG-SINGLE@S1`）
  - 阻断条件：Single AdvanceEvent 未冻结 source、owner、单 Channel target 与 binding snapshot；TargetSelection 偷看资源；声明跨时钟组合却无可信映射。
  - 必需证据：单 Channel routing、binding revision、clock-correlation compile 正反例；不采集 Continuous/Group 结果。
- **`ASSERT-TRG-ADMISSION-SINGLE-001`**（`ARCH-TRG-02 / TRG-SINGLE@S1`）
  - 阻断条件：一次已提交的 Single 测量推进候选没有恰好建立一个完整身份的 `AdvanceEvent`、一个含唯一 `TargetSlot` 的 `TargetBatch`、一份指向精确父 Initiation 的 `BatchMembership` 和一个 Run；Run 的父与 membership 不一致；处于 Queued、Rejected 或 Cancelled 的候选却建立上述正式对象；pending/final 未复核 Open；Stop/ChannelDelete/generation cutoff 先胜仍接纳。单槽外部触发在第一个 arm 前未足额建立 `ExternalTriggerArmCycleReservation/PreAdmittedRunReservation`，或 arm 前 `AdvanceEvent/TargetBatch/TargetSlot/Run` 任一实例数非零；matching evidence 不是以单一 commit 同时创建全部对象、登记 membership 并把 reservation 转为 Run/child Lease；布防线性化点之后、调用方观察到回执之前丢失同代证据；重复 Initiate、Restart、Hold/Continue 产生双 live 父或复用旧身份。
  - 必需证据：Single 中已提交候选、AdvanceEvent、TargetBatch、TargetSlot、BatchMembership 与 Run 的 `1:1:1:1:1:1`，以及 Queued/Rejected/Cancelled 候选零正式对象的反例。对单槽 `EdgePulse/LevelGate` 从每个执行资源、future identity/记录槽、child Lease reservation 到第一个 arm 逐点 kill：arm 前 exact 向量足额、任一维少一零 arm，且四类对象实例数全为零。matching evidence commit 前后逐点 kill：提交前不可见半成品，提交后一次得到 `1:1:1:1:1:1`、Registered membership 和恰好一次 Run/child Lease 转换。另覆盖 Stop/ChannelDelete/generation cutoff 与 commit 竞态、evidence cursor 前后到达，以及 Initiate/Hold/Continue/Restart/Stop/Close first-wins。断言 `Hold cutoff→旧父 terminal→Held 下零 live→Continue 新 identity`，旧 terminal 不覆盖较新意图，任一观察点 live Initiation 数量 `<=1`。
- **`ASSERT-TRG-PROGRESS-SINGLE-001`**（`ARCH-TRG-03 / TRG-SINGLE@S1`）
  - 阻断条件：Single 不等于一次完整 execution，或 terminal 先于 ProgressReservation 与唯一 completion 收口。
  - 必需证据：Single=1 cursor/property test、重复/缺失完成和 terminal-before-release 负向测试。
- **`ASSERT-TRG-CLOSE-SINGLE-001`**（`ARCH-TRG-04 / TRG-SINGLE@S1`）
  - 阻断条件：Stop/Hold/Abort/Close 后 ingress 被 final/rollback CAS 重开，terminal 遗留 gate、queue、claim、evidence 无 disposition；旧父 terminal 后的 Continue/Restart/普通 Initiate 复用旧 identity、与旧 live owner 重叠；或只凭 Host isolation 把物理未知写成 Stopped/PhysicalQuiescent 并复用设备。
  - 必需证据：Single × Stop/Hold/Abort/Close × pending/final/rollback、Continue/Restart/普通 Initiate 表驱动测试，断言 Hold 后 Held 零 live、Continue 新 identity、旧父先收口、live 数量不超过一且资源归零；另验证 `SoftwareFenced` 只能得到物理状态不可知隔离，不能满足物理静止或设备复用门。

##### 连续扫描（`Continuous`）：`TRG-CONTINUOUS@S2`

- **`ASSERT-TRG-ROUTE-CONTINUOUS-001`**（`ARCH-TRG-01 / TRG-CONTINUOUS@S2`）
  - 阻断条件：Continuation 跨代继承旧 binding/latch，或后继 TargetBatch 改写冻结 source/owner/target/clock 关系。
  - 必需证据：多 TargetBatch 同 Initiation 的 routing/epoch/clock lineage，以及 rebind/epoch change 拒绝测试；`Queue/Reject/Coalesce/IgnoreWithDiagnostic` 四种忙时策略的有界容量、稳定处置和诊断正反例；不采集 Group 粒度结果。
- **`ASSERT-TRG-ADMISSION-CONTINUOUS-001`**（`ARCH-TRG-02 / TRG-CONTINUOUS@S2`）
  - 阻断条件：把 AdvanceEvent/TargetBatch envelope 预算冒充执行预算；单 Channel 的某个 TargetBatch 未取得完整最坏执行预算便建 Run；Stop 后仍接纳后继；同 Channel 的重复 Initiate 新建第二 live 父，或 Restart 在旧 Continuous 父排空前发布 successor。
  - 必需证据：单 Channel 长时逐 TargetBatch admission、每批完整资源向量 exact/少一单位、Stop cutoff/drain、背压、duplicate Initiate=`AlreadyInitiated` 与 Restart/Stop/Close first-wins；任何时刻该 Channel 至多一个 live 父，且 restart 后无 orphan。S2 不采集多目标、`PerTargetAdmission`、Group=N 或 mixed finite 证据。
- **`ASSERT-TRG-PROGRESS-CONTINUOUS-001`**（`ARCH-TRG-03 / TRG-CONTINUOUS@S2`）
  - 阻断条件：Continuous 被 TargetBatch/count 自然终结，每个已接纳 TargetBatch 的 ProgressReservation 未独立收口，或 Average Clear/Trace Hold Restart 被实现成常驻模式、跨 reset 复活旧 turn capability。
  - 必需证据：单 Channel `NoNaturalCompletion` 长时测试、逐 TargetBatch 进度、Stop/drain terminal 和慢消费者测试；Average Clear/Trace Hold Restart × turn 计算/提交/Stop/Close/epoch 切换表驱动测试，证明 reset 回执幂等、`StateGeneration/ResetRevision` 递增、旧 capability 失效且新 epoch 为空；另运行 24 小时 current-only Continuous，证明非显式 reset 路径的 durable capability/port、WAL、record、ResultArtifact/持久 ResultLease、Repository 调用和磁盘字节增量均为零，live slot、buffer、reader lease 与通知队列保持在冻结上限内。ZNB/SNA 忙时外观没有真机 transcript 时不解禁。该长时证据是 S2 增量，不能回填 R2 或 S1 回执。
- **`ASSERT-TRG-CLOSE-CONTINUOUS-001`**（`ARCH-TRG-04 / TRG-CONTINUOUS@S2`）
  - 阻断条件：handoff/Restart 产生零个或多个 successor、新旧 live 父重叠、复活已胜出的 Stop/Hold、Continue 重开旧父、跨代继承 latch、queued evidence 没有 Cancelled/Transferred receipt，或 Host 隔离后把设备标为已静止/可复用。
  - 必需证据：Continuous handoff 五终态 × queued evidence × Initiate/Stop/Hold/Continue/Abort/Restart/Close，并验证 Hold 后旧父 terminal、Held 零 live、Continue 唯一新 identity、每 Channel live 数量 `<=1` 与 source-zero transfer；主进程死、worker 阻塞、Host 死、ACK 丢、设备续扫时分别验证物理状态处置和设备隔离。

##### 分组扫描与细粒度推进（`Group`）：`TRG-GROUP-GRANULARITY@S5`

- **`ASSERT-TRG-ROUTE-GROUP-001`**（`ARCH-TRG-01 / TRG-GROUP-GRANULARITY@S5`）
  - 阻断条件：Group(N)/multi-Channel AdvanceEvent 未冻结完整 TargetSlot 集、per-binding selector 与 Point/Segment/Partial 粒度；跨 ClockDomain AllOf 无映射仍接纳；`TargetSelection`、`TargetBatchAdmissionPolicy` 与 `PhysicalExecutionTopology` 互相推导而非正交编译；同一 DeviceSession 的多个通道没有生成一次 arm/start 的 `SingleInstrumentSequence` 和逐槽结果映射；跨 DeviceSession 仅凭共享门便生成 `MultiDeviceSynchronizedGroup`，或时间对齐不是由唯一规范 `TimingAlignmentProof` 绑定共同参考时钟/时钟域映射、触发路径偏斜、逐设备 trigger→acquisition latency/jitter 上界、产品预算、实测 bundle 与联合最坏误差。
  - 必需证据：三轴笛卡尔积、目标顺序与 capability revision 的确定性编译/hash 测试；同一 DeviceSession 的 Channel/measurement sequence 正反例；跨设备无同步要求时拆成独立单台序列且不产生同步声明；对规范 proof 全字段 mutation、过期及越界测试，并将 declaration/dynamic-proof/activation 的 request/receipt 中 proof identity、revision、ContentHash 逐一改动。任一缺失或错绑都在路由发布或组门激活前失败关闭；商用品手册或主机时间戳不得充当跨设备同步证明。
- **`ASSERT-TRG-ADMISSION-GROUP-001`**（`ARCH-TRG-02 / TRG-GROUP-GRANULARITY@S5`）
  - 阻断条件：
    1. 在 S1 单目标预布防原子性之上，多目标 cycle 没有冻结全部目标的最坏资源向量与一份 `PreAdmittedRunReservation`/目标；matching evidence commit 只创建部分槽、部分 membership 或部分 Run/child Lease；每槽不是恰好一份 membership 指向恰好一个父 Initiation，或 Run 属于错误父；任一父拥有整个跨通道 TargetBatch；
    2. `AtomicAdmission/PerTargetAdmission` 被当成物理拓扑；一次设备调用会推进多个槽时，槽未共同就绪便 start/arm，或运行时临时删步骤改写已编译序列；
    3. `SingleInstrumentSequence` 对同一 DeviceSession 的每个通道分别 start/arm，产生 per-channel MaskedReady、组激活日志或多份设备执行权；设备序列步骤/结果不能唯一映射 TargetSlot；
    4. `MultiDeviceSynchronizedGroup` 缺静态能力声明、本地整批资源预留、逐设备证据槽、真实共享硬件门、完整 TimingAlignmentProof 或实机证据时仍执行第一台设备布防；
    5. 第一台设备 MaskedReady 前未持久 `Building` 来源记录；每个设备回执未先持久便处理下一设备；全部设备就绪后缺动态证明、ReadyToCall、证据槽、与声明相同的 timing proof identity/revision/ContentHash 或 Prepared 仍打开组门；
    6. 未持久提交 `Prepared→Invoking` 就打开硬件门，恢复见 Invoking 又重发，或同一身份物理激活超过一次；`ProvenNotActivated` 未撤防/隔离仍屏蔽设备，结果未知时伪造零启动；
    7. TargetBatch 内重新 Prepare、移动/撤销 Handle 或安装新方案；重复启动、部分 Restart 或 Hold/Continue 造成同一测量通道新旧父任务重叠。
  - 必需证据：
    1. 复用 `TRG-SINGLE@S1` 已要求的每目标预布防/commit 性质，另做 `N=0/1/max` 多目标组合 property test：目标向量的 checked sum exact 时才允许第一个 arm，任一目标或任一资源维减一均零 arm；matching evidence commit 后一次满足 `TargetBatch 1 *-- 0..N TargetSlot`、`Initiation 1 o-- 0..N BatchMembership`、每槽一个 Registered membership 和 `0..1 Run`，且全部 reservation 按目标恰好转为 Run/child Lease；覆盖批次跨多父、一父登记多批次及任一父 Stop/ChannelDelete 与整批提交竞态；
    2. `AtomicAdmission/PerTargetAdmission × SingleInstrumentSequence/MultiDeviceSynchronizedGroup` 组合测试，验证资源策略不改变硬件调用边界；不可拆物理单元必须全体就绪，否则零 start/arm；
    3. 单台仪器多通道：一次设备级 start/arm、逐步骤 receipt/result 唯一映射、per-channel MaskedReady 数为零、组激活来源/决定日志调用数为零；缺已验证 sequence 时以 `NoVerifiedSingleInstrumentSequence` 零副作用拒绝；

    3. [D4D 持久交付](./04D-持久化结果与恢复.md#955-持久交付的唯一提交与恢复协议)的历史字段完整性、identity/semantic/full-envelope 冲突矩阵、descriptor/lineage/provenance 重算、Repository revision 与 ResultArtifact/pin/lease 守恒；
    4. 工作流 `EvidenceStored→Installed|Rejected|OutcomeUnknownTransferred`、workspace CAS、恢复与 source-zero 逐边 kill；任何旧 durable recovery 对 live slot 的写入次数必须为零；
    5. `Disabled|LatestWins × None|RetainHistory|WorkflowEvidence` 组合矩阵，验证 live 与 durable 各自的稳定处置、完成屏障、故障隔离，以及 `SaveCurrentResult` 使用新 durable identity 且不重新打开原 Run。
  - 范围边界：正式 Gate 启用后，S1 依赖精确 `RESULT-COMMIT@R2` 回执，但不能复用 R2 fake 或证据包替代产品验收。当前两者都只是 `DraftPendingReview` 候选定义，不存在可声称的 `Passed` 前置；本 scope 首次验产品 live key/ordinal 以及历史/工作流持久字段，不要求 S7 Save/Recall/File 全事务，也不以 `DEC-PERSIST-001` 充前置。

<a id="race-prepare"></a>

#### 设备预备（`Prepare`）

- 必须覆盖的并发交错：最终执行状态早于调用返回、在途再次编辑、迟到成功、预备期间关闭。
- 关闭条件：generation/revision 精确命中；旧 handle 不泄漏；无双 Prepare。

<a id="race-deployment"></a>

#### 方案部署（`Deployment`）

- 必须覆盖的并发交错：父任务布防与退役 CAS、`AtomicAdmission/PerTargetAdmission` 子任务取得；由 L7 责任方模型和 L2↔L7 集成夹具覆盖重绑移交前后失败、设备预备被更新取代、旧退役围栏与新安装 CAS。
- 关闭条件：Pin/Lease 计数守恒；新旧 record 无双 Handle；descriptor/registry 同时切换；Handle transfer 证据来自 L7/跨层测试，不由 L5 pure compiler fake。

<a id="race-start"></a>

#### 设备启动（`Start`）

- 必须覆盖的并发交错：采样帧或最终执行状态早于启动调用返回、同步返回失败却收到事件。
- 关闭条件：provisional context 精确归属；违约失败关闭；无悬空 Run。

<a id="race-trigger"></a>

#### 触发（`Trigger`）

必须覆盖的并发交错：

- Stop 的 `Open@R→Closed@(R+1)` CAS，与以下步骤逐点交错：Ephemeral acceptance 内存登记、首次完整 identity/revision/Open guard、逐 pending 安装、final guard、`AcceptedWithTargetBatch`/TargetBatchCommitReceipt executor commit、逐 rollback 前后崩溃；
- 外部触发的 `ExternalTriggerArmCycleReservation` 逐资源预留、child Lease reservation、第一个 arm、matching evidence、acceptance commit 与 reservation 转 Run/Lease 的每个前后 kill 点；
- NextEligible 并发事件、跨域 clock update、普通 latch 累积/reset；
- 零 target 与全拒绝。
- 同一 DeviceSession 的多通道 sequence arm/start 与逐步骤结果回传；跨 DeviceSession 同步组的逐设备 MaskedReady、真实共享硬件门、唯一 TimingAlignmentProof 全链引用、ActivationSemantics tagged union，以及逐设备 trigger-arrival/acquisition timing evidence。

关闭条件：

- 无 receipt 时，同序 gate 全回滚并稳定取消；有 receipt 时，幂等 Registered；
- fresh acceptance 使用同一 parent/runtime guard；Ephemeral 不跨 RuntimeEpoch 恢复，CrossRestartAcceptance 在任何副作用前 Unsupported；
- Stop cutoff 先胜时，即使父未 terminal、Ephemeral record 已登记，也非 Accepted 且无 TargetBatch；
- accept 先提交时，membership 阻挡父 terminal；
- 零 target 仍产生唯一空 TargetBatch；全拒绝先全 Registered，再形成完整 disposition；
- 每个 TargetSlot 恰有一个 BatchMembership 指向一个父 Initiation；TargetBatch 可跨父但不归任一父所有；
- 外部触发在 arm 前资源/identity/记录槽/child Lease reservation 足额，但 AdvanceEvent、TargetBatch、TargetSlot 和 Run 实例数全为零；matching evidence commit 后基数、membership、Run/Lease 转换一次同时成立；
- 单台仪器序列的一次设备级调用覆盖冻结步骤，per-channel MaskedReady 和组激活 journal 调用数为零；跨设备同步能力、完整时间误差证明或实机证据不足时零 arm 拒绝；Unmask 回执不得伪造 arrival，任一分支缺真实 trigger-arrival/acquisition 实测或联合越界时都不得进入时间可比结果槽；
- 无 orphan pending。
- V1 所有 Single/Group/Continuous 的 acceptance/TargetBatch commit 全程 `RuntimeEpochEphemeral`，在磁盘只读、持久池耗尽时仍可运行，且 WAL、持久 record、Repository 与磁盘字节增量为零；CrossRestartAcceptance 固定 Unsupported，不能从 WorkflowDurable 状态或持久结果自动解禁。

<a id="race-atomic-admission"></a>

#### 整批准入（AtomicAdmission）

- 必须覆盖的并发交错：第一个或中间目标资源未就绪、整批全拒绝；外部触发预留 exact/减一、arm 前实例数、matching commit 前后基数；资源策略与物理拓扑交叉；单台仪器序列的一次设备级调用，以及跨设备同步组在第一台 arm、逐设备 MaskedReady、硬件门激活前后的故障。
- 关闭条件：首个物理执行单元前任一必需资源失败时零 child 执行且 disposition 完整；外部触发 arm 前零 Run/TargetSlot，matching commit 原子创建对象并转换预留；一次硬件调用覆盖的槽必须共同就绪，不能临时删改序列；单台仪器 sequence 不逐通道 start/arm，跨设备同步缺真实门、TimingAlignmentProof 或实测证据时有界拒绝；TargetBatchTerminal 后才从各父释放对应 membership。`AtomicAdmission` 只保证首次物理副作用前的全有或全无，不承诺回滚已发生测量。

<a id="race-processing"></a>

#### 数据处理（Processing）

必须覆盖的并发交错：

- Acquisition terminal 早于最后 Stage、live publish 或计划中的 durable disposition；
- live current 的 reserve/publish 与更高 ordinal、Recall/Reconfigure/Close/RuntimeEpoch 围栏交错；相同 ordinal 同内容重放和异内容冲突；
- current-only Continuous 长时运行并同时注入 Repository 不可用、磁盘只读与持久池耗尽；
- 仅对计划的历史/工作流目标，在 RecoveryRecord/`ReservedAtAdmission→DurableOwned→CommitInFlight` 各边界 kill；`beginCommit` 前故障零远端调用，ownership receipt 后恢复匹配 InFlight；
- 工作流 EvidenceStored 与 workspace install、ACK/NACK、unknown transfer，以及显式 durable state contribution 的 local-own/commit 边界；
- 计划 boundary 零 candidate；
- 显式 durable contributor 成功/失败/取消；默认实时 Average/Hold 不建立 durable contributor；
- 同一 StageStateKey 的两个 Run 交错完成 worker，仍只能按 commit ordinal 依次读取 R、R+1；
- 冻结图内外，以及先行/晚到的上游 terminal proof。

关闭条件：

- 只有硬件确认的正常物理终态或有效 `PhysicalQuiescenceEvidence` 才允许设备槽复用；软件合成 terminal、Host/Process isolation 和 `PhysicalStateUnknownQuarantined` 均不得复用精确设备；
- live obligation 只以 `PublishedCurrent|SupersededByNewer|InvalidatedByControl|Conflict` 收口，旧 ordinal/epoch 不覆盖新槽；live 缓冲责任归零不等待 Repository；
- `DurableDelivery=None` 时 durable capability、port、WAL、record、ResultArtifact/ResultLease 与 Repository 调用全部为零；
- 对计划的持久目标，任何外部调用前 recovery 与 obligation 原子绑定；`beginCommit/beginContributionCommit` 是唯一建立 durable owner 的入口；
- Repository 拒绝无效 receipt，且组合交付不宣称跨 live slot/Repository/工作区原子；EvidenceStored 未安装不能闭合；
- CommitInFlight 只到真实 disposition，或 source=0/target durable 的 unknown transfer；旧 durable recovery 不写 live current；
- 取消 proof 校验强类型完整 identity、冻结 edge 与 causal revision；
- CompletionFence 只覆盖计划中实际存在的 live/durable/state obligation，且对应 InFlight 都为 0；最终 terminal 只在 fence 后发布。

#### 产品迹线分析（`TraceAnalysisService`）

必须覆盖的并发交错：

- L7 产品 CAS、内存 plan lease 取得、主动刷新入队和产品响应返回逐点交错；
- 旧 revision 求值、当前结果更新、新 revision 主动刷新和旧输出发布乱序完成；
- 跨通道成员在不同 Run/Sweep/ordinal 更新，某成员缺失、删除或 schema 失配；
- 删除/重建分析对象、WorkingSet/AnalysisDefinition revision、Close 与输入快照/求值/发布交错；
- 设备从未启动、Ready/Held/Stop 状态下修改 Marker、MarkerCoupling、限值检查、纹波或带宽设置；
- plan/input/task/refresh/output/retired-reader 任一预算恰好耗尽与少一单位。

关闭条件：

- L7 应用单写者在产品 CAS 中替换唯一 plan pointer；旧 lease 完成旧 revision，新 lease 只见新 revision，失败保持旧产品与 plan；
- 编辑和刷新对 L6、Hardware deployment、Run、Sweep、Frame 零依赖，L6 与硬件 Start/Arm/Stop/Prepare 调用增量为零；
- 每个任务冻结一个有序输入版本集合与摘要，计算中不重读 latest；跨通道不要求相同 ordinal，缺失立即 `Indeterminate`；
- 输出精确绑定 WorkingSetRevision、definition/owner revision 与 input digest；旧 revision、已删除或 ABA 重建对象的迟到发布槽修改次数为零；
- 普通分析编辑没有第二状态投影或激活 Ticket/journal；产品 CAS 成功即 plan 生效，刷新可独立显示 `Refreshing/NoCurrent`；
- 纯 `TraceAnalysisDisplayBinding.visible/style` 修改不进入 L5/L4；所有资源在硬上限内拒绝、合并、排空并最终归零。

<a id="race-first-error"></a>

#### 首错

- 必须覆盖的并发交错：处理阶段或存储库首错与用户中止、自动停止、硬件失败同时到达。
- 关闭条件：四类事实正交；首错不覆盖硬件终因；control error 不覆盖原错。

<a id="race-backpressure"></a>

#### 背压

- 必须覆盖的并发交错：邮箱、计算、结果队列深度均为 1，且外部持有全部结果租约。
- 关闭条件：内存有界；admission 明确拒绝；旧 Run terminal 不等外部 lease。

<a id="race-handoff"></a>

#### 责任移交（Handoff）

- 必须覆盖的并发交错：布防后用户停止、最终 CAS 前后被新请求取代、回滚后恢复失败。
- 关闭条件：最多一个 successor；Stop 胜出不恢复；逐 Channel/binding outcome 完整。

<a id="race-recall-save"></a>

#### 召回与保留既有引用的保存

必须覆盖的并发交错：

- 首枚/逐枚 target-candidate-grandfather pin/lineage 与 Staging journal 两侧 kill；
- `Bound→Delete→Save→Unbind→Recall`；
- 伪造/altered/错 revision/non-live pin；
- Save×Unbind/rebind、gate 前后编辑；
- 旧 processing/ResultCommit、final CAS/late event；
- 旧 Handle cleanup 与显式后续 Prepare 失败。

关闭条件：

- 完整 identity/journal/预算先于 pin；
- Save 先冻结 exact binding/pin/lineage；Repository 只从 live 且 pre-delete root 合法的 source 签发 outgoing pin；
- startup 决议 PinAcquirePending/lineage claim，并释放 orphan；
- 合法链可递归 Recall 且源 pin 不 move；伪造链 fail closed；
- CAS 前零部分发布；CAS 后故障显式；
- Session 二元组隔离；旧结果不得成为当前结果；
- Gate/Pin/Lineage/Lease/RecoveryPool 归零。

<a id="race-file"></a>

#### 文件操作

必须覆盖的并发交错：

- Import 首次 publish/Close/source-zero transfer 各边界，且 Repository 永久断网；
- managed Export record/gate/fence 事务各边界 kill；
- payload/manifest write、file/parent fsync、replace 及 recovery-read 逐项永久阻塞；
- 隔离后旧 Host 迟到提交；
- startup 再次崩溃及外部并发改目标；
- RawPath/sidecar/AtLeastOnce/NonTransactional，或无可隔离 execution capability。

关闭条件：

- Close 不等远端；
- Export 首个目标 I/O 前，已由 process recovery 持完整责任；
- deadline 本地 source-zero 后，Ticket/WAI/Close 为 Transferred，且不冒充成功；
- 旧 Host fence 失效，同 target 为 QuarantinedUnknown，而其他 target/startup 继续；
- 四态不覆盖后继 generation；
- 所有不合格 profile 在 identity/journal/pool/temp/Host/首次 I/O 前稳定拒绝。

<a id="race-close"></a>

#### 关闭

- 必须覆盖的并发交错：已接纳、获取资源、处理中、最终结果交付各阶段关闭。
- 关闭条件：禁止新 admission；旧 exact context 收口；固定 slot 消费后才 join。

<a id="race-host-death"></a>

#### 隔离进程退出

- 必须覆盖的并发交错：数据块或最终事件在途、中止时限到期、主进程死亡但 Host 存活、厂商 worker 阻塞、Host 同时死亡、控制 ACK 丢失、设备继续扫描。
- 关闭条件：Session Fault/Closing；所有软件 Operation 唯一 terminal；共享块与 Credit 归零；另有 `SoftwareFenceEvidence` 和独立物理处置。只有设备回读、硬件看门狗/互锁或独立安全通道证明后置状态才是 `PhysicalQuiescent`；否则必须 `PhysicalStateUnknownQuarantined`，禁止精确设备的新 Open/Prepare/Arm/Start/复用。

竞态测试使用可控执行器、barrier 和虚拟时钟，不用长时间 `sleep` 证明。每个场景同时断言：terminal exactly-once、WorkSet/queue 最终为空、Ledger 守恒、没有回调越过 teardown，以及诊断快照能指出首错和高水位。
