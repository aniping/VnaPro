# TDC1VN08 / TDC1VN10 模拟驱动切换

当前以 **TDC1VN10 新接口**为基准，服务默认加载 VN10 模拟库。TDC1VN08 旧模拟器保留，统一命名为 `tdc1vn08_drv_sim`；此次只改构建目标和产物名称，旧接口、黄金数据与测试行为保持不变。

## 对应关系

| 驱动接口 | 模块目录 / 合同 | CMake target | Windows MinGW 动态库 | 启动参数 |
| --- | --- | --- | --- | --- |
| TDC1VN08 旧接口 | [VnaNativeSimulator](../VnaNativeSimulator/README.md) / [native_api_contract.h](../VnaNativeSimulator/include/vna_native/native_api_contract.h) | `tdc1vn08_drv_sim` | `libtdc1vn08_drv_sim.dll` | `--board tdc1vn08` |
| TDC1VN10 新接口 | [VnaBoardSimulator](../VnaBoardSimulator/README.md) / [board_api_contract.h](../VnaBoardSimulator/include/vna_board/board_api_contract.h) | `tdc1vn10_drv_sim` | `libtdc1vn10_drv_sim.dll` | `--board tdc1vn10`，也可省略 |

Linux 对应 `libtdc1vn08_drv_sim.so`、`libtdc1vn10_drv_sim.so`；macOS 对应 `libtdc1vn08_drv_sim.dylib`、`libtdc1vn10_drv_sim.dylib`。从仓库根目录构建时，两库及 `vna_server` 均输出到构建目录的 `bin` 下；例如 CLion 的 `cmake-build-debug/bin`。构建 `vna_server` 时还自动生成包含两库、运行库和资源的 `release` 发布目录，完整步骤见[自动生成发布目录](../README.md#自动生成发布目录)。单独构建模拟模块只生成该模块，不生成服务或完整发布包。

两个接口有同名但不同签名的函数，因此必须同时匹配 **接口选择**和**动态库**。本版本 `--board` 表示驱动 ABI，不能只看物理板卡名称：后续 VN08 驱动若已对齐 VN10 函数签名，应选择 `--board tdc1vn10`，并通过 `--driver` 指向提供新 ABI 的对应库。

## CLion 中切换

1. 停止正在运行的 `vna_server`。
2. 改名后首次使用，执行 **Reload CMake Project**，再构建 `vna_server`；该目标会同时构建 VN08、VN10 模拟库。
3. 打开 **Run → Edit Configurations**，选择 `vna_server`，Target 保持 `vna_server`。
4. 默认使用 10 单板：**Program arguments** 不填 `--board` 即可，或显式填入 `--board tdc1vn10`；只有要验证旧接口时才填 `--board tdc1vn08`。已有 `--config`、`--port`、`--web-port` 等参数可以继续保留。
5. 检查已有参数中的 `--driver`：本机构建优先删除此参数，让程序按 `--board` 选择 CMake 生成的默认库；若需要自定义路径，则同时改成对应库的绝对路径。
6. 重新运行，查看服务启动日志的 `board` 和 `driver`，确认接口和库路径一致。

环境变量保持原有配置，例如 `VNAPRO_SIM_MODE=noise;VNAPRO_SIM_SEED=42`。从 CLion 的 `bin` 目标运行时，Windows MinGW 的 `I:/mingw64/bin` 必须在服务进程的 `PATH` 中，用于解析 C++ 和线程运行库；完整 `release` 包已携带这些运行库。运行期间无法热切换接口，修改参数后需要停止并重新启动服务；刷新网页不会重新加载驱动。

## PowerShell 启动

下例使用当前项目的 CLion 构建目录；其他构建目录需对应修改程序路径。先在仓库根目录构建服务：

```powershell
Set-Location 'I:/ai/cc/VnaPro'
$env:PATH = 'I:/mingw64/bin;' + $env:PATH
cmake --build cmake-build-debug --target vna_server --parallel
```

不指定板卡参数时，默认启动 VN10：

```powershell
& 'I:/ai/cc/VnaPro/cmake-build-debug/bin/vna_server.exe'
```

选择 VN08，直接运行程序并传入参数：

```powershell
& 'I:/ai/cc/VnaPro/cmake-build-debug/bin/vna_server.exe' --board tdc1vn08
```

停止该进程后，改用 VN10：

```powershell
& 'I:/ai/cc/VnaPro/cmake-build-debug/bin/vna_server.exe' --board tdc1vn10
```

这两个命令直接启动可执行文件；CLion 中则只将 `--board ...` 填入 Program arguments。服务默认仍为 SCPI `127.0.0.1:5025` 和 Web `http://127.0.0.1:8080/`；需要其他端口时，在任一命令后添加相同的 `--port`、`--web-port` 参数。

两种驱动共用 `config/vnapro.yml` 的仪器和日志配置、同一套服务及 WebUI，无需为切换驱动维护两套前端控制逻辑。公司离线构建继续使用 `third-part` 中的压缩包，不增加下载步骤。

## 部署与显式指定库路径

构建后复制整个 `cmake-build-debug/release` 目录即可部署。程序从自身目录选择对应驱动，并读取同目录的 `vnapro.yml` 和 `WebUI`，与启动工作目录无关。默认 VN10；切换 VN08 只需添加板卡参数，无需修改资源路径：

```powershell
& 'I:/ai/cc/VnaPro/cmake-build-debug/release/vna_server.exe' --board tdc1vn08
```

使用包外驱动时，`--driver` 会覆盖默认库路径，**改变 `--board` 不会覆盖已显式填写的 `--driver`**，两参数顺序也不影响这个规则。显式指定 VN08 库的示例：

```powershell
& 'I:/ai/cc/VnaPro/cmake-build-debug/bin/vna_server.exe' --board tdc1vn08 --driver 'I:/ai/cc/VnaPro/cmake-build-debug/bin/libtdc1vn08_drv_sim.dll'
```

切换 VN10 时，将两个参数分别改为 `--board tdc1vn10` 和对应的 `libtdc1vn10_drv_sim.dll` 绝对路径。完整发布包默认使用程序旁的资源；只有采用包外配置或页面时，才需显式填写 `--config`、`--web-root`。外部启动脚本若引用旧库文件名，应更新为本页的新名称，不能只重命名旧 DLL 后用另一个 ABI 加载。

Linux/macOS 从根构建目录启动示例：

```bash
./build/bin/vna_server --board tdc1vn08 --driver "$PWD/build/bin/libtdc1vn08_drv_sim.so"
```

macOS 将后缀改为 `.dylib`。`--driver` 均要求绝对路径；使用包外动态库时，其依赖也需位于系统可解析的位置，必要时配置 Linux 的 `LD_LIBRARY_PATH`、macOS 的 `DYLD_LIBRARY_PATH` 或 Windows 的 `PATH`。自动发布收集的运行库已放在程序旁；本次发布运行验证使用 Windows MinGW，其他工具链与平台需在对应环境复验。

## 验证入口

从仓库根目录完成全目标构建后，运行两种模拟器及对应核心集成测试：

```powershell
cmake --build cmake-build-debug --parallel
cmake -E chdir cmake-build-debug ctest -R '^(native_|board_|core_native|core_board)' --output-on-failure
```

上述 CTest 名称保持原来的 `native_*` 和 `board_*` 分类，改名的是 CMake target 与可执行产物。启动日志打印实际选择；成功启动后，浏览器和 SCPI 继续通过原入口验证完整采集链路。
